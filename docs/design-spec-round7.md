
# Design Spec รอบ 7: Push Notifications, Road-Snap, Vibe/Mood, Niche Filters, Dark Mode, Shared Impact (ส่วนต่อของ docs/design-spec.md และ docs/design-spec-round6.md)

ขอบเขต: US-42..US-47 ตาม `docs/requirements-round7-ba.md` (ไม่แก้ `docs/design-spec.md`)
ลำดับความสำคัญ: เอกสารนี้ "ทับ"/ต่อยอดเฉพาะจุดที่ระบุ (PickupScreen S-34 เดิม, CommuteCardDeck F-7/F-8 เดิม, /nearby S-13, สร้างทริป S-10..S-12, /me และ /me/settings เดิม, UnifiedRideScreen F-1..F-4 เดิม, D.1 tone token เดิม) ส่วนที่ไม่กล่าวถึงใช้ตาม design-spec.md และ design-spec-round6.md เดิมทั้งหมด
ข้อความที่อ้างอิงระบบ: ใช้ชื่อ semantic token เดิม (rider.* / driver.*) และเพิ่มชุดใหม่ `rider-dark.*` / `driver-dark.*` ตามระเบียบวิธีเดียวกับ D.1 เท่านั้น ไม่สร้างระบบธีมที่สาม
ไม่มีโค้ด ไม่เลือกเทคโนโลยี ไม่ตัดสิน business logic ที่ requirement ไม่ได้ระบุ — จุดที่ขัดแย้งกันถูกยกไปหัวข้อ "ข้อเสนอแนะที่อาจขัดกับ requirement" ท้ายเอกสารให้ PM ตัดสิน

## 0. หลักการเพิ่มเติมรอบ 7
- ทุกจุดที่แตะ flow เดิม (PickupScreen, CommuteCardDeck, SwipeToConfirmSlider, quick-reply แชท, router/guard) ต้องเป็น "ส่วนต่อ" ที่มองเห็นเป็นสถานะ/องค์ประกอบเพิ่มเติมเท่านั้น ห้ามออกแบบ flow เดิมใหม่ (ตาม requirement บรรทัด 6, 13, 77, 153)
- Push เป็นเพียง "ทางเข้าซ้ำ" (secondary entry point) ของหน้าที่มีอยู่แล้ว ไม่สร้างหน้าใหม่เพื่อรองรับ push โดยเฉพาะ ยกเว้นหน้าตั้งค่าการแจ้งเตือน
- ข้อความที่ผู้ใช้เห็นจาก push render จาก string table เดิมฝั่ง client เสมอ (ไม่มีข้อความอยู่ใน payload) — สรุปสั้น ๆ ในเอกสารนี้ (รายละเอียด mapping payload/technical เป็นหน้าที่ทีม engineer ไม่ใช่ UX)
- ทุกสวิตช์/ตัวกรองใหม่ (US-44 tag/mood, US-45 institution/women-only) ต้องมีสถานะ "ปิดใช้งานพร้อมเหตุผล" ที่อ่านได้ด้วย screen reader เสมอ ไม่ใช้การซ่อนเฉย ๆ
- Dark mode ต่อยอด token เดิม ไม่ทำให้ component เดิม (ที่อ้าง rider.*/driver.*) ต้องรู้ว่าอยู่ใน mode ไหน — ใช้กลไก ToneScope (D.13) ขยายให้รับ brightness เพิ่มมิติเดียว (ดู G.6.4)
- Haptics/สั่นเป็นส่วนเสริมเท่านั้น (ตาม NFR a11y ของ requirement) ทุกจุดที่มี haptic ต้องมีข้อความ/ภาพสื่อผลเดียวกันอยู่แล้ว (ต่อยอดจาก F.4.4 เดิม ไม่สร้างใหม่)

## G.1 US-42: การแจ้งเตือนพุชระยะไกล (Push Notifications)

### G.1.1 User Flow: US-42 ขอสิทธิ์และรับการแจ้งเตือน
1. ผู้ใช้เข้าสู่ระบบครั้งแรก หรือกด "สร้างทริป" เป็นครั้งแรกของบัญชี (แล้วแต่ว่าอะไรถึงก่อน) ระบบตรวจว่ายังไม่เคยขอสิทธิ์แจ้งเตือน -> แสดง G-1 PushPermissionSheet (ใช้กลไกเดียวกับ ConsentSheet/PermissionRationale C-24 เดิม ไม่สร้าง component ระบบใหม่)
2. ผู้ใช้อ่านคำอธิบายเหตุผล (copy push.rationale_title/body) -> กด "อนุญาตการแจ้งเตือน" -> ระบบขึ้น system permission dialog ของ OS
3. (ก) อนุญาต: บันทึก device token ทันที (เงียบ ไม่มี dialog เพิ่ม) -> snackbar สั้น "เปิดการแจ้งเตือนแล้ว"
4. (ข) ปฏิเสธ/ปิด sheet: กลับไปหน้าเดิมทันที ใช้แอปต่อได้ปกติ (ไม่ block); ตั้ง flag ในเครื่องว่าถามแล้ว ไม่ถามซ้ำอัตโนมัติ — ผู้ใช้เปิดเองภายหลังได้ที่ G-2 NotificationSettingsScreen (ชี้ไปตั้งค่า OS ถ้า permission ถูกปฏิเสธระดับระบบ)
5. ทุกครั้งที่แอปเปิดและ token มีอยู่แต่ permission ระดับ OS ถูกถอนภายหลัง (ผู้ใช้ไปปิดใน OS settings) ระบบลบ token ออกจาก `device_tokens` แบบเงียบในพื้นหลัง (ไม่มี dialog รบกวนผู้ใช้)

### G.1.2 User Flow: US-42 แตะการแจ้งเตือน (deep link)
1. ผู้ใช้แตะ push notification (แอปปิด/พัก/เปิดอยู่หน้าอื่น)
2. ระบบอ่าน `kind` + id จาก payload opaque -> render ข้อความจาก string table -> นำทางตามตาราง G.1.4 โดยใช้ router/guard เดิมทั้งหมด (ไม่สร้าง guard ใหม่)
3. ถ้า session ยังอยู่: เปิดหน้าเป้าหมายทันที ทับ/แทนที่ stack ปัจจุบันแบบเดียวกับ deep link เดิมของรอบ 6 (`/matches/:id/live` เดิม) — ไม่ทำให้ state ของหน้าที่เปิดอยู่ก่อนหายถ้าไม่จำเป็น (เช่น แชทที่พิมพ์ค้างในหน้าอื่นยังอยู่เมื่อกด "กลับ")
4. ถ้า session หมดอายุ/หลุด (stale): redirect ไป `/auth/sign-in` ตาม guard เดิม (ข้อ 2.3 ของ design-spec.md) พร้อมเก็บปลายทางเดิมไว้เป็น "pending deep link" แบบเดียวกับ `returnTo` ที่มีอยู่แล้วใน D.9 (`/me/driver/register`) — หลัง login สำเร็จ นำทางต่อไปปลายทางเดิมทันทีโดยไม่ต้องแตะ push ซ้ำ; ถ้า login ไม่สำเร็จ/ผู้ใช้ยกเลิก ปลายทางที่ค้างไว้จะถูกทิ้ง (ไม่พยายามค้างข้ามเซสชัน)
5. ถ้าปลายทางไม่ valid อีกต่อไป (เช่น match ถูกยกเลิกไปแล้วระหว่างรอ login) ใช้ guard เดิมของหน้านั้น (เช่น `live.unavailable` ของ F.10) redirect ไปหน้าที่เหมาะสมที่สุด (เช่น `/matches/:id` หรือ `/trips`) พร้อม snackbar กลาง ไม่ error หน้าขาว

### G.1.3 Components

#### G-1 PushPermissionSheet
- Purpose: ขอสิทธิ์แจ้งเตือนพร้อมเหตุผลภาษาไทยก่อนขึ้น system dialog (ต่อยอด C-24 ConsentSheet/PermissionRationale เดิม ไม่สร้าง component ใหม่ทั้งหมด)
- Content: หัวข้อ, คำอธิบาย 1-2 บรรทัด (เหตุผล: ไม่พลาดคำชวน/ตอบรับ/ข้อความ/แจ้งเมื่อคนขับถึงจุดรับ), ปุ่มหลัก "อนุญาตการแจ้งเตือน", ปุ่มรอง "ไว้ทีหลัง"
- States: default / requesting (กำลังรอผล system dialog) / granted (snackbar แล้วปิด sheet) / denied (ปิด sheet เงียบ ไม่มี error) / already-decided (ไม่แสดง sheet นี้ซ้ำ ถ้าต้องการเปลี่ยนใจให้ไปที่ G-2)
- A11y: หัวข้อโฟกัสอัตโนมัติเมื่อเปิด, ปุ่มมี label ชัดเจน, ปิดด้วยปุ่มย้อน/แตะนอกได้เหมือน sheet อื่น

#### G-2 NotificationSettingsScreen (/me/settings/notifications ใหม่)
- Purpose: จุดเดียวให้ผู้ใช้ดู/แก้สถานะการแจ้งเตือนภายหลัง (เข้าถึงจาก /me/settings แถวใหม่ "การแจ้งเตือน")
- โครง: (1) แถวสถานะสิทธิ์ระดับ OS ("เปิดอยู่" / "ปิดอยู่ — ไปเปิดในตั้งค่าเครื่อง" พร้อมปุ่มพาไปหน้าตั้งค่า OS) (2) สวิตช์หลัก "รับการแจ้งเตือน" (มาสเตอร์ทอกเกิล — ดูเหตุผลด้านล่าง) (3) ข้อความอธิบายประเภทเหตุการณ์ที่จะได้รับ (รายการอ่านอย่างเดียว ไม่ใช่ทอกเกิลย่อย ในรอบนี้)
- **การตัดสินใจออกแบบ (มาสเตอร์ทอกเกิลเดียว ไม่ทำ per-kind toggle ในรอบนี้)**: เหตุผล — (ก) requirement/schema ที่ BA ระบุ (`device_tokens`) ไม่มีคอลัมน์เก็บ preference ต่อประเภทเหตุการณ์ การทำ per-kind ต้องเพิ่ม schema ใหม่ผ่าน /db-architect ซึ่งอยู่นอกขอบเขตที่ BA เขียนไว้ (ข) เหตุการณ์ทั้ง 4 ประเภท (คำขอใหม่/ตอบรับ/ข้อความ/ถึงจุดรับ/ยกเลิก) ล้วนเป็นเหตุการณ์ "action required หรือเวลาจำกัด" ของทริปที่กำลังดำเนินอยู่ ไม่ใช่การตลาด/spam จึงมีความเสี่ยงต่ำที่ผู้ใช้อยากปิดเฉพาะบางประเภท (ค) มาสเตอร์ทอกเกิลลดความซับซ้อนของ UI และ query — แต่ไม่ครบตามที่ US-42 acceptance criteria พูดถึง "การตั้งค่าเปิด/ปิดการแจ้งเตือน" อย่างกว้าง ๆ ไม่ได้ระบุว่าต้องละเอียดระดับ kind จึงตีความว่ามาสเตอร์ทอกเกิลเพียงพอ **— จุดนี้ยกให้ PM ตัดสินยืนยัน ดูหัวข้อความขัดแย้งท้ายเอกสาร**
- ปิดมาสเตอร์ทอกเกิล = ลบ device token ปัจจุบันออกจาก `device_tokens` ทันที (เทียบเท่าปิดสิทธิ์); เปิดใหม่ = ขอสิทธิ์ใหม่ถ้ายังไม่เคยอนุญาตระดับ OS (เปิด G-1 อีกครั้ง) หรือบันทึก token ใหม่ทันทีถ้า OS ยังอนุญาตอยู่
- States: loading / default (permission granted, master on) / master-off / os-denied (มาสเตอร์ toggle ใช้งานไม่ได้ พร้อมคำอธิบายให้ไปเปิดใน OS settings ก่อน) / saving / error
- A11y: สวิตช์มี label + สถานะอ่านได้ ("รับการแจ้งเตือน เปิดอยู่/ปิดอยู่")

#### G-3 NotificationTapHandler (ไม่ใช่ UI, กลไก routing)
- Purpose: จุดเดียวที่แปลง `kind`+id จาก payload เป็นปลายทาง ผ่าน router/redirect เดิม (ระบุไว้เพื่อให้ engineer ทราบขอบเขต ไม่ใช่ component ที่มี state ให้ผู้ใช้เห็น)

### G.1.4 Deep-link destinations ต่อ kind
| kind (opaque) | ข้อความที่ render จาก string table | ปลายทาง (ใช้ route/guard เดิม) |
|---|---|---|
| new_request (มีคำขอจับคู่ใหม่) | push.new_request | `/nearby/requests` (S-15 เดิม) ถ้าไม่พบคำขอนั้นแล้ว (ถูกถอน/หมดอายุ) -> `/nearby` (F-7 CommuteCardDeck) พร้อม snackbar กลาง |
| match_accepted (จับคู่ตอบรับแล้ว) | push.match_accepted | `/matches/:matchId` (S-16) ถ้าเข้าเงื่อนไขทริปกำลังเดินทางแล้ว ให้ guard เดิมพาไป UnifiedRideScreen ตามปกติ (F.10) |
| driver_arrived (คนขับถึงจุดรับ) | push.driver_arrived | `/matches/:matchId/live` -> UnifiedRideScreen (F-1) sheet เปิดที่ Collapsed |
| match_cancelled (จับคู่/ทริปถูกยกเลิก) | push.match_cancelled | `/matches/:matchId` (แสดง MatchEndNotice C-37 เดิม) ถ้าทริปตนเองยังกำลังเดินทางอยู่ -> UnifiedRideScreen สถานะ peer-ended (F.3.4) |
| new_message (ข้อความแชทใหม่) | push.new_message | ถ้าทริปกำลังเดินทาง -> UnifiedRideScreen ที่ระดับ Full โฟกัสช่องพิมพ์ (ตาม F.10 บรรทัด deep link แชท); ถ้าไม่ -> `/chats/:matchId` (S-18 เดิม) |

- ทุกแถวใช้ guard เดิมของปลายทางนั้น ๆ (ไม่มี guard ใหม่); ถ้าปลายทางไม่ valid แล้ว (ทริป/match หายไป) แสดง snackbar กลางแบบเดียวกับที่ระบบใช้อยู่แล้วเมื่อ deep link ล้าสมัย

### G.1.5 States/Empty/Error รวม (US-42)
- ไม่มี permission: แอปทำงานปกติทุกจุด ไม่มีจุดใด block การใช้งาน (ตาม AC)
- Token invalid ที่ FCM ปฏิเสธ: ไม่ใช่ UI ที่ผู้ใช้เห็นโดยตรง แต่ผลลัพธ์คือผู้ใช้อาจไม่ได้รับแจ้งเตือน — G-2 ควรมีสถานะ "ลองส่งแจ้งเตือนทดสอบ" (P2, ทางเลือกเสริมเพื่อ debug ให้ผู้ใช้ตรวจสอบเองว่าได้รับหรือไม่) — ระบุเป็นข้อเสนอ ไม่ใช่ AC บังคับ
- แตะ push ขณะแอปเปิดอยู่แล้วหน้าอื่น: แสดง in-app banner สั้นแบบ non-blocking (ใช้รูปแบบ OfflineBanner C-5/Snackbar C-29 เดิม ไม่สร้าง banner ใหม่) แตะ banner = นำทางตาม G.1.4 เดิม

## G.2 US-43: Road-Snapped Pickup Pin (ส่วนต่อ PickupScreen เดิม, S-34 `/matches/:matchId/pickup`)

**ขอบเขต**: แก้เฉพาะช่วง "ปล่อยหมุด -> ก่อนกดเสนอจุด" ของ S-34 เดิม ไม่แตะโครงหน้า ไม่แตะ off-route warning เดิม (pickup.off_route ยังทำงานเหมือนเดิมทุกประการ เป็นคนละกลไก)

### G.2.1 User Flow: US-43 Snap หมุดเข้าถนน
1. ผู้ใช้ลากหมุดบนแผนที่ของ S-34 แล้วปล่อยนิ้ว (flow เดิม)
2. ทันทีที่ปล่อย: หมุดเข้าสถานะ G-4 SnappingIndicator (ข้อความสั้นลอยเหนือหมุด "กำลังปรับหมุดให้ตรงถนน…" + spinner จิ๋วบนหมุด) เรียก OSRM `nearest` (timeout สั้น)
3. (ก) สำเร็จและระยะเบี่ยงอยู่ในเกณฑ์: หมุดขยับไปตำแหน่งที่ snap แล้วด้วยแอนิเมชันสั้น (150-200 ms, reduce-motion: ขยับทันทีไม่มีแอนิเมชัน) เปลี่ยนสไตล์หมุดเป็น "snapped" (G.2.2) พร้อมข้อความชั่วคราว "ปรับหมุดให้ตรงถนนแล้ว" (toast/caption ใต้แผนที่ 2-3 วินาทีแล้วจางหาย ไม่ใช่ dialog)
4. (ข) ผลเบี่ยงเกินเกณฑ์ปลอดภัย (กลางแม่น้ำ/ทางด่วน): ไม่ snap ใช้จุดดิบต่อ หมุดคงสไตล์ "raw" ไม่มีข้อความแจ้งเตือนเพิ่ม (เงียบ เพราะไม่ใช่ความผิดของผู้ใช้ และ off-route warning เดิมจะทำงานแยกต่างหากถ้าเข้าเงื่อนไข)
5. (ค) service ล้มเหลว/timeout/rate-limit: fallback ใช้จุดดิบทันที หมุดคงสไตล์ "raw" พร้อมข้อความเล็กใต้แผนที่ครั้งเดียว (ไม่ใช่ error สีแดง เป็น caption กลาง) "ใช้ตำแหน่งที่คุณปักไว้ (ปรับให้ตรงถนนไม่ได้ตอนนี้)" หายไปเอง 2-3 วินาที ไม่บล็อกการกดเสนอจุด
6. ผู้ใช้ยังลากแก้ตำแหน่งเองต่อได้หลัง snap เสมอ (การลากใหม่แต่ละครั้งวนกลับไปข้อ 2)
7. ผู้ใช้กด "เสนอจุดนี้" (ปุ่มเดิม): ใช้ตำแหน่งล่าสุดที่แสดงบนจอ (ไม่ว่า snapped หรือ raw) เรียก `propose_meeting_point` เดิมทันที ไม่มีขั้นตอนเพิ่ม

## G.3 US-44: Vibe Tags & Daily Mood

### G.3.1 User Flow: US-44 ตั้งแท็ก/mood ตอนสร้างทริป
1. ในขั้นตอนสร้างทริป (S-11 Create trip step 2 /trip/new/options เดิม หรือการ์ดกลับบ้าน 1 แตะ US-39 ถ้าเลือก "ไปตั้งทีละขั้น") ผู้ใช้เห็นส่วนใหม่ "สไตล์การเดินทางของคุณวันนี้ (ไม่บังคับ)" ต่อท้ายตัวเลือกเดิม (วิธีเดินทาง/บทบาท) ก่อนปุ่ม "ต่อไป"
2. ผู้ใช้แตะชิปแท็กจาก allow-list ตาม role ที่เลือกไว้ (Driver เห็นชุดของ Driver, Rider/ทั่วไปเห็นชุด Rider) เลือกได้สูงสุด 3 ชิป ชิปที่ 4 ที่พยายามเลือกจะถูกปฏิเสธพร้อมข้อความสั้น (ไม่ error หนัก)
3. ผู้ใช้พิมพ์ mood ในช่องข้อความสั้น (ไม่บังคับ) เห็นตัวนับถอยหลัง "12/35" ใต้ช่อง
4. ถ้าพิมพ์เกิน 35 ตัวอักษร: ตัวนับเปลี่ยนเป็นสีแดง (+ ไอคอนเตือน ไม่ใช้สีอย่างเดียว) ข้อความ inline "สั้นลงอีกนิดนะ (สูงสุด 35 ตัวอักษร)" ปุ่ม "ต่อไป"/"สร้างทริป" ยังกดได้แต่ระบบตัดข้อความเกินหรือปฏิเสธการบันทึกจนกว่าจะแก้ (ดูข้อเสนอ conflict ท้ายเอกสารเรื่องพฤติกรรมเมื่อเกิน — เสนอ "ปฏิเสธ inline ต้องแก้ก่อนไปต่อ" เป็นค่าเริ่มต้น)
5. mood ที่มีแต่ตัวเลขล้วน หรือเข้าเกณฑ์ blocklist ฝั่ง client (คำสั้น ๆ ที่ระบบตรวจแบบพื้นฐาน เช่น เบอร์โทร/ลิงก์ที่จับรูปแบบได้ง่าย — ไม่ใช่การกรองคำหยาบเต็มรูปแบบตาม assumption ข้อ 9 ของ BA) แสดงข้อความ inline "อย่าใส่เบอร์โทรหรือลิงก์ในข้อความนี้นะ" กันไปต่อจนกว่าจะแก้
6. กด "สร้างทริป"/"ต่อไป" สำเร็จ: แท็ก+mood ถูกบันทึกผูกกับทริปนั้น แสดงบนการ์ดของตนเองใน CommuteCardDeck (มุมมองคนอื่นเห็น), และเห็นตัวอย่าง preview ของตัวเองก่อนส่งได้ในขั้นสรุป S-12 (แสดงเป็น read-only แถวเพิ่ม)
7. ผู้ใช้แก้/ลบแท็ก-mood เองได้จากหน้ารายละเอียดทริป S-20 (ปุ่ม "แก้ไขสไตล์การเดินทาง") ก่อนทริปจบ/ก่อน 24 ชม.
8. เมื่อทริปจบ หรือผ่านไป 24 ชม. (แล้วแต่ถึงก่อน): ระบบล้างค่าอัตโนมัติ ไม่มี dialog รบกวน — ครั้งถัดไปที่ผู้ใช้เปิดหน้าเดิมเห็นช่องว่างเปล่าพร้อมข้อความอธิบายสั้น (mood.autocleared_notice) ถ้าเพิ่งถูกล้างไปหมาด ๆ

## G.4 US-45: ตัวกรองความปลอดภัย (สถาบันเดียวกัน + Women-Only)

### G.4.1 User Flow: US-45 เปิดสวิตช์สถาบันเดียวกัน

### G.6.2 Components

#### G-11 SharedImpactCard
- Purpose: แสดงผลกระทบเชิงบวก (CO2 โดยประมาณ) + ทางเข้าสู่การขอบคุณ
- Content: ไอคอนใบไม้/โลก + ข้อความหลัก impact.summary (ใส่ชื่อเล่นเพื่อนแบบเดียวกับสิทธิ์การมองเห็นชื่อเดิม) + ป้าย "(โดยประมาณ)" ติดกับตัวเลข + footnote 1 บรรทัดเล็ก (impact.footnote) + ปุ่ม "ส่งสติกเกอร์ขอบคุณ"
- States: default (มีตัวเลขคำนวณได้ > 0) / hidden (ทริปเดี่ยว/ไม่มีคู่ตอบรับ/บล็อกกัน/ระยะทาง = 0 หรือคำนวณไม่ได้ — ไม่แสดงการ์ดทั้งใบ ไม่แสดง "0 kg" ที่ดูแปลก) / sticker-sheet-open (ปุ่มยังคงอยู่เบื้องหลัง sheet) / sticker-sent-ack (หลังกลับจากหน้าแชทที่ส่งสำเร็จ ปุ่มเปลี่ยนเป็น "ส่งสติกเกอร์ขอบคุณอีกครั้ง" ไม่ล็อกปุ่มถาวร เพราะยังอยากให้ส่งซ้ำได้ถ้าอยากขอบคุณเพิ่ม)
- A11y: ตัวเลข CO2 อ่านพร้อมคำว่า "โดยประมาณ" เสมอในลำดับเดียวกัน ไม่แยกอ่านคนละที่

#### G-12 ThankYouStickerPicker
- Purpose: เลือกข้อความขอบคุณสำเร็จรูป (ไม่มีช่องพิมพ์อิสระ) ส่งผ่านกลไก quick-reply แชทเดิม
- Content: 3-4 ตัวเลือกปุ่มเต็มความกว้าง เรียงตามแนวตั้ง เช่น "ขอบคุณมากนะ!", "ขับปลอดภัยครับ", "เพลงเพราะมาก", (ตัวเลือกที่ 4 สำรอง เช่น "เจอกันใหม่นะ") — รายการ preset ที่แน่นอนอิงตาม requirement AC ข้อ 3 ของ US-47 เป็นหลัก
- States: default / selecting (แตะแล้วรอเปิดหน้าแชท) / dismissed (ปิดโดยไม่เลือก, ไม่มีผลใด ๆ)
- A11y: sheet โฟกัสหัวข้อ "เลือกข้อความขอบคุณ" เมื่อเปิด, แต่ละปุ่มอ่านข้อความเต็ม

### G.6.3 สูตรคำนวณ CO2 และป้ายกำกับ
- สูตร: ระยะทางที่เดินทางร่วมกัน (กม.) x 120 g/km = CO2 โดยประมาณ (แปลงหน่วยเป็น kg ในการแสดงผลถ้าค่ามาก) — ค่าคงที่นี้เป็นเรื่อง copy/เนื้อหา ไม่ใช่การตัดสินใจ UX เพิ่มเติมจาก assumption ของ BA
- ทุกจุดที่แสดงตัวเลขนี้ต้องมีป้าย "(โดยประมาณ)" ติดกับตัวเลขเสมอ (ไม่แยกเป็น disclaimer แยกต่างหากที่อ่านไม่ต่อเนื่องกับตัวเลข) สอดคล้องรูปแบบ ETA/ระยะที่มีป้าย "โดยประมาณ" ของรอบก่อน (เช่น pickup ETA ใน F.3.4)

### G.6.4 Haptic feedback points (ต่อยอด hook reduce-motion เดิมของ SwipeToConfirmSlider, ไม่สร้างระบบใหม่)
| จุด | ชนิด haptic | เงื่อนไข |
|---|---|---|
| ลาก CommuteCard (F-8) เริ่มลาก | selection (เบา) | เมื่อผู้ใช้เริ่มลากการ์ดเกินระยะ threshold เล็กน้อย (ไม่ใช่ทันทีที่แตะ เพื่อไม่สั่นทุกครั้งที่แตะเฉย ๆ) |

- **ข้อบังคับร่วม**: ทุกจุด haptic ข้างต้นต้องเช็คค่าตั้งของ OS ก่อนเสมอ — reduce-motion และ/หรือ haptics/vibration ที่ผู้ใช้ปิดไว้ระดับระบบ = ไม่สั่นเลย ไม่มีทางบังคับสั่นแทน (ตรงตาม NFR a11y ของ requirement); ผลลัพธ์ทางภาพ/ข้อความของการกระทำนั้น (การ์ดหลุดออก, thumb ล็อกปลาย) ยังคงทำงานปกติเหมือนเดิมไม่ว่าจะสั่นหรือไม่ (ใช้ hook `disableAnimations`/reduce-motion เดียวกับ F.4 เดิม ไม่ใช่ flag แยก)

## G.8 Accessibility (a11y) สรุปรอบ 7
- G-1/G-2: การแจ้งเตือน/สวิตช์ตั้งค่าอ่านสถานะได้ครบด้วย screen reader; ไม่พึ่งเสียง/สั่นเป็นทางเดียวในการสื่อว่าแจ้งเตือนมาถึง (ข้อความในแอปคู่กันเสมอ)
- G-2/G-4/G-8/G-10: ทุกสวิตช์/ปุ่มที่ disabled ต้องอ่านเหตุผลได้ทันทีที่โฟกัส ไม่ใช่ต้องแตะก่อนถึงจะรู้เหตุผล
- G-4 (marker snapped/raw): ความแตกต่างสื่อด้วยรูปทรง (วงแหวน+ไอคอน) ไม่ใช่สีอย่างเดียว + มี a11y label ประกาศเปลี่ยนสถานะ
- G-5 (VibeTagChipPicker): เพดาน 3 แท็กประกาศชัดเจนเมื่อถึงขีดจำกัด ไม่ปล่อยให้ผู้ใช้เดา
- G-6 (MoodTextField): ข้อความ error ประกาศแบบ assertive ครั้งแรกเท่านั้น ไม่ถี่ทุกตัวอักษร
- G.5 (dark mode): ทุก token ใหม่ผ่าน WCAG AA ตามตาราง G.5.1.3 รวมหมุดแผนที่ (G.5.2) ไม่พึ่งสีอย่างเดียวสำหรับข้อมูลสำคัญ (คงหลักการเดิมของ US-32/US-34)
- G.6 (haptics): เป็นส่วนเสริมเท่านั้น เคารพ reduce-motion/haptics setting ของ OS เสมอ (G.6.4); ตัวเลข CO2 อ่านคู่กับคำว่า "โดยประมาณ" เสมอ

## G.9 Empty / Error / Loading states สรุปรวม (เพิ่มจากที่ระบุในแต่ละหัวข้อ)
- G-1 PushPermissionSheet: ไม่มี "error" ที่ผู้ใช้ต้องแก้ไข มีแค่ granted/denied (ทั้งสองไม่ block การใช้แอป)
- G-2 NotificationSettingsScreen: os-denied ไม่ใช่ error แต่เป็นสถานะที่ต้องพาไปตั้งค่า OS
- G-4 SnappingIndicator: ไม่มี error สีแดงเต็มรูปแบบ มีแค่ caption fallback ชั่วคราว (fail-open เสมอ)
- G-5/G-6 (vibe/mood): validation error เป็น inline เท่านั้น ไม่ใช่ dialog บล็อกทั้งหน้า
- G-8 (safety filter): disabled-ineligible ไม่ใช่ error เป็นสถานะพร้อมทางแก้ (ลิงก์ไปยืนยัน/ตั้งค่า)
- G-11 SharedImpactCard: "hidden" คือสถานะปกติที่พบบ่อย (ทริปเดี่ยว/Peer เป็นส่วนใหญ่ของแอปตาม design เดิม) ไม่ใช่ error

## G.10 Motion notes สรุปรวม
- G.2 (snap animation): 150-200 ms ปกติ, ข้ามทั้งหมดเมื่อ reduce-motion (ขยับตำแหน่งทันที)
- G.5 (dark mode switch ขณะดูแผนที่/ระหว่างทริป): cross-fade tile สั้น, ข้ามเมื่อ reduce-motion (สลับทันที); ไม่ reload state ทริป/ตำแหน่งกล้อง
- G.6 (haptics): ไม่ใช่ motion แต่ผูกกฎเดียวกับ reduce-motion/haptics setting; ผลภาพ/ข้อความของการกระทำที่ haptic ประกบอยู่ (การ์ดหลุด, slider ล็อกปลาย) เป็น motion เดิมของรอบ 6 ที่มี reduce-motion อยู่แล้ว ไม่มี motion ใหม่จาก US-47 เอง

## G.11 ข้อเสนอแนะที่อาจขัดกับ requirement / จุดที่ต้องให้ PM ตัดสิน (รอบ 7)

### Q-G1 มาสเตอร์ทอกเกิลเดียว vs per-kind toggle การแจ้งเตือน (US-42)
- ประเด็น: BA ระบุ schema `device_tokens` เท่านั้น ไม่มีคอลัมน์ preference ต่อประเภทเหตุการณ์ เอกสารนี้จึงออกแบบเป็นมาสเตอร์ทอกเกิลเดียว (G-2) เพื่อไม่ต้องเพิ่ม schema ใหม่
- ทางเลือก A (ที่ออกแบบไว้): มาสเตอร์ทอกเกิลเดียว — ง่าย ไม่ต้องแตะ /db-architect เพิ่ม แต่ผู้ใช้ปิดได้แค่ "ทั้งหมด" หรือ "ไม่ปิดเลย"
- ทางเลือก B: per-kind toggle (เช่น แยกปิดเฉพาะ "ข้อความแชทใหม่" แต่เปิด "คนขับถึงจุดรับ") — ต้องเพิ่มคอลัมน์/ตาราง preference ใหม่ผ่าน /db-architect (นอกขอบเขต schema ที่ BA ระบุไว้ในรอบนี้) และเพิ่มความซับซ้อนของ G-2
- ต้องการคำตัดสินจาก PM ก่อน implement เพราะกระทบ schema (ทางเลือก B ต้องขอ /db-architect เพิ่ม)

### Q-G2 พฤติกรรมเมื่อ mood เกิน 35 ตัวอักษร (US-44)
- ประเด็น: requirement บอกแค่ "ยาวไม่เกิน 35 ตัวอักษร" ไม่ได้ระบุว่าต้อง "ตัดข้อความอัตโนมัติ" หรือ "บล็อกไม่ให้ไปต่อจนกว่าจะแก้"
- ทางเลือก A (ที่ออกแบบไว้ใน G.3.2): บล็อก inline จนกว่าจะแก้ให้สั้นลง — ชัดเจนตรงไปตรงมา แต่เพิ่มแรงเสียดทานเล็กน้อยตอนสร้างทริป
- ทางเลือก B: ตัดข้อความอัตโนมัติที่ตัวที่ 35 แล้วปล่อยผ่านทันที — ลื่นไหลกว่าแต่ผู้ใช้อาจไม่รู้ตัวว่าข้อความถูกตัด (ข้อความอาจดูค้างกลางประโยค)
- แนะนำ A แต่ให้ PM ยืนยัน

### Q-G3 ตำแหน่งหน้า GenderSettingsScreen ใน Me tab (US-45)
- ประเด็น: requirement ไม่ได้ระบุตำแหน่งวางในโครง /me ที่มีอยู่ (S-27..S-32) เอกสารนี้เลือกวางเป็นแถวใหม่ใน /me/settings (S-31 เดิม) เคียงกับ privacy settings เพราะเป็นข้อมูลอ่อนไหวเชิง PDPA เหมือนกัน
- ทางเลือก A (ที่ออกแบบไว้): อยู่ใต้ /me/settings เคียง privacy — สอดคล้องกับข้อมูลอ่อนไหวอื่น (เช่น ลบบัญชี, export ข้อมูล) ที่อยู่โซนเดียวกันอยู่แล้ว
- ทางเลือก B: อยู่ใต้ /me/verification (S-29) เพราะเป็น "ข้อมูลตัวตน" คล้ายอีเมล/องค์กร/เบอร์โทร แต่เสี่ยงให้ผู้ใช้เข้าใจผิดว่าต้อง "ยืนยัน" เพศ (ซึ่งไม่ใช่ ตาม requirement ที่ระบุว่าเป็น self-declare ไม่มีการยืนยัน) จึงอาจทำให้เข้าใจผิดเรื่องระดับความน่าเชื่อถือ
- แนะนำ A แต่ให้ PM ยืนยันเนื่องจากกระทบ IA (information architecture) ของแท็บ Me ทั้งหมด

### Q-G4 ตำแหน่งวาง SafetyFilterSwitchGroup: หน้าค้นหา (deck) เท่านั้น หรือหน้าสร้างทริปด้วย (US-45)
- ประเด็น: requirement AC เขียนว่า "ในหน้าค้นหา/deck" เป็นหลัก แต่ US-45 as-a-story พูดถึง "เลือกจับคู่เฉพาะ..." ซึ่งอาจตีความว่าควรตั้งค่าได้ตั้งแต่ตอนสร้างทริป (คล้ายตัวกรองที่ผูกกับทริปนั้น) หรือควรเป็นค่าที่ผูกกับ "ผู้ใช้" (ใช้ทุกทริปจนกว่าจะปิด) แทนที่จะผูกกับทริปเดียว
- ทางเลือก A (ที่ออกแบบไว้): สวิตช์อยู่ที่หน้า deck/ค้นหา เป็นค่าที่ปรับได้ทุกครั้งที่ค้นหา (ไม่ผูกกับทริปที่สร้างไว้ก่อนหน้า) — ยืดหยุ่นกว่า แต่ต้องเปิดใหม่ทุกครั้งที่เข้าหน้าค้นหาถ้าไม่ได้เก็บเป็นค่าเริ่มต้นระดับผู้ใช้
- ทางเลือก B: ผูกกับ "ทริป" เหมือน vibe/mood ของ US-44 (ตั้งตอนสร้างทริป แล้วคงอยู่ตลอดอายุทริปนั้น) — สอดคล้อง mental model เดียวกับ US-44 แต่ requirement ไม่ได้ระบุว่า filter ผูกกับทริปหรือผู้ใช้ ต้องยืนยันกับ /db-architect ว่าเก็บที่ไหน (คอลัมน์ `profiles` หรือ `trips`/`search params`)
