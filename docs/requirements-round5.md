# Requirements รอบ 5: แก้กฎจับคู่ car, รูปโปรไฟล์, แผนที่สด/นำทาง, รีวิว, โลโก้ (ส่วนต่อของ docs/requirements.md)

## สถานะเอกสารและลำดับความสำคัญ
- เอกสารนี้เป็นส่วนต่อของ `docs/requirements.md` (US-1..US-20 คงเดิม) ใช้เลข story ต่อจาก US-21
- ถ้าข้อความขัดกับ requirements.md ให้ถือเอกสารนี้เป็นหลัก ตามตาราง "รายการที่เอกสารนี้แทนที่" ด้านล่าง (ผู้ประสานงานควรนำไปแก้ requirements.md ตามตารางนั้นและต่อ Changelog ท้ายไฟล์นี้)
- ไม่มีการออกแบบ UI, ไม่มีโค้ด, ไม่เลือกเทคโนโลยี (ชื่อ config เป็นชื่อเรียกอ้างอิงตามธรรมเนียมเดิม เช่น `match.pickup_max_deviation_m`)

## บริบทรอบ 5
1. บั๊ก P0: ทริป car คู่หนึ่งบนข้อมูลจริง (ทริป Driver 5e7b… กับ Rider 333…) ห่างจุดเริ่ม 1 ม. ต่างเวลา 1.1 นาที เส้นทาง Rider ซ้อนบน Driver 100% แต่ไม่จับคู่ เพราะปลายทางห่างกัน 2,461 ม. > `match.dest_radius_m` (2,000 ม.) (หมายเหตุ: คำตัดสินผลิตภัณฑ์ล่าสุดทำให้ผลที่ถูกต้องของคู่นี้ขึ้นกับระยะรับส่งที่ Driver ตั้ง ดู US-21 และ Regression AC)
2. รูปโปรไฟล์ยกจาก P1 เป็น P0
3. แผนที่สดแสดงรถ/คนของคู่ + นำทาง (deep link P0, turn-by-turn P1)
4. คำแนะนำการตรวจสอบรถ/ใบขับขี่ (US-25: เลื่อนออกจากรอบ 5 แล้ว)
5. รีวิวและคะแนน (P1)
6. โลโก้แอปจริง
7. รายการข้อเสนอ (P2 ยังไม่ผูกมัด)

## คำตัดสินจากผู้ใช้ (รอบ 5) (ไม่ใช่สมมติฐาน)
- แนวคิดของแอป: "กลับบ้านแถวเดียวกัน โดยคนขับไปส่งเพื่อนร่วมทางแถวปลายทางของคนขับเอง" ไม่ใช่บริการรับส่งตามเส้นทาง (route-based ride service)
- กฎจับคู่ car Driver↔Rider (แทนที่กฎ corridor/ระยะเบี่ยงที่เคยตัดสินไว้ในรอบ 5; US-21): (ก) จุดเริ่มห่างกัน ≤ `match.car_origin_radius_m` (ค่าเริ่มต้น 2,000 ม.) (ข) ปลายทางของ Rider ต้องอยู่ห่างจากปลายทางของ Driver ไม่เกิน "ระยะรับส่งสูงสุดต่อทริป" `trips.max_dropoff_m` ที่ Driver เลือกเอง (ค) เส้นทางซ้อนกัน ≥ `match.min_overlap_pct` (40% เหมือนเดิม) (ง) เวลาออกเดินทางต่างกัน ≤ 30 นาที; บังคับที่ server ทั้งการค้นหา (ทั้งสองฝั่ง), การส่งคำขอ (request_match) และการตอบรับ (accept) ด้วยเงื่อนไขชุดเดียวกัน
- `trips.max_dropoff_m`: Driver เลือกเป็นเมตร จำนวนเต็ม ขั้นละ 100 ม. ช่วง 500-5,000 ม. ค่าเริ่มต้น 2,000 ม. ไม่เกินเพดาน config `match.car_dest_radius_max_m` (5,000); การเลือกในแอปเป็นตัวเลื่อน/ตัวปรับเป็นเมตร พร้อมปุ่มลัด 1,000/2,000/3,000/5,000; เก็บเฉพาะทริป Driver; แก้ไขไม่ได้ขณะมีคำขอค้างหรือการจับคู่ตอบรับ (ล็อกเดียวกับการแก้จุดเริ่ม/ปลายทาง); ตรวจความถูกต้องที่ server; แสดงต่อ Rider บนการ์ดว่า "คนขับรับส่งได้ไม่เกิน X เมตร/กม. จากปลายทางของเขา" (X เป็นเมตรเมื่อต่ำกว่า 1,000 ม. ไม่งั้นเป็น กม. ทศนิยม 1 ตำแหน่ง)
- กฎ corridor/ระยะเบี่ยง (`match.car_corridor_m`, `match.car_max_detour_m`, `match.car_min_rider_coverage`) เก็บไว้ที่ backend เท่านั้นเป็น "ทางเลือกที่ปิดเป็นค่าเริ่มต้น" ผ่านสวิตช์ `match.car_rule` = 'neighbourhood' | 'corridor' (ค่าเริ่มต้น 'neighbourhood') สำหรับการทดลองอนาคต ไม่มี UI; ไม่แสดง `approx_detour_m` อีกต่อไป
- หมวดคำอธิบายเมื่อไม่พบผลเป็น: has_results / none_found / far_destination (ปลายทางของ Rider เกินระยะของ Driver หรือกลับกัน) / far_origin ทั้งหมดเป็นหมวดเท่านั้น (category-only); โหมด Peer (เดิน/ขนส่งสาธารณะ/แท็กซี่) คงเดิม
- เวลาต่างกันไม่เกิน 30 นาทีคงเดิม; รูปโปรไฟล์เป็น P0; ความเป็นส่วนตัวของรูป: เฉพาะคู่ที่จับคู่ตามกรอบเวลาเดิม
- นำทาง: P0 = แสดงเส้นทาง + เปิดแอปนำทางภายนอก (Google Maps/Apple Maps); P1 = รายการเลี้ยวจาก OSRM steps; นำทางด้วยเสียงอยู่นอกขอบเขต
- ข้อมูลรถ: MVP คงการแจ้งเอง; US-25 (ตรวจรูปรถ/ใบขับขี่ด้วยเอกสาร) เลื่อนออกจากรอบ 5 (deferred)
- รีวิว: P1 รอบนี้ (DB + UI พื้นฐาน) ไม่มีผลทางเงิน
- กฎแสดงคะแนนรวม (คำตัดสินของ orchestrator): แสดงค่ารวมบนการ์ดโปรไฟล์ทุกจุด (รวมการ์ดใกล้เคียง/nearby) เฉพาะเมื่อมีรีวิวที่เปิดเผยแล้ว ≥ 3; ต่ำกว่านั้นซ่อนองค์ประกอบนั้นทั้งหมด ไม่แสดงข้อความ "ยังมีรีวิวไม่พอ" หรือข้อความแทนใด ๆ
- รายงานรูปโปรไฟล์: รูปที่ถูกรายงานโดยผู้ใช้ต่างกัน (distinct) ตั้งแต่ 2 คนขึ้นไป ถูกซ่อนอัตโนมัติจากทุกคนจนกว่าผู้ดูแลตรวจ
- จุดลง: ไม่แชร์จุดลง/ปลายทางจริงของ Rider ให้ Driver; ให้ Rider เสนอ "จุดลงสาธารณะ" (P1) และมีข้อความตอบกลับด่วนในแชทเพื่อตกลงเรื่องจุดลง (P0)
- โลโก้: ใช้ PNG ที่ผู้ใช้ให้ (1024x1024 สี่เหลี่ยมมุมมนบนขอบขาวนวล ไล่สีน้ำเงินเป็นเขียว)
- รายการปรับปรุงเสนอ: ทั้งหมดเป็น PROPOSAL/P2 ยังไม่ผูกมัด และ "ทิปตอบแทน" ถูกตัดออกอย่างชัดเจน

## สมมติฐาน (รอบ 5)

### กฎจับคู่ car (US-21)
- สมมติฐาน: ชื่อ config ทั้งหมดเก็บที่จุดเดียวกับ config เดิม ไม่ hardcode: `match.car_rule` = 'neighbourhood' (ค่าเริ่มต้น; อีกค่าคือ 'corridor'), `match.car_origin_radius_m` = 2000, `match.car_dest_radius_max_m` = 5000 (เพดานของ `trips.max_dropoff_m`), `match.min_overlap_pct` = 40 (ค่าเดิม), ช่วงเวลา 30 นาทีใช้ค่าเดิม; ค่าเสริมของโหมด corridor (ปิดเป็นค่าเริ่มต้น): `match.car_corridor_m` = 1000, `match.car_max_detour_m` = 3000, `match.car_min_rider_coverage` = 0.80
- สมมติฐาน: `match.dest_radius_m` (2,000 ม. เดิม) ไม่ใช้กับ car ในโหมด 'neighbourhood' อีก (ใช้ `trips.max_dropoff_m` ของ Driver แทน) และยังใช้กับ Peer ตามเดิม; เกณฑ์จุดเริ่มของ car อ่านจาก `match.car_origin_radius_m` (ค่าเริ่มต้นเท่าเดิม 2,000 ม.) ส่วน Peer ยังอ่านค่าเดิม
- สมมติฐาน: "ระยะระหว่างปลายทาง" วัดเป็นระยะทางเส้นตรงบนผิวโลกระหว่างปลายทางของ Driver กับปลายทางของ Rider (ไม่ใช่ระยะตามถนน); เกณฑ์เป็น ≤ (เท่ากับพอดีผ่าน)
- สมมติฐาน: overlap ≥ `match.min_overlap_pct` วัดเทียบเส้นทางของ Rider เหมือนเดิม
- สมมติฐาน: `trips.max_dropoff_m` แก้ได้เมื่อทริปไม่มีคำขอค้างและไม่มีการจับคู่ตอบรับ (กติกาเดียวกับการแก้จุดเริ่ม/ปลายทางเดิม); เมื่อการจับคู่สิ้นสุดหรือคำขอถูกปฏิเสธ/ยกเลิก กลับมาแก้ได้
- สมมติฐาน: ทริป Driver เดิมที่ไม่มีค่า `max_dropoff_m` (ข้อมูลก่อนฟีเจอร์นี้ หรือค่าว่าง) ถือเป็น 2,000 ม. ทุกจุดที่ตรวจกฎ (ไม่ใช่ปฏิเสธหรือไม่จำกัด); ค่านอกช่วง/ไม่ใช่จำนวนเต็ม/ไม่ตรงขั้น 100 ม. ถูกปฏิเสธที่ server ไม่ปัดเงียบ ๆ
- สมมติฐาน: ถ้า config เพดาน `match.car_dest_radius_max_m` ถูกลดต่ำกว่าค่าที่ Driver บางคนเคยตั้งไว้ ตอนตรวจกฎใช้ค่าที่น้อยกว่าระหว่างค่าของทริปกับเพดาน (ไม่แก้ข้อมูลเดิมย้อนหลัง)
- สมมติฐาน: ทริปของ Rider ไม่มีระยะรับส่งของตนเอง; กฎบังคับที่ Driver เป็นผู้กำหนดเท่านั้น
- สมมติฐาน: คะแนนเรียงลำดับผลค้นหาเป็นฟังก์ชันที่ดีขึ้นเมื่อระยะจุดเริ่มน้อยลง, ระยะปลายทางน้อยลง, overlap สูงขึ้น, เวลาต่างกันน้อยลง; น้ำหนักอยู่ใน config; ผูกคะแนนเท่ากันด้วยกฎ deterministic (เช่น เวลาสร้างทริป แล้ว id); เกณฑ์ผ่าน/ไม่ผ่านตัดสินที่ threshold ไม่ใช่คะแนน
- สมมติฐาน: กฎใช้สมมาตรทั้ง Driver เห็น Rider และ Rider เห็น Driver (ผลตรงกันทั้งสองทิศ); การคำนวณระยะปลายทางทำที่ server เท่านั้น และไม่ส่งปลายทางของ Rider ให้ Driver (สอดคล้องคำตัดสินไม่แชร์ปลายทางจริงของ Rider ให้ Driver ใน US-24)
- สมมติฐาน: ทริปใหม่/ผลค้นหา/การส่งคำขอ/การตอบรับใช้กฎใหม่ทั้งหมด; คำขอค้างและการจับคู่ตอบรับที่มีอยู่ก่อนเปิดใช้กฎ ไม่ถูกประเมินซ้ำจนกว่าจะถึงขั้นตอน accept (ที่ตรวจซ้ำตามกฎเดียวกันเสมอ)
- สมมติฐาน: ความเสี่ยงยอมรับ: ในโหมด 'neighbourhood' ไม่มีการตรวจว่า Rider ลงตามทางหรือไม่ นอกจาก overlap 40% และระยะปลายทาง (ตรงกับแนวคิด "ส่งแถวบ้านคนขับ")
- สมมติฐาน: ตัวเลขที่แสดงผู้ใช้: ระยะรับส่งสูงสุดของ Driver เป็นค่าที่ Driver ตั้งเอง (ไม่ใช่ตำแหน่ง) จึงแสดงตามจริงได้; ไม่แสดงระยะห่างปลายทางจริงระหว่างสองทริป
- สมมติฐาน: corridor 1 กม. (โหมด 'corridor') แยกจาก `match.pickup_max_deviation_m` 500 ม. (เตือนจุดรับ US-18 P1) ไม่รวมเป็นค่าเดียวกัน
- สมมติฐาน (P1 hint): คำอธิบายเมื่อไม่พบผล เป็นหมวดเหตุผลรวมเท่านั้น (has_results / none_found / far_destination / far_origin) ไม่แสดงจำนวน ไม่แสดงเวลา/ตำแหน่ง/ระยะ/ตัวตนของทริปอื่น; หมวดเดียวต่อครั้งเลือกตามลำดับ far_destination > far_origin > none_found; Peer ใช้หมวดชุดเดียวกันตามกฎเดิมของ Peer (สมมติฐาน)

### รูปโปรไฟล์ (US-22)
- สมมติฐาน: ย่อฝั่งแอปให้ด้านยาวสุด ≤ 512 px, JPEG (คุณภาพ ~80), เป้าหมาย ≤ 300 KB; server รับไม่เกิน 1 MB เฉพาะ JPEG (ปฏิเสธชนิดอื่นแม้เรียก API ตรง); การเข้ารหัสใหม่ต้องตัด metadata ทั้งหมด (รวม EXIF/GPS)
- สมมติฐาน: 1 บัญชีมีรูปได้ 1 รูป (แทนที่เมื่ออัปโหลดใหม่) เก็บใน bucket ส่วนตัวที่ path แยกตาม user id
- สมมติฐาน: ผู้เห็นรูป = เจ้าของ และคู่ที่จับคู่ "ตอบรับแล้ว" ขณะทริปใช้งานหรือภายใน 24 ชม. หลังทริปจบ; ไม่เห็นในผลค้นหา คำขอที่รอตอบ/ถูกปฏิเสธ และไม่เห็นหลังยกเลิกการจับคู่ก่อนขึ้นรถ (ใช้กฎเดียวกับข้อมูลรถ US-17 AC "การจับคู่สิ้นสุด")
- สมมติฐาน: การตรวจเนื้อหาอัตโนมัติอยู่นอกขอบเขต; ใช้ "รายงานรูป" + ผู้ดูแลตรวจผ่านฐานข้อมูลโดยตรง (ไม่มี admin panel)
- สมมติฐาน: รูปหน้าเป็นข้อมูลส่วนบุคคลทั่วไป ไม่ประมวลผลชีวมิติ (ไม่จดจำใบหน้า/ไม่เทียบรูป) ตั้งไว้เป็นเงื่อนไข ถ้าทำอย่างอื่นต้องทบทวน PDPA

### แผนที่สดและนำทาง (US-23, US-24)
- สมมติฐาน: ตำแหน่งสดคงกติกาเดิม (สมมติฐานหลัก): ส่งเฉพาะขณะทริป "กำลังเดินทาง" ทุก 15 วินาที (ตั้งค่าได้ ขั้นต่ำฝั่ง server 5 วินาที) ความ "เรียลไทม์" จึงเป็นระดับ ~15 วินาที เพิ่มความสมูทฝั่งแสดงผล ไม่ใช่ความถี่ส่งสูงขึ้น; ถ้าต้องการถี่ขึ้นเป็นการตัดสินใจ PM (แลกกับแบตเตอรี่/โควตา Supabase Realtime)
- สมมติฐาน: ใครเห็นใคร: Rider เห็นตำแหน่งสดของ Driver จนจบทริป; Driver เห็นตำแหน่งสดของ Rider ก่อน Rider กด "ขึ้นรถแล้ว" เท่านั้น (คงสมมติฐานหลัง Rider ขึ้นรถแล้วหยุดแชร์); ผู้ชมต้องมีทริปของตน "กำลังเดินทาง" และการจับคู่ตอบรับอยู่
- สมมติฐาน: ETA คำนวณจากตำแหน่งปัจจุบันไปจุดหมายถัดไป (จุดรับก่อนขึ้นรถ, ปลายทางของผู้ชมหลังขึ้นรถ) ผ่าน routing สาธารณะ ปรับใหม่ไม่ถี่เกิน rate limit (สมมติ ≤ 1 ครั้ง/30-60 วินาที) และป้าย "โดยประมาณ" เสมอ; ถ้าเรียก routing ไม่ได้ ใช้ค่าประมาณจากระยะเส้นตรงและแจ้งว่าไม่แม่น
- สมมติฐาน: "ตัวกรอง/ควบคุมแผนที่" ตีความเป็นปุ่มควบคุมมุมมอง: กลับมาตามตำแหน่ง (recenter), พอดีทั้งสอง (fit both), ซูมเข้า/ออก; เลเยอร์ (เช่น เปิด/ปิดเส้นทาง) เป็นทางเลือก P2
- คำตัดสิน (แทนสมมติฐานเดิม): เป้าหมายนำทาง P0 = จุดรับที่ตกลงแล้ว (US-18) และปลายทางของตนเอง; จุดลง/ปลายทางจริงของ Rider ไม่ถูกเปิดเผยให้ Driver เป็นพิกัด (ปลายทางของ Rider มักเป็นบ้าน) ให้ตกลงกันผ่านแชท (ข้อความตอบกลับด่วน P0) และ Rider เสนอ "จุดลงสาธารณะ" ได้ (P1) ดู US-24
- สมมติฐาน: deep link ส่งเฉพาะพิกัดที่ผู้ใช้มีสิทธิ์เห็นอยู่แล้ว ไม่ส่งตำแหน่งสดของคู่หรือปลายทางของคู่; ครั้งแรกแจ้งผู้ใช้ว่าพิกัดจะถูกส่งให้แอปแผนที่ภายนอก
- สมมติฐาน: ข้อความรายการเลี้ยว (P1) ต้องเป็นภาษาไทยโดยแปลงจากประเภทการเลี้ยวของ OSRM; ชื่อถนนใช้ชื่อไทยเมื่อมี

### ข้อมูลรถ/ใบขับขี่ (US-25 เลื่อน) และรีวิว (US-26) และโลโก้ (US-27)
- สมมติฐาน (รีวิว): รีวิวให้กันได้เมื่อการจับคู่ตอบรับ และ Rider กด "ขึ้นรถแล้ว" (มีเวลา boarded) และทริปของผู้รีวิวเองจบด้วย "ถึงแล้ว"
- สมมติฐาน: หน้าต่างรีวิวเริ่มเมื่อผู้ใช้คนแรกของการจับคู่กด "ถึงแล้ว" และปิดหลัง 7 วัน; รีวิวเปิดเผย (ต่อผู้ถูกรีวิว/นับคะแนน) เมื่อ ทั้งสองฝ่ายส่งครบ หรือครบ 7 วัน อย่างใดอย่างหนึ่งก่อน
- สมมติฐาน: ส่งแล้วแก้ไม่ได้ (กันการปรับตามรีวิวอีกฝ่าย); ความคิดเห็น ≤ 200 ตัวอักษร ตัวเลือกแท็กกำหนดล่วงหน้า (รายการสุดท้ายเป็นของทีมผลิตภัณฑ์)
- สมมติฐาน: คะแนนแยก 2 บทบาท (ในฐานะคนขับ / ในฐานะคนนั่ง); แสดงค่าเฉลี่ย + จำนวนเมื่อมีรีวิวที่เปิดเผยแล้ว ≥ 3; ต่ำกว่านั้นซ่อนองค์ประกอบทั้งหมด (ไม่มีข้อความแทน) ตามคำตัดสินด้านบน
- คำตัดสิน: การ์ดโปรไฟล์คือที่ที่แสดงชื่อ+ป้ายของผู้ใช้อยู่แล้ว (รายการค้นหา รวมการ์ดใกล้เคียง/nearby คำขอ หน้าจับคู่) จึงแสดงค่ารวมที่ทุกจุดนั้นได้เมื่อครบเกณฑ์ ≥ 3 (ค่ารวมไม่เปิดเผยตัวตนของผู้รีวิว) (ปิดประเด็นเปิด 2)
- สมมติฐาน: ความคิดเห็นเห็นได้เฉพาะผู้ถูกรีวิว (หลังเปิดเผย) และผู้ดูแล; ไม่แสดงชื่อผู้รีวิว แต่ผู้ถูกรีวิวอาจอนุมานได้จากการเดินทางร่วมกัน
- สมมติฐาน: ผลของการลบบัญชี: รีวิวที่เขียนถึงผู้ที่ลบบัญชีถูกลบ; รีวิวที่ผู้ลบบัญชีเขียนไว้ถูกลบข้อความความคิดเห็นและตัดความเชื่อมโยงผู้เขียน คงเฉพาะคะแนน/แท็กแบบไม่ระบุตัวตนในค่ารวมของอีกฝ่าย (ฝ่ายกฎหมายทบทวน)
- สมมติฐาน: โลโก้ต้นฉบับมีขอบขาวนวลและมุมมนในตัวภาพ ไอคอนแอปบน iOS/Android ต้องไม่เห็นกรอบขาวหรือมุมซ้อน จึงต้องมีไฟล์ต้นฉบับแบบเต็มพื้นที่หรือให้ฝ่ายออกแบบยืนยันวิธีตัดขอบ (ประเด็นเปิด 3); ไอคอนบนเครื่องไม่เปลี่ยนตามบทบาท (Rider/Driver)

## User Stories (รอบ 5)

### US-21: จับคู่ car แบบ "กลับบ้านแถวเดียวกัน" ตามระยะรับส่งของคนขับ [P0] และคำอธิบายเมื่อไม่พบผล [P1]
As a Driver หรือ Rider ของทริป car, I want ให้ระบบจับคู่เมื่อจุดเริ่มอยู่ใกล้กัน เส้นทางซ้อนกันพอ และปลายทางของ Rider อยู่ในระยะที่ Driver ยอมไปส่งจากปลายทางของตน, so that Driver ส่งเพื่อนร่วมทางแถวบ้านตนเองได้ตามที่ตั้งใจ และ Rider ไม่เสียเวลากับคู่ที่ปลายทางไกลเกินไป

**Acceptance Criteria (P0):**
- [ ] ทริป car Driver↔Rider (โหมด `match.car_rule` = 'neighbourhood' ซึ่งเป็นค่าเริ่มต้น) จับคู่ได้เมื่อครบทุกข้อ: (ก) จุดเริ่มห่างกัน ≤ `match.car_origin_radius_m` (ค่าเริ่มต้น 2,000 ม.) (ข) ปลายทางของ Rider ห่างจากปลายทางของ Driver ≤ `trips.max_dropoff_m` ของทริป Driver (ระยะเส้นตรง) (ค) เส้นทางซ้อนกัน ≥ `match.min_overlap_pct` (40%) (ง) เวลาออกเดินทางต่างกัน ≤ 30 นาที (ตาม config เดิม)
- [ ] `trips.max_dropoff_m` (ทริป Driver เท่านั้น): จำนวนเต็มเป็นเมตร ขั้นละ 100 ม. ช่วง 500-5,000 ม. ค่าเริ่มต้น 2,000 ม. และไม่เกิน `match.car_dest_radius_max_m` (5,000); การเลือกในแอปเป็นตัวเลื่อน/ตัวปรับเป็นเมตร พร้อมปุ่มลัด 1,000/2,000/3,000/5,000; การสร้างทริป Driver โดยไม่ระบุค่าได้ค่า 2,000
- [ ] Server ตรวจค่า `max_dropoff_m` (ทดสอบเรียก API ตรง): ปฏิเสธค่าต่ำกว่า 500, สูงกว่าเพดาน config, ไม่ใช่จำนวนเต็ม, ไม่ตรงขั้น 100 ม., ติดลบ/ไม่ใช่ตัวเลข; ค่าที่ส่งมากับทริป Rider ถูกปฏิเสธหรือไม่ถูกเก็บ (ไม่มีระยะรับส่งบนทริป Rider)
- [ ] ล็อกการแก้ไข: ขณะทริป Driver มีคำขอค้าง หรือมีการจับคู่ตอบรับ ห้ามแก้ `max_dropoff_m` (ล็อกเดียวกับการแก้จุดเริ่ม/ปลายทาง) ทั้งที่ UI และ server (ทดสอบเรียก API ตรง: ถูกปฏิเสธและค่าไม่เปลี่ยน); เมื่อไม่มีคำขอค้างและไม่มีการจับคู่ตอบรับ แก้ได้และมีผลกับการค้นหา/คำขอถัดไป
- [ ] บังคับที่ server ด้วยเงื่อนไขชุดเดียวกัน (predicate เดียว ไม่แยกสำเนา) ในการค้นหา (ทั้ง Driver เห็น Rider และ Rider เห็น Driver), การส่งคำขอ (request_match) และการตอบรับ (accept): คำขอ/การตอบรับที่ไม่ผ่านถูกปฏิเสธแม้เรียก API ตรง; ตรวจซ้ำตอน accept ด้วยค่าปัจจุบัน
- [ ] Regression บั๊กจริง (ข้อมูลจำลองที่ไม่ระบุตัวบุคคล): ทริป Driver และ Rider ที่ระยะจุดเริ่ม 1 ม., ต่างเวลา 1.1 นาที, overlap 100%, ปลายทางห่างกัน 2,461 ม.: "ต้องไม่จับคู่" เมื่อระยะรับส่งของ Driver = 2,000 ม.; "ต้องจับคู่ได้" เมื่อระยะรับส่ง = 3,000 ม.; ทดสอบทั้งสองฝั่งของการค้นหา (Driver เห็น Rider / Rider เห็น Driver), request_match และ accept (ทั้ง 4 จุด ทั้งสองค่า); เป็นกรณีทดสอบอัตโนมัติถาวร
- [ ] ขอบเขต: ระยะปลายทางเท่ากับระยะรับส่งพอดี = ผ่าน; เกินเล็กน้อย (เช่น +1 ม.) = ไม่ผ่าน; จุดเริ่มเท่ากับ `match.car_origin_radius_m` พอดีผ่าน เกินไม่ผ่าน; overlap เท่ากับ 40% พอดีผ่าน; ต่างเวลา 30 นาทีพอดีผ่าน 31 ไม่ผ่าน
- [ ] ค่า config (`match.car_rule`, `match.car_origin_radius_m`, `match.car_dest_radius_max_m`, `match.min_overlap_pct`, เวลา 30 นาที) อ่านจาก config จุดเดียว เปลี่ยนแล้วผลเปลี่ยนโดยไม่แก้ตรรกะ (มีชุดทดสอบตรวจขอบ)
- [ ] ผลสมมาตร: ถ้า Driver เห็น Rider คนนี้ Rider คนนี้ต้องเห็น Driver คนนั้น และกลับกัน (ทดสอบ)
- [ ] `match.dest_radius_m` ไม่ถูกใช้กับ car ในโหมด 'neighbourhood'; Peer ยังใช้กฎเดิมและผลของ Peer ไม่เปลี่ยน: ชุดทดสอบ Peer เดิมผ่านโดยไม่แก้
- [ ] แสดงต่อ Rider บนการ์ดของ Driver (ผลค้นหา และหน้า/การ์ดอื่นที่แสดงการ์ด Driver ตามกฎการมองเห็นเดิม): "คนขับรับส่งได้ไม่เกิน X เมตร/กม. จากปลายทางของเขา" โดย X เป็นเมตรเมื่อต่ำกว่า 1,000 ม. (เช่น 500 -> "500 เมตร") ไม่งั้นเป็น กม. ทศนิยม 1 ตำแหน่ง (เช่น 1,000 -> "1.0 กม.", 2,500 -> "2.5 กม.", 5,000 -> "5.0 กม."); มีชุดทดสอบการจัดรูปแบบที่ค่า 500, 900, 1,000, 2,500, 5,000
- [ ] ไม่แสดง `approx_detour_m` หรือ "เบี่ยงประมาณ ~x กม." ที่ใดในแอปอีก; ไม่แสดงพิกัดปลายทาง/ระยะห่างปลายทางจริงระหว่างสองทริป และ API ที่ส่งให้ Driver ไม่มีปลายทางของ Rider (ทดสอบเรียก API ตรง)
- [ ] คะแนนเรียงลำดับ: ระยะจุดเริ่ม/ปลายทางน้อยกว่า, overlap มากกว่า, เวลาใกล้กว่า ได้คะแนนไม่น้อยกว่าเมื่อค่าอื่นเท่ากัน; ผลคำนวณซ้ำได้เหมือนเดิม และเสมอกันเรียงตามกฎ deterministic (ทดสอบ)
- [ ] กฎ role ตรงข้าม / 1 คู่ต่อทริป / ความเป็นส่วนตัวเดิม ยังใช้ครบ
- [ ] สวิตช์ทางเลือก: `match.car_rule` = 'corridor' ใช้กฎ corridor/ระยะเบี่ยง/ครอบคลุม (`match.car_corridor_m` 1,000, `match.car_max_detour_m` 3,000, `match.car_min_rider_coverage` 0.80) ที่ backend เท่านั้น ไม่มี UI ไม่มีข้อความให้ผู้ใช้เห็น ค่าเริ่มต้นเป็น 'neighbourhood'; ค่าที่ไม่รู้จักถูกปฏิเสธตอนเริ่มระบบหรือ fallback เป็น 'neighbourhood' พร้อม log (ตัดสินโดยผู้พัฒนา แต่ต้องไม่ทำให้จับคู่ผิดกฎ); ชุดทดสอบโหมด 'corridor' เดิมยังผ่านเมื่อเปิดสวิตช์ (เพื่อการทดลองอนาคต); ในโหมด 'corridor' ยังใช้ระยะรับส่งของ Driver หรือไม่ ให้ถือว่าไม่ใช้ (กฎโหมดนั้นเป็นอิสระ) และห้ามแสดง `approx_detour_m`
- [ ] ปรับเอกสารกฎที่ผู้ใช้เห็น (คำอธิบายในแอป) ให้สื่อว่า "จับคู่คนที่กลับแถวเดียวกัน คนขับเลือกได้ว่าจะไปส่งห่างจากปลายทางของตนไม่เกินเท่าไร"

**Acceptance Criteria (P1 คำอธิบายเมื่อไม่พบผล):**
- [ ] เมื่อผลค้นหาสำหรับทริป car (และควรใช้กับ Peer ด้วย) ระบบคืนหมวดเหตุผลเดียวจากชุด: `has_results` (มีผล ไม่แสดงคำอธิบาย), `none_found` (ยังไม่มีทริปที่รออยู่/ไม่มีที่เข้าเกณฑ์อื่น), `far_destination` (ปลายทางของ Rider เกินระยะรับส่งของ Driver หรือกลับกัน), `far_origin` (จุดเริ่มห่างเกิน); แสดงข้อความช่วยเหลือภาษาไทยตามหมวดพร้อมคำแนะนำสั้น ๆ (เช่น ปรับปลายทาง/ระยะรับส่ง หรือจุดเริ่ม)
- [ ] เป็นหมวดเท่านั้น (category-only): ห้ามเปิดเผยตำแหน่ง ระยะจริง เวลาที่แน่นอน จำนวน ค่าระยะรับส่งของ Driver รายคน หรือตัวตนของทริปอื่น ห้ามระบุเหตุผลรายบุคคล; หมวดเดียวต่อครั้งตามลำดับ far_destination > far_origin > none_found (สมมติฐาน)
- [ ] เหตุผลคำนวณที่ server ภายใต้ rate limit เดียวกับการค้นหา (กันการสอบถามซ้ำเพื่อเดาว่ามีใครอยู่แถวไหน) และไม่ทำให้ผลค้นหาปกติช้าลงเกินกรอบเดิม
- [ ] ไม่มีผลข้างเคียงต่อการจับคู่ (เป็นข้อมูลอ่านอย่างเดียว); ทดสอบว่า Rider ที่มีระยะปลายทางเกินระยะของ Driver ได้ `far_destination` และคู่ Regression ที่ระยะรับส่ง 2,000 ม. ให้หมวดนี้โดยไม่มีตัวเลข 2,461

**Dependencies:** เส้นทางของทั้งสองทริปต้องมีรูปทรงเส้นทางเต็มที่ backend ใช้ได้ (มีอยู่แล้วสำหรับ overlap); การเพิ่มคอลัมน์ `trips.max_dropoff_m` และค่าเริ่มต้นสำหรับทริป Driver เดิม (ระบบตรวจกฎถือ null เป็น 2,000); ฟอร์มสร้าง/แก้ไขทริป Driver (US-5) ต้องมีตัวเลือกระยะรับส่ง (ตามคำตัดสินผลิตภัณฑ์ รายละเอียด UI เป็นหน้าที่ฝ่ายออกแบบ); สวิตช์ `match.car_rule` ในไฟล์ config เดียวกับ config เดิม

### US-22: รูปโปรไฟล์ (อัปโหลด/ตั้ง/ลบ) [P0]
As a สมาชิก, I want ตั้ง เปลี่ยน และลบรูปโปรไฟล์จากคลังภาพหรือกล้อง, so that คู่ที่จับคู่กับฉันจำฉันได้และรู้สึกปลอดภัยขึ้น

**Acceptance Criteria:**
- [ ] เลือกรูปจากคลังภาพหรือถ่ายจากกล้องได้ (เว็บ: ตัวเลือกไฟล์); ขอสิทธิ์กล้อง/คลังภาพเมื่อจะใช้เท่านั้นพร้อมคำอธิบายไทย; ปฏิเสธสิทธิ์แล้วยังใช้ทางเลือกอื่นหรือใช้ต่อด้วย avatar ตัวอักษรย่อได้
- [ ] แอปย่อและบีบอัดก่อนอัปโหลด: ด้านยาวสุด ≤ 512 px, JPEG, ตัด EXIF/ตำแหน่ง; ไฟล์ที่ไม่ใช่รูป/เสีย/ใหญ่เกินกำหนดถูกปฏิเสธพร้อมข้อความไทย; server ปฏิเสธชนิด/ขนาดผิดแม้เรียกตรง (ทดสอบ)
- [ ] เก็บใน bucket ส่วนตัว path แยกตามผู้ใช้; ผู้ใช้เขียน/ลบได้เฉพาะรูปของตนเอง (ทดสอบ row/storage policy)
- [ ] เห็นรูปได้เฉพาะเจ้าของและคู่ที่จับคู่ตอบรับแล้วตามกรอบเวลาเดิม (ทริปใช้งานหรือ 24 ชม. หลังทริปจบ); ไม่เห็นในผลค้นหา คำขอที่รอตอบ/ปฏิเสธ; หมดสิทธิ์แล้วอ่านไม่ได้แม้รู้ path (ทดสอบ) และลิงก์เข้าถึงรูปมีอายุสั้น
- [ ] avatar ตัวอักษรย่อคงเป็น fallback ทุกที่: ไม่มีรูป, โหลดล้มเหลว, ออฟไลน์, หมดสิทธิ์ดู, หรือถูกรายงานแล้ว
- [ ] ลบรูปแล้ว ไฟล์ถูกลบจริงจาก storage (ไม่ใช่แค่ตัดการอ้างอิง) และทุกที่กลับเป็นตัวอักษรย่อภายในเวลาสมเหตุผล (แคชที่เครื่องคู่หมดอายุ/ถูกล้างเมื่อหมดสิทธิ์ดู)
- [ ] อัปโหลดรูปใหม่แทนรูปเก่า ไม่ทิ้งไฟล์เก่าค้าง; อัปโหลดล้มเหลวกลางทางแล้วรูปเดิมยังใช้ได้; ปุ่มปิดระหว่างรอ
- [ ] ก่อนตั้งรูปแรก แสดงคำอธิบายว่าใครเห็นรูปและเมื่อไร (เฉพาะคู่ที่จับคู่ ช่วงเวลาที่จำกัด)
- [ ] รายงานรูป: คู่ที่เห็นรูปกด "รายงานรูปนี้" พร้อมเหตุผลจากรายการได้; ผลคือบันทึกรายงาน (ผู้รายงาน, ผู้ถูกรายงาน, เวลา, เหตุผล) ให้ผู้ดูแลตรวจผ่านฐานข้อมูล และรูปนั้นถูกซ่อนจากผู้รายงานทันที; ผู้ดูแลลบรูปได้; ผู้ถูกรายงานไม่เห็นตัวตนผู้รายงาน
- [ ] ซ่อนอัตโนมัติเมื่อถูกรายงานหลายคน: รูปที่ถูกรายงานโดยผู้ใช้ที่ต่างกัน (distinct) ตั้งแต่ 2 คนขึ้นไปถูกซ่อนจากทุกคนอัตโนมัติ (ทุกที่กลับเป็น avatar ตัวอักษรย่อ) จนกว่าผู้ดูแลตรวจ; รายงานซ้ำจากผู้ใช้คนเดียวกันนับเป็น 1; การซ่อนบังคับที่ backend/storage policy ไม่ใช่แค่ UI (ทดสอบ: ผู้มีสิทธิ์เดิมอ่านรูปไม่ได้เมื่อเกณฑ์ครบ); ผู้ดูแลตัดสินคืนรูปหรือลบรูป
- [ ] ลบบัญชี: ลบรูปออกจาก storage พร้อมรายงานที่เกี่ยวกับรูปนั้นตามกรอบ US-15 (รายงานที่ผู้อื่นยื่นเก็บเฉพาะข้อมูลไม่ระบุตัวตนตามที่กฎหมายต้องใช้ ตัดสินโดยฝ่ายกฎหมาย)
- [ ] ไม่ log รูป/ชื่อไฟล์/ลิงก์รูปใน production; ห้ามใช้รูปเพื่อจดจำใบหน้าหรือเทียบตัวตน (สมมติฐาน)

**Dependencies:** bucket ส่วนตัวและนโยบายสิทธิ์ (ใช้ร่วมกับ US-25 รูปรถ ซึ่งเลื่อนออกจากรอบ 5); กรอบการเข้าถึงคู่ตามข้อมูลรถ; ปุ่มรายงานต้องมีจุดในหน้าจับคู่/แชท; ต้องมีเวลาฝ่ายกฎหมายอัปเดตนโยบายความเป็นส่วนตัว

### US-23: แผนที่สดแสดงพาหนะของคู่ + ตัวควบคุมมุมมอง + ETA [P0 / บางส่วน P1]
As a คนขับหรือคนนั่งที่จับคู่กันและกำลังเดินทาง, I want เห็นตำแหน่งสดของคู่บนแผนที่ (คนขับเป็นไอคอนรถ, คนนั่งเป็นไอคอนคน/หมุด) พร้อมเวลาโดยประมาณ, so that รู้ว่าอีกฝ่ายใกล้ถึงแค่ไหนและนัดพบได้ง่าย

**Acceptance Criteria:**
- [ ] (P0) เมื่อการจับคู่ตอบรับและทริปของทั้งสองฝ่ายกำลังเดินทาง ผู้ชมเห็นตำแหน่งคู่ตามสิทธิ์ในสมมติฐาน: Rider เห็น Driver ตลอด; Driver เห็น Rider จนกว่า Rider กด "ขึ้นรถแล้ว"; ตำแหน่งสดของผู้ชมแสดงด้วยเช่นกัน
- [ ] (P0) ไอคอนต่างกันตามบทบาท: รถสำหรับ Driver, คน/หมุดสำหรับ Rider; มีป้ายข้อความ/คำอ่านของ screen reader ไม่พึ่งสีอย่างเดียว
- [ ] (P0) ตำแหน่งอัปเดตตามที่ได้รับ และการเคลื่อนที่ของไอคอนระหว่างจุดต้องต่อเนื่อง (ไม่กระโดด) โดยไม่คาดเดาไปข้างหน้าเกินตำแหน่งล่าสุดที่ทราบ; ไม่ถ่วงการเลื่อน/ซูมแผนที่
- [ ] (P0) ตำแหน่งที่เก่าเกินเกณฑ์ (สมมติ > 45 วินาที ตั้งค่าได้) แสดงสถานะ "ตำแหน่งล่าสุดเมื่อ..." ไม่แสดงเหมือนสดอยู่; เมื่อการเชื่อมต่อหลุดแสดงข้อความและต่อใหม่อัตโนมัติ
- [ ] (P0) โหมดติดตาม (follow) ปรากฏเป็นค่าเริ่มต้นเมื่อเข้าหน้า; เมื่อผู้ใช้เลื่อนแผนที่เอง โหมดติดตามหยุดและมีปุ่ม "กลับมาที่ตำแหน่ง" (recenter) ให้กดกลับ
- [ ] (P0) ปุ่ม "ดูทั้งสองฝ่าย" (fit both) ปรับมุมมองให้เห็นทั้งตนเองและคู่ (หรือคนเดียวถ้าคู่ไม่มีตำแหน่ง)
- [ ] (P1) ปุ่มซูมเข้า/ออก; (P2) เลเยอร์ทางเลือก (เช่น เปิด/ปิดเส้นทาง)
- [ ] (P0) แสดง ETA โดยประมาณ: Rider เห็นเวลาที่ Driver จะถึงจุดรับก่อนขึ้นรถ; หลังขึ้นรถผู้ใช้แต่ละคนเห็นเวลาถึงปลายทางของตน; อัปเดตไม่ถี่กว่า rate limit ของ routing; เมื่อคำนวณไม่ได้แสดงค่าประมาณจากระยะเส้นตรงพร้อมป้ายไม่แม่น หรือซ่อน ETA อย่างสุภาพ ไม่ค้าง
- [ ] (P0) แสดงส่วนของเส้นทางนัดพบ/จุดรับที่ตกลงแล้ว (ถ้ามี) และเครดิต OSM ตามเดิม
- [ ] (P0) คู่ยกเลิก/no-show/จบทริป/บล็อก: ไอคอนของคู่หายทันทีและแสดงข้อความเป็นกลาง (ไม่ระบุเหตุผล) ตามกฎเดิม (US-18)
- [ ] (P0) ห้ามเห็นตำแหน่งสดของคู่ก่อนเงื่อนไขครบ (คำขอรอตอบ ค้นหา ยังไม่เริ่มเดินทาง หลังเลิกจับคู่) บังคับที่ backend/สิทธิ์ realtime ไม่ใช่แค่ซ่อนใน UI (ทดสอบ)
- [ ] (P1) ประหยัดแบตเตอรี่: หยุดส่ง/รับตำแหน่งความถี่สูงเมื่อไม่มีหน้าจอนี้เปิด (ยังส่งตามรอบปกติของทริป); ไม่ติดตามเบื้องหลังนอกทริป

**Dependencies:** Realtime และ rate limit/โควตา Supabase free tier; routing สาธารณะสำหรับ ETA; หน้าจอทริปกำลังเดินทางเดิม (US-9, US-12); สิทธิ์ตำแหน่ง while-in-use

### US-24: เส้นทางและการนำทาง [P0 deep link / P1 รายการเลี้ยว / P1 เสนอจุดลงสาธารณะ / P0 ตอบกลับด่วนเรื่องจุดลง]
As a คนขับหรือคนนั่ง, I want เห็นเส้นทางบนแผนที่และเปิดแอปนำทางไปยังจุดรับหรือปลายทางได้, so that ไปถึงจุดหมายได้ง่ายโดยไม่ต้องพิมพ์ที่อยู่เอง

**Acceptance Criteria:**
- [ ] (P0) แผนที่แสดงเส้นทางไปยังเป้าหมายถัดไป: Driver = จุดรับที่ตกลงแล้ว แล้วปลายทางของตน; Rider = จุดรับก่อนขึ้นรถ แล้วปลายทางของตน
- [ ] (P0) ปุ่ม "นำทางด้วยแอปแผนที่" เปิดแอปภายนอกไปยังจุดที่เลือก: iOS เสนอ Apple Maps (และ Google Maps ถ้ามี), Android เปิด Google Maps; ถ้าไม่มีแอปเปิดลิงก์เว็บแผนที่แทน; ล้มเหลวแล้วแสดงข้อความและไม่ทำให้แอปค้าง
- [ ] (P0) ถ้ายังไม่มีจุดรับที่ตกลงแล้ว ปุ่มนำทางไปจุดรับปิดพร้อมข้อความ "ยังไม่ได้กำหนดจุดรับ" (ไม่ใช้พิกัดที่ไม่ได้ตกลงกันหรือพิกัดตำแหน่งสดของคู่)
- [ ] (P0) ครั้งแรกที่กดแจ้งว่าพิกัดปลายทางจะถูกส่งให้แอปภายนอก (ตามนโยบายของแอปนั้น) และ deep link ส่งเฉพาะพิกัดเป้าหมายที่ผู้ใช้เห็นอยู่แล้ว ไม่รวมตำแหน่งสดหรือข้อมูลส่วนตัวของคู่
- [ ] (P0) จุดลง/ปลายทางจริงของ Rider ไม่ถูกแชร์ให้ Driver (ทั้งในแผนที่ ปุ่มนำทาง deep link และข้อมูลที่ API ส่งให้ฝั่ง Driver; ทดสอบเรียก API ตรง)
- [ ] (P0) ข้อความตอบกลับด่วน (quick replies) ในแชทเพื่อตกลงจุดลง: มีชุดข้อความสำเร็จรูปให้กดส่ง เช่น ขอลงที่จุดสาธารณะใกล้ปลายทาง, ลงตรงนี้ได้, ลงจุดนี้ไม่สะดวก, ขอเสนอจุดอื่น (รายการสุดท้ายโดยทีมผลิตภัณฑ์); ทั้งสองบทบาทใช้ได้เมื่อการจับคู่ตอบรับและแชทเปิดอยู่ตามกฎแชทเดิม; การกดส่งข้อความสำเร็จรูปไม่แนบพิกัดหรือชื่อสถานที่ปลายทางจริงของผู้ส่งโดยอัตโนมัติ
- [ ] (P1) Rider เสนอ "จุดลงสาธารณะ" (เช่น จุดที่ไม่ใช่บ้านหรือที่พักของตน) ให้ Driver: Driver ตอบรับหรือปฏิเสธได้; เฉพาะจุดที่ Rider เลือกเสนอและ Driver ตอบรับแล้วจึงใช้เป็นเป้าหมายนำทางฝั่ง Driver ได้; จุดที่ไม่ตอบรับหรือปฏิเสธไม่ถูกใช้และไม่ค้างเห็นได้; ไม่ใช้ปลายทางจริงของ Rider แทนอัตโนมัติ; ยกเลิกการจับคู่/ทริปจบแล้วจุดหมดสิทธิ์ตามกฎเดียวกับจุดรับ (US-18)
- [ ] (P1) รายการเลี้ยวในแอป (turn-by-turn list) จากขั้นตอนเส้นทางของบริการ routing: ข้อความไทยของแต่ละขั้น (ประเภทการเลี้ยว + ชื่อถนนถ้ามี + ระยะ), ไฮไลต์ขั้นปัจจุบันตามตำแหน่ง, แสดงเมื่อผู้ใช้เปิดรายการเท่านั้น
- [ ] (P1) ออกนอกเส้นทางเกินระยะที่ config ได้ แจ้งและขอคำนวณเส้นทางใหม่ ไม่ถี่เกิน rate limit; คำนวณไม่ได้ให้คงเส้นทางเดิมพร้อมข้อความ
- [ ] (P0) ไม่มีการนำทางด้วยเสียงในรอบนี้ และแอปไม่อ้างว่าเป็นการนำทางเต็มรูปแบบ; ข้อความเตือนให้ปฏิบัติตามกฎจราจร/ไม่ใช้มือถือขณะขับ (ข้อความสั้น ๆ ก่อนนำทาง)

**Dependencies:** ข้อกำหนดบริการ routing สาธารณะ (การเรียก steps และการคำนวณใหม่ต้องอยู่ในนโยบายการใช้งาน; ระบุจุดตั้งค่า endpoint ที่เปลี่ยนได้); การรับ deep link ของ Google/Apple Maps บนอุปกรณ์; จุดรับที่ตกลงแล้ว (US-18); แชทของการจับคู่เดิม

### US-25: การตรวจสอบรถและใบขับขี่ (คำแนะนำ) [เลื่อนออกจากรอบ 5 (DEFERRED)]
**สถานะ: เลื่อนออกจากรอบ 5 (deferred) ไม่อยู่ใน scope รอบนี้ ไม่ต้องพัฒนา/ทดสอบ; เนื้อหาด้านล่างเก็บไว้เป็นข้อมูลอ้างอิงสำหรับรอบถัดไป และ MVP คงข้อมูลรถแบบแจ้งเองพร้อมป้าย "ยังไม่ผ่านการตรวจสอบ" ตาม US-17/US-19 ตามเดิม**

As a Rider ที่จะขึ้นรถของ Driver, I want มั่นใจว่ารถตรงกับที่แจ้งไว้ และได้ทราบสถานะการตรวจสอบตามจริง, so that ขึ้นรถถูกคันและไม่เข้าใจผิดว่าแอปตรวจสอบคนขับแล้ว

**คำแนะนำ (สมมติฐาน/ข้อเสนอของ BA เพื่อให้ PM ตัดสิน):**
- MVP 0.1: คงข้อมูล ทะเบียน/รุ่น/สี แบบแจ้งเอง ตามเดิม พร้อมป้าย "ยังไม่ผ่านการตรวจสอบ"
- P1: รูปรถแบบ "ไม่บังคับ" (เห็นตัวรถและป้ายทะเบียน) อัปโหลดเข้า bucket ส่วนตัว ตรวจด้วยคนภายหลัง
- P1: ตรวจใบขับขี่ด้วยการอัปโหลดเอกสาร + ตรวจด้วยคน หลังมีเครื่องมือผู้ดูแลและผ่านฝ่ายกฎหมาย
- ไม่ทำใน MVP: สำเนาเล่มทะเบียนรถ/บัตรประชาชน (ข้อมูลอ่อนไหวตาม PDPA, ต้องมีหน้าจอผู้ดูแล, ต้องมีที่ปรึกษากฎหมาย/นโยบายเก็บรักษา)

**Acceptance Criteria (เลื่อน ไม่อยู่ใน scope รอบ 5):**
- [ ] (MVP, P0) ไม่เพิ่มการเก็บเอกสารใด ๆ นอกเหนือจากที่มีใน US-17/US-19; ป้าย "แจ้งเอง ยังไม่ผ่านการตรวจสอบ" คงเดิมทุกจุดที่แสดงข้อมูลรถ
- [ ] (P1) รูปรถ: Driver อัปโหลด/ลบได้ (กฎย่อรูป/ตัด EXIF/bucket ส่วนตัว/path ตามผู้ใช้เหมือน US-22); Rider เห็นได้เฉพาะเมื่อจับคู่ตอบรับแล้ว ตามกรอบเดียวกับข้อมูลรถ (US-17); ห้ามส่งออกนอกแอปผ่านแชร์/SOS (ทะเบียนที่อยู่ในรูปถือเป็นข้อมูลทะเบียนและอยู่ใต้สวิตช์ยินยอมเดิม จึงไม่ส่งรูป); ติดป้าย "รูปที่คนขับแจ้งเอง ยังไม่ผ่านการตรวจสอบ" จนกว่าจะมีการตรวจจริง
- [ ] (P1) สถานะการตรวจ (แจ้งเอง / รอตรวจ / ยืนยันแล้ว / ไม่ผ่าน) แยกจากข้อมูลที่แจ้งเอง; ป้าย "ยืนยันแล้ว" แสดงได้เฉพาะเมื่อมนุษย์ตรวจแล้วเท่านั้น (ห้ามป้ายที่สื่อว่าตรวจแล้วถ้ายังไม่ตรวจ)
- [ ] (P1) ตรวจใบขับขี่ผ่านการอัปโหลด: เก็บภาพเอกสารเฉพาะเพื่อตรวจ ลบภาพหลังตรวจเสร็จภายในกำหนด (สมมติ 30 วัน) และเหลือเฉพาะสถานะ + วันที่ตรวจ; ผู้ดูแลเห็นได้ตามสิทธิ์และมีบันทึกการเข้าถึง; ห้ามเก็บเลขบัตร/เลขใบขับขี่นอกจากจำเป็น
- [ ] (P1) การเปิดใช้ต้องผ่านฝ่ายกฎหมาย (release gate) และมีเครื่องมือผู้ดูแลก่อน; ถ้ายังไม่พร้อม ฟีเจอร์ยังปิดและ MVP ไม่ได้รับผลกระทบ

**Dependencies:** เครื่องมือผู้ดูแล (admin) ซึ่งยังไม่มี; bucket ส่วนตัว (US-22); ฝ่ายกฎหมาย; นโยบายเก็บรักษา

### US-26: รีวิวและคะแนนหลังเดินทาง [P1] (รอบนี้: ฐานข้อมูล + UI พื้นฐาน)
As a คนขับหรือคนนั่งที่เดินทางร่วมกันแล้ว, I want ให้คะแนน 1-5 ดาวพร้อมแท็กและความเห็นสั้น ๆ และเห็นคะแนนรวมของอีกฝ่าย, so that ช่วยให้ชุมชนปลอดภัยขึ้นและตัดสินใจจับคู่ได้ดีขึ้น

**Acceptance Criteria:**
- [ ] สิทธิ์รีวิว: เฉพาะสองฝ่ายของการจับคู่ตอบรับที่ Rider กด "ขึ้นรถแล้ว" และทริปของผู้รีวิวจบด้วย "ถึงแล้ว"; ไม่มีสิทธิ์เมื่อยกเลิกการจับคู่/no-show/ยังไม่ขึ้นรถ; รีวิวตนเองหรือคนที่ไม่ใช่คู่ของการจับคู่นั้นไม่ได้ (บังคับที่ backend ทดสอบเรียก API ตรง)
- [ ] 1 รีวิวต่อ 1 การจับคู่ต่อ 1 ทิศทาง (Driver→Rider, Rider→Driver) ส่งซ้ำไม่ได้; ส่งแล้วแก้ไม่ได้ (สมมติฐาน)
- [ ] เนื้อหา: ดาว 1-5 (บังคับ), แท็กจากรายการกำหนดล่วงหน้าตามบทบาทที่ถูกรีวิว (ไม่บังคับ; ตัวอย่าง: ตรงเวลา สุภาพ ขับปลอดภัย รถตรงตามที่แจ้ง / มาช้า ไม่ตรงนัด — รายการสุดท้ายโดยทีมผลิตภัณฑ์), ความเห็น ≤ 200 ตัวอักษร (ไม่บังคับ); server ตรวจความยาว/ค่าที่อนุญาต
- [ ] แบบมองไม่เห็นกัน (blind): ไม่มีฝ่ายใดเห็นรีวิวของอีกฝ่าย และค่ารวมไม่รวมรีวิวนั้น จนกว่า ทั้งสองฝ่ายส่งครบ หรือครบ 7 วันนับจากเปิดหน้าต่างรีวิว (ก่อนอย่างใดอย่างหนึ่ง); หลัง 7 วันปิดรับรีวิวใหม่
- [ ] ค่ารวม (กฎการแสดง): แสดง "ค่าเฉลี่ย + จำนวนรีวิว" บนการ์ดโปรไฟล์ทุกจุด (รวมการ์ดใกล้เคียง/nearby) แยกตามบทบาท (ในฐานะคนขับ/ในฐานะคนนั่ง) เฉพาะเมื่อมีรีวิวเปิดเผยแล้ว ≥ 3; น้อยกว่านั้นให้ซ่อนองค์ประกอบคะแนนทั้งหมด ไม่แสดงข้อความ "ยังมีรีวิวไม่พอ" หรือข้อความ/ตัวแทนอื่นใด และไม่แสดงค่าเฉลี่ยหรือดาวรายรีวิว (ทดสอบ: 0, 1, 2 รีวิวไม่มีองค์ประกอบนี้ใน DOM/หน้าจอ; 3 รีวิวแสดง; การ์ด nearby ใช้กฎเดียวกัน)
- [ ] ความเห็นเห็นได้เฉพาะผู้ถูกรีวิว (หลังเปิดเผย) และผู้ดูแล ไม่แสดงต่อสาธารณะหรือต่อคู่อื่น; ไม่แสดงชื่อผู้รีวิว
- [ ] รายงานรีวิว: ผู้ถูกรีวิวรายงานความเห็นว่าไม่เหมาะสมได้; รีวิวที่ถูกรายงานถูกซ่อนจากผู้ถูกรีวิวและถูกพักไม่นับค่ารวมจนกว่าผู้ดูแลตัดสิน (ผ่านฐานข้อมูล)
- [ ] ไม่มีผลลงโทษ ไม่มีผลทางเงิน และไม่ปรับผลการค้นหาอัตโนมัติในรอบนี้ (ไม่มี "ป้ายเชื่อถือ" หรือสิทธิ์พิเศษ); ห้ามใช้ถ้อยคำเชิงพาณิชย์
- [ ] ข้อมูลออกแบบให้ต่อยอดได้: เก็บรีวิวเป็นแถวแยก (คะแนน, แท็ก, บทบาทที่ถูกรีวิว, การจับคู่, เวลา, สถานะเปิดเผย/พัก) และมีมุมมองสรุปรวมต่อผู้ใช้ต่อบทบาท เพื่อให้ฟีเจอร์อนาคต (ป้ายเชื่อถือ ลำดับความสำคัญ) อ่านได้โดยไม่แก้โครงเดิม
- [ ] ลบบัญชี: ลบรีวิวที่เขียนถึงผู้นั้น; รีวิวที่ผู้นั้นเขียนไว้ถูกตัดความเห็นและความเชื่อมโยงผู้เขียน (ตามสมมติฐาน ฝ่ายกฎหมายทบทวน); ค่ารวมของอีกฝ่ายคำนวณใหม่ตามกฎ
- [ ] ผู้ใช้เห็นก่อนส่งว่า ความเห็นใครเห็นได้บ้าง และรีวิวจะเปิดเผยเมื่อไร

**Dependencies:** สถานะ boarded ของการจับคู่ (US-12/US-18) และ "ถึงแล้ว"; การ์ดโปรไฟล์ (US-4/US-6/US-7); ช่องทางรายงาน (ใช้ร่วมกับรายงานรูป US-22); ขอบเขตกฎหมายเรื่องข้อมูลบุคคลในความเห็น

### US-27: โลโก้และไอคอนแอป [P0]
As a เจ้าของผลิตภัณฑ์, I want ใช้โลโก้จริงที่ให้มาเป็นไอคอนแอปและโลโก้ในหน้าเปิดแอป/ต้อนรับ/เข้าสู่ระบบ, so that แบรนด์สอดคล้องกันทุกจุดและดูเป็นแอปจริง

**Acceptance Criteria:**
- [ ] ไอคอนแอป Android (adaptive), iOS และเว็บ (favicon + ไอคอน PWA ขนาดมาตรฐานรวมแบบ maskable) สร้างจากภาพโลโก้ต้นฉบับ 1024x1024 ที่ให้มา
- [ ] บนตัวเครื่องทุกรูปทรงมาสก์ที่เป็นไปได้ (วงกลม สี่เหลี่ยมมุมมน) ไม่เห็นกรอบขาว มุมซ้อน หรือโลโก้ถูกตัดขอบ; iOS ไม่มีช่องโปร่งใส (ผ่านการตรวจโดยฝ่ายออกแบบ/QA บนอุปกรณ์จริงหรือ emulator อย่างละ 1 ตัวขั้นต่ำ)
- [ ] โลโก้แสดงบน splash (US-1), onboarding (US-1) และหน้าเข้าสู่ระบบ/สมัคร (US-2/US-3) พร้อมข้อความทางเลือกสำหรับ screen reader ("กลับด้วยกันมั้ย")
- [ ] คงโทนสีของแอป (token เดิม: navy/blue/teal/green/mint สำหรับ Rider; Driver deep navy + amber) โดยไม่เปลี่ยนโทนที่กำหนดใน US-20; ไอคอนที่ตัวเครื่องคงเดิมไม่เปลี่ยนตามบทบาท
- [ ] โลโก้ไม่เบลอ/ผิดสัดส่วนในทุกขนาด (ตรวจที่ขนาดเล็กสุดที่แพลตฟอร์มกำหนด และหน้าจอความหนาแน่นสูง)
- [ ] ไฟล์ต้นฉบับถูกเก็บไว้ในโปรเจกต์เป็นสินทรัพย์ (แหล่งเดียวของความจริง) และมีคำอธิบายสั้น ๆ ว่าไอคอนอื่นสร้างจากไฟล์นั้นอย่างไร (ให้ทำซ้ำได้)
- [ ] ยืนยันว่าเจ้าของมีสิทธิ์ใช้ภาพตามกฎหมายทรัพย์สินทางปัญญา (สมมติฐาน: เจ้าของผลิตภัณฑ์เป็นผู้ให้ภาพและรับผิดชอบสิทธิ์)

**Dependencies:** ต้องมีภาพต้นฉบับแบบเต็มพื้นที่ (ไม่มีขอบขาว) หรือคำตัดสินของฝ่ายออกแบบว่าจะตัดขอบอย่างไร (ประเด็นเปิด 3); กระบวนการสร้างไอคอนของแต่ละแพลตฟอร์มเป็นหน้าที่ฝ่ายพัฒนา

### US-28: ข้อเสนอปรับปรุง (PROPOSAL) [P2 ทั้งหมด ยังไม่ผูกมัด]
As a ทีมผลิตภัณฑ์, I want รายการข้อเสนอที่มีเหตุผลกำกับ, so that ตัดสินใจรอบหน้าได้โดยไม่ปะปนกับ scope รอบ 5

- [ ] รวมอยู่ในนโยบายความเป็นส่วนตัว (วัตถุประสงค์ ใครเห็น เก็บนานเท่าใด) และการส่งออกข้อมูลของตน (P1)

### รีวิวและความเห็น [P1]
- [ ] คะแนนและความเห็นเป็นข้อมูลส่วนบุคคล: อ่านได้เฉพาะตามสิทธิ์ (ผู้ถูกรีวิว หลังเปิดเผย; ผู้ดูแล); ผู้เขียนเห็นรีวิวของตนเอง; ค่ารวมเปิดเผยตามเงื่อนไขขั้นต่ำ 3 (ต่ำกว่านั้นซ่อน ไม่มีข้อความแทน); ไม่ปรากฏใน realtime channel ที่คนอื่นรับได้ (ทดสอบ row-level)
- [ ] กลไก blind บังคับที่ server (ไม่ใช่ซ่อนใน UI): ก่อนเปิดเผยแถวรีวิวอ่านไม่ได้แม้โดยผู้ถูกรีวิวและไม่นับในค่ารวม
- [ ] รวมอยู่ในการลบบัญชีและการส่งออกข้อมูล (P1) และนโยบายความเป็นส่วนตัว; ความเห็นไม่ถูกบันทึกใน log/crash report ของ production
- [ ] ป้องกันการใช้ผิด: 1 รีวิวต่อการจับคู่ต่อทิศทาง, จำกัดความยาว, จำกัดอัตราการส่ง; ความเสี่ยงการปั่นคะแนนด้วยบัญชี/ทริปปลอมยอมรับใน MVP และบันทึกเป็นข้อจำกัด (ลดด้วยเงื่อนไขต้องขึ้นรถจริงและค่าเฉลี่ยขั้นต่ำ 3)
- [ ] ไม่ใช้คะแนนเป็นเงื่อนไขทางเงินหรือลงโทษอัตโนมัติ

### ตำแหน่งสดและแผนที่ [P0]
- [ ] สิทธิ์ดูตำแหน่งสดของคู่ (การจับคู่ตอบรับ + ทริปทั้งสองกำลังเดินทาง + Rider ยังไม่ขึ้นรถสำหรับทิศ Rider→Driver) บังคับที่ backend/Realtime ไม่ใช่ UI (ทดสอบ: ผู้ไม่มีสิทธิ์ subscribe ไม่ได้)
- [ ] ตำแหน่งสดหยุดทันทีเมื่อการจับคู่สิ้นสุด/ทริปจบ/ยกเลิก; การเก็บและลดความละเอียดตามกฎเดิม (7 วัน)
- [ ] การนำทางภายนอกส่งเฉพาะพิกัดเป้าหมายที่ผู้ใช้มีสิทธิ์เห็น (ไม่ส่งตำแหน่งคู่); แจ้งผู้ใช้ตอนใช้ครั้งแรก
- [ ] การเรียก routing (ETA, steps, reroute) ต้องเคารพนโยบาย/rate limit ของบริการสาธารณะ มีแคช timeout และจุดตั้งค่า endpoint; ล้มเหลวแล้วแอปไม่ค้าง (ตามข้อ NFR ประสิทธิภาพเดิม)

### การจับคู่ (US-21) [P0]
- [ ] ชุดทดสอบอัตโนมัติ: กรณีบั๊กจริง (ปลายทางห่าง 2,461 ม.: ไม่ผ่านเมื่อระยะรับส่ง 2,000 ม., ผ่านเมื่อ 3,000 ม. ทั้งสองฝั่งของการค้นหา, request_match และ accept), ตารางผ่าน/ไม่ผ่านทุกเงื่อนไข ขอบ threshold, ความสมมาตร, deterministic, การตรวจค่า `max_dropoff_m` และล็อกการแก้ไข, การจัดรูปแบบข้อความ เมตร/กม., Peer ไม่เปลี่ยน
- [ ] ค่า config (`match.car_rule`, `match.car_origin_radius_m`, `match.car_dest_radius_max_m`, `match.min_overlap_pct`, เวลาเดิม) และค่าของโหมด corridor เปลี่ยนได้ที่จุดเดียวและมีค่าเริ่มต้นในเอกสาร/README; ค่าเริ่มต้น `match.car_rule` = 'neighbourhood'
- [ ] predicate การจับคู่ car เป็นฟังก์ชันเดียวที่ใช้ร่วมกันทั้งค้นหา request_match และ accept (ไม่มีตรรกะซ้ำที่คลาดเคลื่อนได้) ตรวจได้จากชุดทดสอบเดียวกัน
- [ ] `trips.max_dropoff_m` ผ่านการตรวจชนิด/ช่วง/ขั้นที่ server และอยู่ใต้สิทธิ์แก้ไขของเจ้าของทริปเท่านั้น (ทดสอบ row-level: ผู้อื่นแก้ไม่ได้); การย้ายข้อมูลไม่ทำให้ทริป Driver เดิมเสียหรือหลุดจากการค้นหา (null = 2,000)
- [ ] ตัวเลขที่ส่งถึงผู้ใช้ไม่มีข้อมูลตำแหน่งแม่นยำ (ไม่มีระยะห่างปลายทางจริง/ระยะเบี่ยง) ในผลค้นหาและในข้อความช่วยเหลือ

### โลโก้ [P0]
- [ ] ผ่านตรวจภาพบนอุปกรณ์/emulator ตามรายการ AC ของ US-27 ก่อนปล่อย; ข้อความทางเลือกของโลโก้ตามข้อกำหนดการเข้าถึง

### กฎหมาย/PDPA (release gate เพิ่มเติม รอบ 5)
- [ ] ฝ่ายกฎหมายทบทวน: การเก็บรูปโปรไฟล์ (รูปรถเลื่อนพร้อม US-25), ข้อความรีวิวและผลของการลบบัญชีต่อรีวิว, การส่งพิกัดให้แอปแผนที่ภายนอก, ก่อนเปิดใช้จริง

## Edge Cases (รอบ 5)

### การจับคู่ car (ระยะรับส่งของคนขับ)
- Regression จริง: ปลายทางห่างกัน 2,461 ม. -> ไม่จับคู่เมื่อระยะรับส่งของ Driver = 2,000 ม. และจับคู่เมื่อ = 3,000 ม. (หมวดคำอธิบายเมื่อไม่พบผลของกรณีแรกคือ `far_destination`)
- พยายามเปลี่ยนระยะรับส่งขณะมีคำขอค้างหรือการจับคู่ตอบรับ: ถูกปฏิเสธที่ server (ปุ่ม/ตัวเลือกใน UI ปิดพร้อมเหตุผล) ค่าเดิมคงอยู่; ผลของกฎก่อนหน้าไม่ถูกย้อนหลัง
- ลดระยะรับส่งจาก 3,000 เป็น 2,000 หลังการจับคู่สิ้นสุด/คำขอถูกปฏิเสธ: มีผลกับผลค้นหาและคำขอถัดไปเท่านั้น
- Driver ยกเลิกคำขอค้างแล้วแก้ระยะ: แก้ได้หลังคำขอนั้นไม่ค้างแล้ว
- ทริป Driver ที่ไม่มีค่า `max_dropoff_m` (ทริปเก่า/ค่าว่าง): ใช้ค่า 2,000 ม. ทุกจุดที่ตรวจ ไม่ปฏิเสธและไม่ปล่อยไม่จำกัด; การ์ดแสดง "2.0 กม." ตามค่าที่ใช้จริง
- Driver ตั้งระยะ 500 ม. (ต่ำสุด): จับคู่ได้เฉพาะ Rider ที่ปลายทางห่างจากปลายทาง Driver ≤ 500 ม.; การ์ดแสดง "500 เมตร"; ผลค้นหาอาจว่างบ่อย -> คำอธิบาย `far_destination` เมื่อมี Rider ที่ปลายทางไกลเกิน
- Driver ตั้งระยะ 5,000 ม. (สูงสุด): ยังต้องผ่านจุดเริ่ม ≤ 2,000 ม., overlap ≥ 40%, เวลา 30 นาที; เพดานไม่ได้หมายถึงจับคู่ทุกปลายทาง
- ค่าที่ส่งมานอกช่วง (499, 5,100, 2,050, ข้อความ, null ตอนสร้างทริปใหม่): ค่าไม่ถูกต้องถูกปฏิเสธ; ไม่ระบุค่าตอนสร้างได้ 2,000
- Config เพดาน `match.car_dest_radius_max_m` ลดลงต่ำกว่าค่าของทริปเดิม: ใช้ค่าที่น้อยกว่าตอนตรวจ; ไม่แก้ข้อมูลย้อนหลัง
- Rider ปลายทางอยู่ในระยะของ Driver A แต่เกินระยะของ Driver B: เห็นเฉพาะ A; Driver A เห็น Rider นั้นด้วย (สมมาตร); Driver B ไม่เห็น
- ปลายทางของ Rider ใกล้ปลายทาง Driver มาก แต่ overlap < 40% หรือจุดเริ่มห่าง > 2,000 ม.: ไม่ผ่าน (เงื่อนไขอื่นยังใช้)
- ค่าเท่ากับ threshold พอดี (ระยะปลายทาง = ระยะรับส่ง, จุดเริ่ม = 2,000 ม., overlap = 40%, ต่างเวลา 30 นาที): ถือว่าผ่าน (เกณฑ์เป็น ≤/≥); เกินเล็กน้อยไม่ผ่าน
- การตอบรับ (accept) ตรวจซ้ำ: ถ้าระหว่างรอ ค่า config เปลี่ยนจนไม่ผ่านแล้ว การตอบรับถูกปฏิเสธที่ server และคำขอไม่ถูกจับคู่ (ข้อความเป็นกลางไม่เปิดเผยตัวเลข)
- Rider หลายคนผ่านกฎของ Driver คนเดียว: ทั้งหมดเห็น Driver ตามคะแนน แต่ตอบรับได้ 1 คน (คงเดิม)
- เส้นทางที่ routing ให้มาไม่สมบูรณ์/ไม่พบ: ทริปไม่บันทึกตาม US-5; ทริปเก่าที่ไม่มีรูปทรงเส้นทางไม่ปรากฏในผลค้นหา car (เพราะคำนวณ overlap ไม่ได้)
- สวิตช์ `match.car_rule` เปลี่ยนเป็น 'corridor' ระหว่างมีคำขอค้าง: คำขอที่ส่งแล้วไม่ถูกประเมินซ้ำจนถึง accept ซึ่งใช้โหมดที่เปิดอยู่ ณ ตอนนั้น (ความเสี่ยงที่ต้องแจ้งผู้ดูแลระบบ: อย่าสลับโหมดขณะมีผู้ใช้จริง)
- ค่า `match.car_rule` ที่ไม่ถูกต้อง: ไม่ทำให้จับคู่พังหรือผ่านทุกคู่; ใช้ 'neighbourhood' หรือปฏิเสธการเริ่มระบบพร้อม log
- คำอธิบายเมื่อไม่พบผลอาจถูกใช้สอบถามซ้ำเพื่อสืบตำแหน่ง/ระยะรับส่งของคนขับ: จำกัดอัตราและให้แค่หมวดเหตุผล (`far_destination` ไม่บอกว่ามีคนขับกี่คนหรือระยะเท่าไร)
- ผู้ใช้เดาปลายทางของ Driver จากการ์ดที่แสดงระยะรับส่ง: ตัวเลขระยะรับส่งไม่เปิดเผยตำแหน่งปลายทาง (ไม่ใช่พิกัด) และ Driver ตั้งเองโดยรับรู้ว่าแสดงต่อ Rider

### รูปโปรไฟล์
- ไม่ให้สิทธิ์กล้อง/คลัง: ใช้ทางอื่น/ตัวอักษรย่อ
- รูปใหญ่มาก/ไม่ใช่รูป/HEIC: แอปแปลงเป็น JPEG ที่ย่อแล้วหรือแจ้งว่าไม่รองรับ ไม่ทำให้แอปล่ม
- ออฟไลน์ระหว่างอัปโหลด/ลบ: แจ้งและให้ลองใหม่ รูปเดิมยังคงอยู่จนสำเร็จ
- รูปที่มีบุคคลอื่น/ไม่เหมาะสม: รายงานได้; ไม่มีการตรวจอัตโนมัติ
- คู่หมดสิทธิ์ดูระหว่างที่แอปยังแคชรูป: ต้องกลับเป็นตัวอักษรย่อ
- ผู้ใช้ลบบัญชีระหว่างที่คู่กำลังดูรูป: รูปหายจากฝั่งคู่เมื่อรีเฟรช
- รูปที่ถูกรายงานแล้วผู้ถูกรายงานอัปโหลดใหม่ทันที: รายงานเดิมผูกกับรูปเดิม รูปใหม่เริ่มใหม่ (นับผู้รายงานต่างกันใหม่จาก 0)
- ผู้ใช้คนเดียวรายงานรูปเดิมซ้ำหลายครั้ง (หรือสร้างหลายบัญชีเพื่อปิดรูปคนอื่น): นับเป็น 1 ต่อผู้ใช้; ความเสี่ยงการรายงานกลั่นแกล้งด้วยหลายบัญชียอมรับใน MVP ผู้ดูแลตัดสินคืนรูปได้

### แผนที่สด/นำทาง
- ตำแหน่งคู่หายชั่วคราว (อุโมงค์/สัญญาณ): แสดง "ตำแหน่งล่าสุดเมื่อ..." ไม่ให้แสดงเหมือนสด
- ตำแหน่งกระโดด/ความแม่นยำต่ำ: ไม่ทำให้ไอคอนวาร์ป (ปรับแบบสมูท) แต่ไม่คาดเดาเกินตำแหน่งล่าสุด
- Rider กด "ขึ้นรถแล้ว": ไอคอน Rider หายจากฝั่ง Driver ทันที; Driver ยังเห็นตนเองบนแผนที่
- Driver กด "ถึงแล้ว" ก่อน Rider: ไอคอนรถหายจากฝั่ง Rider ตามกติกาการจับคู่สิ้นสุด/ทริปจบ
- ไม่มีจุดรับที่ตกลงแล้ว: ปุ่มนำทางไปจุดรับปิดพร้อมเหตุผล
- ยังไม่ได้ตกลงจุดลง: Driver ไม่มีเป้าหมายนำทางจุดลง ต้องตกลงผ่านแชท (ข้อความตอบกลับด่วน) หรือรอ Rider เสนอจุดลงสาธารณะ (P1)
- ไม่มีแอปแผนที่ในเครื่อง: เปิดเว็บแผนที่แทน; ผู้ใช้ปฏิเสธการเปิดแอปภายนอก: ไม่มีผลต่อทริป
- routing ล่ม/ถูกจำกัด: ETA ไม่แสดงหรือแสดงค่าประมาณ ไม่ค้าง
- ผู้ใช้เลื่อนแผนที่ขณะโหมดติดตาม: หยุดติดตามและแสดงปุ่มกลับ (ไม่ดึงกลับเอง)
- อุปกรณ์เปิดโหมดลดการเคลื่อนไหว: ลดแอนิเมชันการเคลื่อนไหวของไอคอน (ยังอัปเดตตำแหน่งตามจริง)
- เบี่ยงเส้นทางจนต้องคำนวณใหม่ซ้ำ ๆ: จำกัดความถี่ตาม rate limit

### รีวิว
- Rider ไม่ได้ขึ้นรถ/no-show/ยกเลิกการจับคู่: ไม่มีรีวิวทั้งสองฝ่าย
- ฝ่ายหนึ่งไม่ส่งรีวิว: อีกฝ่ายรอครบ 7 วัน จึงเปิดเผย; ไม่ส่งจะไม่บังคับ
- ผู้ใช้ปรับคะแนนโดยรู้ว่าอีกฝ่ายให้อย่างไร: กันด้วย blind และไม่ให้แก้หลังส่ง
- คู่ที่บล็อกกันแล้ว: ยังให้รีวิวได้ตามสิทธิ์เดิมของการจับคู่ (ตัดสินโดย PM ถ้าต้องการปิด)
- ผู้ที่มีรีวิวที่เปิดเผย 1-2 รายการ: ซ่อนองค์ประกอบคะแนนทั้งหมด ไม่มีข้อความแทน (ป้องกันการระบุตัวและการตัดสินจากตัวอย่างน้อย)
- รีวิวถูกรายงานขณะเป็นตัวชี้ขาดของค่าเฉลี่ยขั้นต่ำ: องค์ประกอบคะแนนอาจถูกซ่อนกลับ (เหลือ < 3)
- ผู้ถูกรีวิวลบบัญชีก่อนเปิดเผย: ลบรีวิวที่เกี่ยวข้อง
- บัญชีสองบัญชีสมคบกันปั่นคะแนน: ยอมรับเป็นข้อจำกัด MVP บันทึกในความเสี่ยง

### โลโก้
- ไอคอนถูกมาสก์เป็นวงกลม/ตัดมุมโดยตัวเครื่อง: ต้องไม่เห็นขอบขาว/มุมซ้อน
- ภาพต้นฉบับมีขอบขาว: ต้องได้ไฟล์เต็มพื้นที่หรือคำตัดสินการตัดขอบ (ประเด็นเปิด 3)

## Out of Scope (รอบ 5)
- US-25 ทั้งหมด (รูปรถ, ตรวจใบขับขี่/ทะเบียนด้วยเอกสาร, สถานะการตรวจ) เลื่อนออกจากรอบ 5 (deferred)
- UI สำหรับสวิตช์ `match.car_rule` และการแสดงกฎ corridor/ระยะเบี่ยง (`approx_detour_m`) ให้ผู้ใช้; โหมด 'corridor' เป็นเพียงทางเลือกที่ backend ปิดเป็นค่าเริ่มต้นสำหรับการทดลองอนาคต
- บริการรับส่งแบบตามเส้นทาง (route-based ride service) เช่น ตรวจว่า Rider ลงตามทางของ Driver, ระยะเบี่ยง, จุดแวะหลายจุด; ระยะรับส่งสูงสุดที่กำหนดโดย Rider หรือกำหนดต่อคู่; ระยะรับส่งที่เกิน 5,000 ม. หรือไม่ใช่ขั้น 100 ม.
- นำทางด้วยเสียง; การนำทางเต็มรูปแบบในแอปเทียบเท่า Google/Apple Maps (รอบ 5 มีแค่เส้นทาง + deep link + รายการเลี้ยว P1)
- ตรวจเนื้อหารูปโดย AI/จดจำใบหน้า; หน้าผู้ดูแล (moderation ผ่านฐานข้อมูลโดยตรง)
- รวบรวมสำเนาเล่มทะเบียนรถ/บัตรประชาชน/เอกสารอ่อนไหวอื่นใน MVP; การตรวจใบขับขี่จริงใน MVP (P1 ภายหลัง)
- ผลลัพธ์ของรีวิวที่มีผลทางเงิน ลงโทษอัตโนมัติ หรือปรับผลค้นหา; ป้ายเชื่อถือ (PR-8)
- ทิปตอบแทน/เงินขอบคุณ (ตัดออกอย่างชัดเจน); ทุกข้อในตาราง PR-1..PR-11 (P2 ยังไม่ผูกมัด)
- การแชร์จุดลง/ปลายทางจริงของ Rider ให้ Driver (ไม่ทำ); จับคู่ Driver หลายจุดแวะ (คงเดิม) (หมายเหตุ: การเสนอ "จุดลงสาธารณะ" โดย Rider เป็น P1 ใน US-24 ไม่อยู่ในข้อนี้)
- ไอคอนแอปที่เปลี่ยนตามบทบาท; การปรับแบรนด์อื่นนอกจากโลโก้ที่ให้มา

## ลำดับพึ่งพา (Dependencies รวม)
- US-21 -> รูปทรงเส้นทางที่เก็บไว้ของทั้งสองทริป (มีแล้ว) + คอลัมน์ `trips.max_dropoff_m` และตัวเลือกระยะรับส่งในฟอร์มทริป Driver (US-5) ก่อนงานอื่นของรอบนี้เพราะเป็นบั๊ก P0
- US-22 -> bucket ส่วนตัว + นโยบายสิทธิ์; ใช้ร่วมกับช่องทางรายงานที่ใช้ร่วมกับ US-26 (US-25 รูปรถเลื่อนออกจากรอบนี้)
- US-23/US-24 -> Realtime/โควตา + routing สาธารณะ (ข้อจำกัด rate limit) + จุดรับที่ตกลงแล้ว (US-18) + แชทเดิม (ข้อความตอบกลับด่วน)
- US-26 -> สถานะ boarded/"ถึงแล้ว" (US-12) และการ์ดโปรไฟล์
- US-27 -> ต้นฉบับโลโก้เต็มพื้นที่ / คำตัดสินฝ่ายออกแบบ
- ทุกข้อที่เก็บข้อมูลส่วนบุคคลใหม่ (รูป, รีวิว) -> การทบทวนกฎหมาย/นโยบายความเป็นส่วนตัวก่อนเปิดใช้จริง

## ประเด็นเปิดที่ต้องการคำตัดสิน
1. (ปิดแล้ว) จุดลงของ Rider: ไม่แชร์จุดลง/ปลายทางจริงให้ Driver; Rider เสนอจุดลงสาธารณะ (P1) + ข้อความตอบกลับด่วน (P0) ตาม US-24 — เหลือให้ PM ยืนยันรายการข้อความสำเร็จรูปสุดท้าย
2. (ปิดแล้ว) ค่ารวมคะแนนแสดงบนการ์ดทุกจุดรวม nearby เมื่อ ≥ 3 รีวิว ไม่งั้นซ่อน
3. ต้นฉบับโลโก้แบบเต็มพื้นที่ (ไม่มีขอบขาว/มุมมนฝัง) หรือให้ฝ่ายออกแบบตัดขอบ
4. ความถี่ตำแหน่งสดที่หน้าจอแผนที่เปิดอยู่ (คงเดิม 15 วินาที หรือเร็วขึ้นสูงสุด 5 วินาที)
