- ถ้าข้อความขัดกับร่างของผู้ใช้ ให้ถือเอกสารนี้เป็นหลักตามตาราง "ส่วนที่ปรับจากร่าง" ท้ายเอกสาร (ทุกจุดที่ปรับมาจากคำตัดสินของ orchestrator เพื่อไม่ให้ซ้ำของที่มีอยู่แล้ว)
- ไม่มีการออกแบบ UI ไม่มีโค้ด ไม่เลือกเทคโนโลยี (ชื่อ service/ตาราง เช่น FCM, OSRM `nearest`, `device_tokens`, `storage_purge_queue`, `PresetController` ใช้เป็นชื่ออ้างอิงจากร่างผู้ใช้/สถาปัตยกรรมที่มีอยู่แล้วเท่านั้น)
- ระดับความสำคัญ: P0 = ต้องมีก่อนปล่อย/ด้านความปลอดภัย, P1 = ควรมีในรอบนี้, P2 = ทำถ้ามีเวลา

## บริบท
รอบ 7 สานต่อ "กลับด้วยกันมั้ย" ให้ใช้งานได้จริงแม้ปิดแอป (push แจ้งเตือน), นัดจุดรับแม่นยำขึ้นด้วยการ snap หมุดเข้าถนน, เพิ่มความเป็นมนุษย์ (vibe/mood) และตัวกรองเฉพาะกลุ่มเพื่อความอุ่นใจ (women-only), โหมดมืดสำหรับขับตอนกลางคืน, การ์ดสรุปผลกระทบเชิงบวกหลังจบทริปพร้อม haptics, การสื่อสารแบบ hands-free ด้วยเสียงสำหรับคนขับ, กลไกจัดการความล่าช้าที่ไม่ลงโทษฝ่ายใดฝ่ายหนึ่งเกินจำเป็น, และการรองรับการจับคู่แบบยอมรับระยะเบี่ยงเพิ่มบนเส้นทางผ่าน (ใช้ได้กับปลายทางคนนั่งทุกที่ ไม่จำกัดเฉพาะสถานีขนส่งสาธารณะ) โดยไม่ลดระดับความปลอดภัย/ความเป็นส่วนตัวที่มีอยู่ (US-9, US-10, US-15, US-18, US-21..24, US-26, US-38 เรื่อง PDPA)

## สิ่งที่มีอยู่แล้ว (baseline ที่ต้องไม่ทำซ้ำ/ไม่ถดถอย) — สำคัญมากสำหรับรอบนี้
- **การนัดจุดรับมีอยู่แล้ว**: RPC `propose_meeting_point` / `confirm_meeting_point` (ตั้งแต่รอบ 3-5), หน้า `PickupScreen` มีตัวเลือกจุดบนแผนที่ (point-picker) และคำเตือน off-route แบบนุ่มนวล (soft warning) อยู่แล้ว ขอบเขตใหม่จริงของ US-43 คือ **การ snap หมุดเข้าถนนที่ปลอดภัยที่สุด** เท่านั้น ส่วนการเสนอ/ยืนยัน/นำทาง **ใช้ flow เดิมทั้งหมด ไม่ออกแบบใหม่**
- **การยืนยันอีเมลสถาบัน/องค์กรมีอยู่แล้วและเป็นอัตโนมัติ**: ตาราง `org_domains` + `verifications` ซิงก์เองเมื่อผู้ใช้ยืนยันอีเมล (ไม่ต้องกรอกรหัส OTP 6 หลักตามร่าง) — **อัปเดต:** สวิตช์ค้นหา "หาเฉพาะเพื่อนในสถาบันเดียวกัน" ที่เคยวางแผนไว้เป็นขอบเขตฝั่งสถาบันของ US-45 ในฉบับก่อนหน้า **ถูกตัดออกทั้งหมดตามการตัดสินใจของผู้ใช้** (เหตุผล: ไม่สำคัญเท่าที่คิด และใช้ได้เฉพาะผู้ใช้กลุ่มที่มี org verification เท่านั้น ไม่ global/ไม่ scale เท่า women-only ซึ่งเป็นความต้องการที่เกี่ยวข้องกับผู้ใช้ทุกคนเป็นสากลกว่า) — US-45 รอบนี้เหลือเฉพาะตัวกรอง **women-only** เท่านั้น (ดู Changelog)
- **Remote push ยังไม่มี**: `LocalNotifier` ปัจจุบันเป็น no-op/debug log เท่านั้น (`docs/dev-notes.md` บรรทัด "ไม่มี remote push") — US-42 คือของใหม่จริงทั้งหมด
- OSRM ใช้อยู่แล้วสำหรับ routing/preview (`osrm_routing.dart`, endpoint สลับได้ผ่าน `--dart-define` เช่น `OSRM_BASE_URL_FOOT/CAR`) — การ snap หมุด (US-43) และการคำนวณระยะเบี่ยงเส้นทางผ่าน (US-50) ควรใช้รูปแบบ config เดียวกัน (endpoint สลับได้, fail-closed คือ fallback กลับไปใช้จุดดิบเมื่อ service ล้มเหลว/ถูก rate-limit)
- `SwipeToConfirmSlider` มี hook รองรับ reduce-motion อยู่แล้ว (`disableAnimations`) — US-47 ต้องต่อยอด ไม่สร้างระบบใหม่
- ระบบโทนสี rider/driver (tone token) และ config tile ของแผนที่ (`TILE_URL` สลับได้) มีอยู่แล้ว — US-46 ต้องต่อยอดเป็น token ชุดที่สอง ไม่สร้างระบบธีมที่สาม
- แชท quick-reply แบบข้อความสำเร็จรูป (ไม่ส่งอัตโนมัติ, ไม่แนบพิกัด) มีรูปแบบอยู่แล้ว (US-8/US-24/US-33) — US-47 "สติกเกอร์ขอบคุณ" และ US-48 sub-feature (B) "วลีสำเร็จรูปพูดด้วยเสียง" ใช้รูปแบบ allow-list เดียวกัน
- flow การลบบัญชี (US-15) มีอยู่แล้วและต้องถูกขยายเพื่อรวมการลบ `device_tokens` (US-42)
- **Storage cleanup มีรูปแบบอยู่แล้ว (ค้างรอบ 5)**: `storage_purge_queue`/Edge Function ที่ตั้งใจใช้ลบไฟล์ storage อัตโนมัติ (service_role key + cron secret, ต้องขออนุมัติ deploy) — US-48 sub-feature (A) "บันทึกเสียงสั้น" ต้อง**ใช้ซ้ำ pattern เดียวกันนี้** ไม่สร้างกลไก cleanup ใหม่ (ขยายให้ drain หลาย bucket หรือรับ bucket param เป็นการตัดสินใจของ /db-architect)
- **Preset สถานที่โปรด (Home/Office) มีอยู่แล้ว (US-38 รอบ 6)**: เก็บแบบ **device-local secure storage ผูก user id เท่านั้น** ล้างเมื่อออกจากระบบ/ลบบัญชี ไม่ซิงก์ server — **US-50 (ฉบับปรับทิศทางใหม่) ไม่แตะ `PresetController`/preset นี้เลย**: ปลายทางของคนนั่งเลือกผ่าน flow ค้นหา/ปักหมุดปลายทางที่มีอยู่แล้วตามปกติในการสร้างทริป ไม่มี UI ใหม่/หมวดใหม่สำหรับ "เลือกสถานี" ใด ๆ ทั้งสิ้น (คนละเรื่องกับ Home/Office เดิมโดยสิ้นเชิง)
- `trips.max_dropoff_m` มีอยู่แล้ว (รอบ 5, ระยะรับ-ส่งเบี่ยงทั่วไปจากปลายทางคนขับ) — US-50 เพิ่ม**คอลัมน์ใหม่แยกต่างหาก**สำหรับระยะทางเบี่ยงเพิ่มที่ยอมรับได้บนเส้นทางไป-กลับ (route detour tolerance) ใช้ได้กับปลายทางของคนนั่งที่ไหนก็ได้ ไม่จำกัดเฉพาะสถานีขนส่งสาธารณะ ไม่ใช่ค่าเดียวกับ `max_dropoff_m` ไม่แก้ความหมายของ `max_dropoff_m` เดิม

## สมมติฐานและคำตัดสิน (รอบ 7)
คำตัดสินของ orchestrator บันทึกเป็นสมมติฐาน ทุกข้อมีเครื่องหมาย "สมมติฐาน:" — PM ยืนยันแล้วทุกข้อ (Q1-Q10 ปิดแล้ว ดูสรุปรายข้อในหัวข้อ "คำถามเปิดสำหรับ PM" ท้ายเอกสาร) เช่นเดียวกับรอบ 6

1. สมมติฐาน: US-43 แคบกว่าร่างผู้ใช้โดยตั้งใจ — ไม่ใช่การสร้างระบบเลือกจุดนัดรับใหม่ (มีอยู่แล้ว) แต่คือการเพิ่มขั้นตอน "snap หมุดที่ผู้ใช้ลากเข้ากับถนนที่ใกล้ที่สุด" ผ่านบริการ OSRM `nearest` (endpoint สลับได้แบบ config เดียวกับ OSRM ที่มีอยู่); ถ้าบริการล้มเหลว/timeout/โดน rate-limit ให้ fallback ใช้จุดดิบที่ผู้ใช้ลากไว้ (fail-open ต่อผู้ใช้ แต่ fail-closed ต่อการยอมรับพิกัดที่ไม่ปลอดภัย เช่น กลางแม่น้ำ/ทางด่วน — ต้องมีการตรวจสอบระยะห่างจากผลลัพธ์ nearest ไม่ให้เบี่ยงเกินเกณฑ์ที่กำหนด)
2. ~~สมมติฐาน (เดิม): US-45 ฝั่งสถาบันไม่มีการเพิ่ม OTP/ขั้นตอนยืนยันใหม่ (มีอยู่แล้วและอัตโนมัติผ่าน `org_domains`/`verifications`) มีเฉพาะสวิตช์ค้นหาใหม่ที่จับคู่บน `org_suffix` ที่ยืนยันแล้วของทั้งสองฝ่าย — ถ้าฝ่ายใดฝ่ายหนึ่งไม่มี org verification สวิตช์นี้ทำให้ไม่ match กันในสระนั้น (ไม่ error ไม่ปิดการค้นหาแบบอื่น)~~ — **ตกไปแล้ว (moot):** สวิตช์ค้นหา "หาเฉพาะเพื่อนในสถาบันเดียวกัน" ถูกตัดออกจาก US-45 ทั้งหมดตามการตัดสินใจของผู้ใช้ (ไม่สำคัญเท่าที่คิด, ไม่ global/ไม่ scale เท่า women-only) — ดู Changelog; US-45 เหลือเฉพาะ women-only
3. สมมติฐาน: US-45 ฝั่ง women-only เป็นของใหม่จริง ต้องเพิ่มฟิลด์เพศที่ผู้ใช้ระบุเอง (self-declared, nullable, optional) ใน `profiles` เป็นข้อมูล "ตาตัวเองเห็นเท่านั้น" + ใช้เพื่อการจับคู่เท่านั้น ไม่แสดงบนการ์ด/โปรไฟล์ต่อสาธารณะ (แสดงได้แค่สถานะสวิตช์ส่วนตัวของตนเอง); ถือเป็นข้อมูลอ่อนไหวเชิง PDPA ต้องลบได้ และไม่รวมอยู่ใน partner-visible profile data
4. สมมติฐาน: US-42 ส่ง payload แบบ data-only (opaque: `kind` + `trip_id`/`match_id` เท่านั้น ไม่มีแม้ข้อความไทยมาตรฐานทั่วไป) ข้อความไทยทั้งหมด render ฝั่ง client จาก string table เดิม (`strings_trip.dart`/`strings_roles.dart`) เพื่อให้มีแหล่งความจริงเดียว (single source of truth) — ต่างจากร่างผู้ใช้ที่ระบุว่า payload มีข้อความไทยมาตรฐานอยู่ในนั้น
5. สมมติฐาน: `device_tokens (user_id, token, platform, updated_at)` ถูกลบเมื่อ sign-out **และ** เมื่อลบบัญชี (ขยาย flow ลบบัญชีเดิมของ US-15)
6. สมมติฐาน: การส่ง push ใช้ pattern `push_outbox` (ตาราง outbox + DB trigger insert แถวเมื่อ: สร้างคำขอจับคู่, จับคู่ตอบรับ, มีข้อความแชทใหม่, event คนขับถึงจุดรับ (US-33 เดิม), จับคู่/ทริปถูกยกเลิก) แล้ว drain โดย scheduled Edge Function รูปแบบเดียวกับ `purge-storage-queue` ที่มีอยู่แล้ว (service_role key + cron secret) เรียก FCM HTTP v1; **การ deploy ฟังก์ชันนี้ต้องได้รับความเห็นชอบจากผู้ใช้ก่อนเสมอ** (เช่นเดียวกับ purge-storage-queue ที่ค้างรอบ 5)
7. สมมติฐาน: รอบนี้ทำ Android + Web ผ่าน FCM เท่านั้น; iOS ผ่าน APNs เป็น **P1 เลื่อนออกจากรอบนี้** (สมมติฐาน: ต้องมี Apple Developer Program enrollment ที่ผู้ใช้อาจยังไม่มี)
8. สมมติฐาน: การสร้าง schema/Dart client ของ US-42 (ตาราง `device_tokens`/`push_outbox`, การขอสิทธิ์แจ้งเตือน, deep-link routing, การแสดงผล foreground ผ่าน `LocalNotifier`-style plumbing เดิม) **ไม่ต้องรอ** ของผู้ใช้ แต่การทดสอบ **ส่งจริงถึงอุปกรณ์แบบ end-to-end** ต้องใช้ Firebase project ของผู้ใช้เอง (service account JSON + `google-services.json`/firebase config) — บันทึกเป็น dependency ไม่ใช่ blocker ต่อการสร้าง
9. สมมติฐาน (PM ยืนยันแล้ว, Q6): US-44 แท็ก vibe เป็น allow-list เท่านั้น (server-validate ห้าม free text); ข้อความ mood ≤ 35 ตัวอักษร มี **guard ราคาถูกทั้ง client และ server**: ปฏิเสธข้อความที่มีเลขติดกัน ≥8 หลัก (รูปแบบคล้ายเบอร์โทร) หรือชนกับ blocklist คำหยาบชุดเล็ก — ไม่ใช่ full moderation ความเสี่ยงที่เหลือ (เนื้อหาไม่เหมาะสมรูปแบบอื่นที่ไม่ใช่เบอร์โทร/คำหยาบในลิสต์) ยอมรับและบันทึกเป็นความเสี่ยงต่อ (ดู Edge case); mood และ tag ผูกกับ "ทริป" ไม่ใช่ "โปรไฟล์" (PM ยืนยันแล้ว, Q5) เพื่อไม่ให้ค้างข้ามทริป/รั่วไปทริปอื่น เคลียร์อัตโนมัติเมื่อจบทริปหรือผ่าน 24 ชม. (อันไหนถึงก่อน)
10. สมมติฐาน: US-46 ใช้ระบบ tone token เดิม เพิ่มชุด `rider-dark`/`driver-dark` เท่านั้น ไม่สร้างระบบธีมที่สาม; tile แผนที่โหมดมืดสลับผ่าน config เดียวกับ `TILE_URL` เดิม (CartoDB Dark Matter `https://a.basemaps.cartocdn.com/dark_all/{z}/{x}/{y}.png` ตามร่างล่าสุดของผู้ใช้); หมุดผ่านเกณฑ์ contrast WCAG AA ด้วยกลไก glow/drop-shadow ที่ระบุชัดในร่างล่าสุด (ไม่ใช่แค่เปลี่ยนสีหมุด); route casing กว้าง 1.5–2dp สีสว่างล้อมเส้นทางบนแผนที่มืด; โหมดเลือกมี 4 ทาง (System/Light/Dark/Auto-by-time 18:00–06:00) ตามร่างล่าสุด — **แทนที่สมมติฐานเดิมที่มีแค่ system/manual 2 ทาง**
11. สมมติฐาน: US-47 สติกเกอร์ขอบคุณเป็นข้อความสำเร็จรูปเท่านั้น (ใช้รูปแบบ quick-reply แชทเดิม) ไม่มีข้อความอิสระ; haptics เคารพการตั้งค่า reduce-motion/haptics ของ OS ต่อยอดจาก hook ที่มีใน `SwipeToConfirmSlider`
12. สมมติฐาน: สูตร CO₂ ตามร่าง (~120 g/km ต่อระยะทางที่เดินทางร่วมกัน) เป็นค่าประมาณเพื่อสร้างความรู้สึกดี ไม่ใช่ตัวเลขที่อ้างอิงทางวิทยาศาสตร์/กฎหมาย ต้องมีป้าย "โดยประมาณ" กำกับ (สอดคล้องกับแนวทาง ETA/ระยะที่มีป้าย "โดยประมาณ" ของรอบก่อน)
13. สมมติฐาน: ทั้ง 9 story ของรอบนี้ไม่มีการแก้ RLS ของตารางเดิม ยกเว้นตารางใหม่ที่ต้องสร้าง (`device_tokens`, `push_outbox`, ฟิลด์เพศใน `profiles`, ฟิลด์ vibe/mood ต่อทริป, private audio bucket ของ US-48, คอลัมน์ระยะเบี่ยงเพิ่ม (route detour tolerance) ของ US-50 — **ไม่มีตารางสถานีอ้างอิงใด ๆ อีกต่อไป**) ซึ่งทั้งหมดต้องผ่าน **/db-architect** ตามข้อกำหนดของผู้ใช้สำหรับงาน schema/migration ใด ๆ
14. สมมติฐาน (US-48): มี**สองกลไกแยกกันโดยสิ้นเชิง** อย่าปนกันในการทดสอบ/สื่อสาร — **(A) บันทึกเสียงสั้น** เป็นไฟล์เสียงจริงเก็บใน private bucket ลบอัตโนมัติใน 24 ชม. ผ่าน pattern `storage_purge_queue` เดิม (ไม่สร้างกลไก cleanup ใหม่ — การขยายให้ drain หลาย bucket หรือรับ bucket param เป็นการตัดสินใจของ /db-architect) กับ **(B) วลีสำเร็จรูปพูดด้วยเสียง** ซึ่ง**ไม่ใช่ไฟล์เสียงเลย** เป็นข้อความ preset (allow-list เดียวกับ quick-reply เดิม) ที่ถูกอ่านออกเสียงด้วย on-device TTS **ฝั่งอุปกรณ์ผู้รับเท่านั้น** ไม่มีการสังเคราะห์เสียงฝั่งเซิร์ฟเวอร์และไม่มีไฟล์เสียงเกี่ยวข้อง
15. สมมติฐาน (US-48): ไฟล์เสียงที่บันทึกไม่ถูกนำไปแปลงเป็นข้อความ (speech-to-text) หรือวิเคราะห์เนื้อหาใด ๆ — ใช้เพื่อเปิดฟัง (playback) เท่านั้น ต้องมี privacy note แจ้งผู้ใช้ก่อนใช้งานครั้งแรก
16. สมมติฐาน (US-49): "ETA ไม่ดีขึ้น" ยังไม่มีนิยามที่เป็นตัวเลขชัดเจนในร่างผู้ใช้ — สมมติฐานชั่วคราว: เทียบค่า ETA ล่าสุดกับค่าก่อนหน้าในรอบ poll เดิมของ live tracking ต่อเนื่องหลายครั้ง (เช่น 3 ครั้งติดที่ไม่ลดลงเลย) ถือว่า "ไม่ดีขึ้น"; **ต้องยืนยันจำนวนครั้ง/หน้าต่างเวลาที่แน่นอนกับ PM ก่อน implement จริง** (คำถามเปิด — ยังไม่ปิด)
17. สมมติฐาน (US-49): ระบบยังไม่มีฟีเจอร์ "อัตราการยกเลิก" จริง — ข้อกำหนดว่าการยกเลิกแบบ no-fault ต้องไม่ถูกนับรวมเป็นข้อกำหนดเชิงป้องกันล่วงหน้า; **ยังไม่ปิดว่าการยกเลิกแบบ no-fault สร้าง reviewable `match_outcome`/แถวที่กระทบระบบรีวิวเหมือนการยกเลิกปกติหรือไม่** — ธงเป็นคำถามเปิดสำหรับ /db-architect ตรวจสอบ schema จริงก่อนพัฒนา
18. สมมติฐาน (US-50, **แทนที่สมมติฐานเดิมข้อ 18-19 ของฉบับก่อนหน้าทั้งหมด** — ดูคำตัดสินสุดท้ายของ orchestrator ท้าย `docs/tasks-round7.md`): **ยกเลิกแนวคิดรายชื่อสถานีอ้างอิง (transit_hubs) ทั้งหมด** เพราะใช้ได้แค่กรุงเทพฯ ไม่ครอบคลุมต่างจังหวัด และซ้ำซ้อนกับ flow ค้นหา/ปักหมุดปลายทางที่มีอยู่แล้ว — กฎจับคู่ใหม่นี้ใช้ได้กับปลายทางของคนนั่ง**ทุกที่** ไม่จำกัดเฉพาะสถานีขนส่งสาธารณะ ไม่จำกัดพื้นที่ทางภูมิศาสตร์ (ทั่วประเทศ ทุกที่ที่ OSRM มีข้อมูลถนน); งานหาพิกัดสถานีที่ทำค้างไว้ก่อนหน้าถูกยกเลิกทั้งหมด (ไม่เสียหาย ไม่ได้ใช้)
19. สมมติฐาน (US-50): กฎจับคู่ใหม่นี้เป็น**ทางเลือกที่สอง**คู่ขนานกับกฎ "ปลายทางใกล้กัน" (`max_dropoff_m`, รัศมีจากปลายทางคนขับ) ที่มีอยู่แล้ว — ทั้งสองกฎ **"หรือกัน"** (match ได้ถ้าผ่านกฎใดกฎหนึ่ง ไม่ต้องผ่านทั้งคู่ ไม่ใช่ AND); ไม่ต้องมีสวิตช์ยินยอมเพิ่มเติมแยกต่างหาก เพราะตัวเลขระยะเบี่ยงที่คนขับตั้งเองถือเป็นการยินยอมอยู่แล้ว (พฤติกรรมเดียวกับ `max_dropoff_m` เดิม)
20. สมมติฐาน (US-50): เมื่อ OSRM ล้มเหลว/timeout ขณะคำนวณ route delta ของกฎนี้ ต้อง **fail-closed เฉพาะ predicate นี้เท่านั้น** คือแค่ไม่ให้ match ผ่านทางกฎระยะเบี่ยงเพิ่ม (ไม่เดา/ไม่ fail-open) แต่**ไม่กระทบ**เงื่อนไข `max_dropoff_m` เดิมที่เป็นอิสระต่อกัน — ทริปยังจับคู่ผ่านเงื่อนไขนั้นได้ตามปกติ

## User Stories

### US-42: การแจ้งเตือนพุชระยะไกล (Remote Push Notifications) [P0]
As a ผู้ใช้ (ทั้งคนขับและคนนั่ง), I want ได้รับการแจ้งเตือนบนมือถือเมื่อมีเพื่อนชวนเดินทางหรือตอบรับคำชวน แม้จะปิดหรือพักแอปอยู่, so that ไม่พลาดการนัดหมายและตอบกลับได้ทันท่วงที

**Acceptance Criteria:**
- [ ] ขอสิทธิ์แจ้งเตือนเมื่อเข้าสู่ระบบครั้งแรกหรือเมื่อสร้างทริปแรก พร้อมคำอธิบายภาษาไทยที่ชัดเจนว่าทำไมต้องขอ; ปฏิเสธสิทธิ์แล้วยังใช้แอปได้ปกติ (ไม่ block)
- [ ] บันทึก device token ลงตาราง `device_tokens (user_id, token, platform, updated_at)` (schema ใหม่ ผ่าน /db-architect); token ซ้ำ (เปลี่ยนเครื่อง/reinstall) อัปเดตแทนการสร้างซ้ำ
- [ ] เมื่อผู้ใช้ sign-out **หรือ** ลบบัญชี token ของอุปกรณ์นั้นถูกลบออกจากฐานข้อมูลทันที (ขยาย flow ลบบัญชีเดิมของ US-15 ให้ครอบคลุม `device_tokens`)
- [ ] payload ที่ส่งผ่าน FCM/APNs เป็น **data-only และ opaque เท่านั้น**: มีแค่ `kind` (ประเภทเหตุการณ์) และ `trip_id`/`match_id` **ไม่มีชื่อ-นามสกุล, เบอร์โทร, ทะเบียนรถ, พิกัด, ข้อความแชทจริง และไม่มีแม้ข้อความไทยมาตรฐานทั่วไป** — ข้อความที่ผู้ใช้เห็นถูก render ฝั่ง client จาก string table เดิม (`strings_trip.dart`/`strings_roles.dart`) เพียงแหล่งเดียว (ต่างจากร่างผู้ใช้ที่ระบุข้อความอยู่ใน payload — ดูตาราง "ส่วนที่ปรับจากร่าง")
- [ ] เหตุการณ์ที่ทริกเกอร์การส่ง (ผ่าน `push_outbox`): มีคำขอจับคู่ใหม่, จับคู่ตอบรับแล้ว, มีข้อความแชทใหม่, คนขับถึงจุดรับ (เหตุการณ์เดิมของ US-33 รอบ 6), จับคู่/ทริปถูกยกเลิก
- [ ] การส่งจริงทำผ่าน scheduled Edge Function (รูปแบบเดียวกับ `purge-storage-queue`: service_role key + cron secret) drain จาก `push_outbox`; **ต้องได้รับอนุมัติจากผู้ใช้ก่อน deploy เสมอ**
- [ ] แตะการแจ้งเตือนแล้วแอปเปิดไปยังหน้าที่เกี่ยวข้องทันที (deep link ใช้เส้นทางเดิมของรอบ 6 เช่น `/matches/:id/live`); ถ้า session หลุดให้กลับไปหน้าเข้าสู่ระบบอย่างปลอดภัยโดยไม่เสียปลายทางที่ต้องการไป (นำทางต่อได้หลัง login)
- [ ] รอบนี้ส่งผ่าน FCM สำหรับ Android + Web เท่านั้น; iOS/APNs เลื่อนเป็น P1 (บันทึกเหตุผลใน out-of-scope)
- [ ] การสร้าง schema/Dart client (ลงทะเบียน token, ขอสิทธิ์, deep-link routing, แสดงผล foreground) ไม่ต้องรอของผู้ใช้; การทดสอบส่งจริงถึงอุปกรณ์ต้องใช้ Firebase project ของผู้ใช้เอง (service account JSON + `google-services.json`/firebase config) — เป็น dependency ที่บันทึกไว้ ไม่ block การพัฒนา
- [ ] ทดสอบได้โดยไม่มี Firebase จริง: มี mode/stub สำหรับ CI ที่ตรวจ payload/opaque ids และ flow deep-link โดยไม่ต้องยิงถึง FCM จริง

**Dependencies:** /db-architect (schema `device_tokens`, `push_outbox`), US-15 (ลบบัญชี), US-33 (เหตุการณ์คนขับถึงจุดรับ), การอนุมัติ deploy Edge Function จากผู้ใช้, Firebase project ของผู้ใช้ (เฉพาะทดสอบ end-to-end)

### US-43: การ Snap หมุดจุดนัดรับเข้าถนนที่ปลอดภัย (Road-Snapped Pickup Pin) [P0]

**หมายเหตุขอบเขต (ต่างจากร่างผู้ใช้โดยตั้งใจ):** ระบบเลือก/เสนอ/ยืนยันจุดนัดรับบนแผนที่ (`propose_meeting_point`/`confirm_meeting_point`, `PickupScreen`, คำเตือน off-route) **มีอยู่แล้วตั้งแต่รอบ 3-5** ขอบเขตจริงของ story นี้คือการเพิ่มขั้นตอน **snap หมุดเข้ากับถนนที่ใกล้และปลอดภัยที่สุด** เท่านั้น ไม่ออกแบบหรือสร้าง flow ใหม่

As a คนขับหรือคนนั่งที่จับคู่กันแล้ว, I want เมื่อฉันลากหมุดไปยังจุดที่สะดวก ระบบช่วยขยับหมุดให้แนบถนนที่ปลอดภัยให้อัตโนมัติ, so that จุดนัดรับที่ตกลงกันแม่นยำและปลอดภัยขึ้นโดยไม่ต้องพิมพ์อธิบายเพิ่ม

**Acceptance Criteria:**
- [ ] เมื่อผู้ใช้กด **"เสนอจุดนี้" เพียงครั้งเดียว** (ไม่ snap ทุกครั้งที่ปล่อยหมุดระหว่างลาก, PM ยืนยันแล้ว Q4) ระบบเรียกบริการ OSRM `nearest` (endpoint สลับได้ผ่าน config แบบเดียวกับ `OSRM_BASE_URL_CAR`/`_FOOT` ที่มีอยู่แล้ว) เพื่อหาจุดบนถนนที่ใกล้ที่สุด แล้วขยับหมุดไปยังจุดนั้นก่อนแสดงให้ผู้ใช้ยืนยัน
- [ ] ถ้าผลลัพธ์จาก `nearest` เบี่ยงจากจุดที่ผู้ใช้ปล่อยเกินระยะที่กำหนด (เช่น อยู่ไกลผิดปกติ/อยู่กลางแม่น้ำ/ทางด่วนที่ไม่ควรจอด) ให้ไม่ snap และใช้จุดดิบแทน (ไม่ยอมรับผลลัพธ์ที่ดูไม่ปลอดภัยแบบเงียบ ๆ)
- [ ] ถ้าบริการ `nearest` ล้มเหลว/timeout/โดน rate-limit ให้ fallback ใช้จุดดิบที่ผู้ใช้ลากไว้ทันที ไม่ error ไม่ค้าง (fail-open ต่อผู้ใช้)
- [ ] หลัง snap แล้ว **ใช้ flow เดิมทั้งหมดต่อ ไม่เปลี่ยน**: เสนอจุด (`propose_meeting_point`) → อีกฝ่ายเห็นหมุดพร้อมปุ่ม "ตกลงเจอกันตรงนี้" → ยืนยัน (`confirm_meeting_point`) → `agreed_pickup_point` → ปุ่มนำทางภายนอกเดิม (US-24)
- [ ] คำเตือน off-route แบบนุ่มนวลที่มีอยู่แล้วยังทำงานเหมือนเดิม (ไม่ถูกแทนที่ด้วยการ snap; snap และ off-route warning เป็นคนละกลไก)
- [ ] ไม่มีการแก้ RLS/RPC เดิมของ meeting point; ไม่มีคอลัมน์ใหม่ใน `trips`/`matches` (การ snap เป็น client-side/service-call ก่อนเรียก RPC เดิมเท่านั้น)
- [ ] ผู้ใช้เห็นความแตกต่างชัดเจนว่าหมุดถูกขยับ (เช่น ข้อความสั้น ๆ ว่า "ปรับหมุดให้ตรงถนนแล้ว") และยังลากแก้ตำแหน่งเองได้ต่อหลัง snap ก่อนกดเสนอจริง

**Dependencies:** flow `propose_meeting_point`/`confirm_meeting_point` เดิม (US-24 ของรอบก่อน), OSRM config เดิม

### US-44: แท็กไลฟ์สไตล์และสเตตัสประจำวัน (Commute Vibe Tags & Daily Mood) [P1]
As a ผู้เดินทาง, I want ระบุสไตล์การเดินทางและข้อความสั้น ๆ ประจำวันบนการ์งของฉัน, so that คนที่กำลังหาเพื่อนร่วมทางเข้าใจ vibe และเลือกเดินทางด้วยกันได้อย่างสบายใจ

**Acceptance Criteria:**
- [ ] เลือกแท็กได้สูงสุด 3 แท็ก จาก allow-list ที่กำหนดตายตัวและ **server-validate** (ปฏิเสธค่านอกรายการ ไม่รับ free text): ฝั่ง Driver (`#เปิดแอร์เย็น`, `#เปิดเพลงฟังเพลิน`, `#ขับนิ่มไม่ซิ่ง`, `#ไม่สูบบุหรี่`, `#มีที่เก็บกระเป๋า`), ฝั่ง Rider/ทั่วไป (`#คุยเก่ง`, `#ขอพักสายตาเงียบๆ`, `#ฟังเพลงสากล`, `#สายประหยัด`, `#พร้อมแชร์เรื่องเล่า`)

- [ ] ข้อความ mood ยาวไม่เกิน 35 ตัวอักษร; มี **guard ราคาถูกทั้ง client และ server** (PM ยืนยันแล้ว, Q6): ปฏิเสธข้อความที่มีเลขติดกัน ≥8 หลัก (รูปแบบคล้ายเบอร์โทร) หรือชนกับ blocklist คำหยาบชุดเล็ก; ไม่ใช่ full moderation — ความเสี่ยงที่เหลือ (เนื้อหาไม่เหมาะสมรูปแบบอื่นที่ไม่ใช่เบอร์โทร/คำหยาบในลิสต์) ยอมรับและบันทึกเป็นความเสี่ยงต่อ (ดู Edge case)
- [ ] แท็กและ mood ผูกกับ "ทริป" ไม่ใช่ "โปรไฟล์" (PM ยืนยันแล้ว, Q5) เพื่อไม่ให้ค้างข้ามทริป/รั่วไปทริปอื่นของผู้ใช้เดียวกัน
- [ ] เคลียร์อัตโนมัติเมื่อจบทริป **หรือ** ผ่านไป 24 ชั่วโมง แล้วแต่ว่าอะไรถึงก่อน; ผู้ใช้ล้างเองก่อนหมดเวลาได้ด้วย
- [ ] ทริปที่ไม่มีแท็ก/mood แสดงการ์ดปกติโดยไม่มีช่องว่างที่ดูเป็นข้อบกพร่อง (สอดคล้องรูปแบบ layout เดิมของ US-34/US-36)
- [ ] การเปลี่ยน schema (คอลัมน์ vibe tags/mood ต่อทริป) ทำผ่าน /db-architect เท่านั้น

**Dependencies:** `profiles`/`trips` schema ใหม่ (/db-architect), CommuteCardDeck (US-34)

### US-45: ตัวกรองความปลอดภัย: เดินทางเฉพาะผู้หญิง (Women-Only) [P1]

**หมายเหตุขอบเขต (อัปเดต — ตัดตัวกรองสถาบันออกทั้งหมด):** ฉบับก่อนหน้าของ US-45 มีสวิตช์ค้นหา "หาเฉพาะเพื่อนในสถาบันเดียวกัน" คู่กับ women-only — **สวิตช์สถาบันถูกตัดออกทั้งหมดตามการตัดสินใจของผู้ใช้** (เหตุผล: ไม่สำคัญเท่าที่คิด และใช้ได้เฉพาะผู้ใช้กลุ่มที่มี org verification เท่านั้น ไม่ scale/ไม่ global เท่า women-only ซึ่งเป็นความต้องการที่เกี่ยวข้องกับผู้ใช้ทุกคนเป็นสากลกว่า) US-45 ฉบับนี้เหลือเฉพาะตัวกรอง **women-only** เท่านั้น — คอลัมน์ `trips.same_org_only` ที่ apply ขึ้น live แล้ว (migration 0012) **ถูกปล่อยทิ้งไว้เฉย ๆ ในสคีมาโดยตั้งใจ** (dead/unused column) ไม่มี Dart/UI ใด ๆ อ่านหรือเขียนค่านี้อีกต่อไป เพื่อเลี่ยง migration แบบทำลายข้อมูล (destructive) ที่ไม่จำเป็น (ดู Changelog และ Out of Scope)

As a ผู้ใช้ที่ต้องการความปลอดภัยเป็นพิเศษ, I want เลือกเดินทางเฉพาะผู้หญิงด้วยกัน, so that รู้สึกอุ่นใจและมั่นใจในความปลอดภัยสูงสุด

**Acceptance Criteria:**
- [ ] **สวิตช์ Women-Only** (ของใหม่): เปิดใช้ได้เฉพาะผู้ใช้ที่ระบุเพศตนเองเป็นหญิง (ฟิลด์ใหม่ nullable/optional ใน `profiles`) และกดยินยอมเปิดเผยข้อมูลนี้เพื่อการจับคู่เท่านั้น
- [ ] จับคู่เมื่อ **ทั้งสองฝ่าย** เปิดสวิตช์นี้ **และ** ระบุเพศเป็นหญิงทั้งคู่เท่านั้น; ถ้าฝ่ายใดฝ่ายหนึ่งยังไม่ได้ระบุเพศ (unset) ระบบกรองฝ่ายนั้นออกจากสระนี้เงียบ ๆ (ไม่ error ไม่แจ้งเตือนที่เปิดเผยว่าอีกฝ่ายเป็นเพศอะไร)
- [ ] ฟิลด์เพศเป็นข้อมูล **ตาตัวเองเห็นเท่านั้น**: ไม่แสดงบนการ์ด/โปรไฟล์สาธารณะ ไม่ส่งให้อีกฝ่ายเห็นค่าที่ระบุ (แสดงได้แค่สถานะ "เปิด/ปิด" ของสวิตช์ตนเอง); ไม่รวมอยู่ใน partner-visible profile data ใด ๆ (เช่น การ์ด deck, Match Moment, UnifiedRideScreen)
- [ ] ผู้ใช้ลบ/ล้างค่าฟิลด์เพศได้เองทุกเมื่อ (สอดคล้อง PDPA — ข้อมูลอ่อนไหว); การลบทำให้สวิตช์ women-only ปิดอัตโนมัติ; **และถ้ามีคำขอ/จับคู่ women-only ที่ pending อยู่ ณ ตอนลบ ต้อง auto-cancel คำขอ/จับคู่นั้นทันที พร้อมข้อความสุภาพแจ้งทั้งสองฝ่าย (ไม่เปิดเผยเหตุผลเจาะจงเรื่องเพศของอีกฝ่าย เช่น ใช้ถ้อยคำกลาง ๆ ว่า "เงื่อนไขการจับคู่พิเศษไม่ครบแล้ว" ไม่ใช่ "อีกฝ่ายไม่ใช่ผู้หญิงแล้ว")** (PM ยืนยันแล้ว, Q7)
- [ ] การเปลี่ยน `find_matches`/schema ที่เกี่ยวข้อง (คอลัมน์เพศ) ทำผ่าน /db-architect เท่านั้น; ห้ามคืนค่าที่ระบุเพศจริงของอีกฝ่ายผ่าน API ใด ๆ (ทดสอบเรียก API ตรง); สวิตช์ต้องเช็คสถานะเพศแบบ **สด (live)** ทุกครั้งที่ `find_matches` ค้นหา ไม่ cache ค่าที่ตั้งไว้ตอนเปิดสวิตช์ (PM ยืนยันแล้ว, Q8 — เดิมครอบคลุมทั้งสถาบัน+เพศ ตอนนี้เหลือเฉพาะเพศ เพราะสวิตช์สถาบันถูกตัดออกแล้ว)
- [ ] คอลัมน์ `trips.same_org_only` (migration 0012 ที่ apply ขึ้น live แล้ว) ต้อง**ไม่ถูกอ่าน/เขียนโดย Dart client หรือ UI ใด ๆ ทั้งสิ้น** ในรอบนี้ (dead column โดยตั้งใจ ไม่ลบเพื่อเลี่ยง destructive migration)

**Dependencies:** `profiles` schema ใหม่สำหรับเพศ (/db-architect), `find_matches` (ขยายเพิ่มเงื่อนไข ผ่าน /db-architect เช่นเดียวกับ US-36 รอบ 6)

### US-46: โหมดมืดและแผนที่มืดสมบูรณ์แบบ (Dark Mode & Night Map Tiles) [P1]

**หมายเหตุขอบเขต (อัปเดต — ฉบับนี้แทนที่ AC ชุดเดิมของ US-46 ในเอกสาร BA ฉบับก่อนหน้าทั้งหมด):** ร่างผู้ใช้ล่าสุดของ `requirements-round7.md` เพิ่มรายละเอียดเฉพาะเจาะจงกว่าเดิม (URL tile, ความกว้าง route casing, marker glow, สี่โหมดสวิตช์ + auto-by-time) — ทีมยังคงต่อยอดระบบ tone token/tile config เดิมเช่นเดิม ไม่สร้างระบบธีมที่สาม

As a คนขับที่วางมือถือหน้ารถตอนกลางคืน, I want ให้ทั้งตัวแอปพลิเคชันและแผนที่เปลี่ยนเป็นโทนสีเข้ม (Dark Mode & Dark Map Tiles), so that แสงสว่างสีขาวไม่สะท้อนกระจกหน้ารถ และไม่แยงตาระหว่างขับขี่

**Acceptance Criteria:**
- [ ] **การเลือกโหมด (4 ทาง):** หน้าตั้งค่ามีตัวเลือก `[ ตามระบบ (System) / สว่างตลอด (Light) / มืดตลอด (Dark) / มืดอัตโนมัติตามเวลา (18:00–06:00) ]`; manual override (Light/Dark ตายตัวที่ผู้ใช้เลือกเอง) มีลำดับความสำคัญเหนือ system และเหนือ auto-by-time เสมอ
- [ ] **โหมดมืดอัตโนมัติตามเวลา:** เปิด dark theme/tile อัตโนมัติในช่วง **18:00–06:00 ตามเวลาเครื่อง (local time)** และปิดอัตโนมัตินอกช่วงนี้ ไม่ต้องพึ่งตำแหน่ง GPS/คำนวณเวลาพระอาทิตย์ตก; ไม่ขัดแย้งกับ system dark mode ของ OS (auto-by-time ใช้เวลาอย่างเดียว ไม่สนใจค่า system setting)
- [ ] เพิ่ม tone token ชุดใหม่ 2 ชุด (`rider-dark`, `driver-dark`) ต่อยอดระบบ tone token เดิม (ไม่สร้างระบบธีมที่สาม, ไม่กระทบ token เดิมของโหมดสว่าง)
- [ ] แผนที่สลับ `TileLayer`/`urlTemplate` ไปใช้ **CartoDB Dark Matter**: `https://a.basemaps.cartocdn.com/dark_all/{z}/{x}/{y}.png` ผ่าน config สลับได้แบบเดียวกับ `TILE_URL` ที่มีอยู่แล้ว; กลับสู่ Light Mode สลับกลับไปใช้ OpenStreetMap มาตรฐานเดิม
- [ ] **Route Casing:** เส้นทาง Polyline ของคนขับ (สีส้มทอง) และคนนั่ง (สีฟ้า) บนแผนที่มืด ต้องมีเส้นขอบสีสว่าง (White/Light Casing) **กว้าง 1.5–2 dp** ล้อมรอบเส้นทาง เพื่อไม่ให้จมหายไปกับพื้นถนนสีดำ
- [ ] **Marker Glow/Shadow:** หมุดตำแหน่งรถ/คนเดิน/จุดนัดรับ มีเงาสะท้อน (subtle glow/drop shadow) รอบหมุด เพื่อให้อ่านง่ายและผ่านเกณฑ์ **WCAG AA** บนพื้นหลัง tile มืด (กลไกที่ระบุชัดคือ glow/shadow ไม่ใช่แค่เปลี่ยนสีหมุด)
- [ ] สลับโหมดระหว่างทริปกำลังดำเนินอยู่ (UnifiedRideScreen) ไม่รีเซ็ตสถานะทริป/แชท/ตำแหน่ง sheet (สอดคล้อง US-29 รอบ 6); ไม่รีโหลด/กระตุกทั้งหน้าจอ
- [ ] ทดสอบ contrast ของสี geofence เขียว (US-32 รอบ 6) และ badge/ปุ่มสำคัญในโหมดมืดผ่านเกณฑ์เดิม
- [ ] อุปกรณ์ที่ไม่รองรับ system dark mode API เก่า ยัง fallback เป็น manual toggle (Light/Dark/Auto-by-time) ได้ตามปกติ

**Dependencies:** tone token system เดิม, tile config เดิม, US-29/US-32 (รอบ 6)

### US-47: สรุปผลกระทบเชิงบวกและสัมผัสสั่น (Shared Impact & Haptics) [P2]
As a ผู้ร่วมเดินทางที่ถึงบ้านปลอดภัยแล้ว, I want เห็นข้อมูลว่าการเดินทางร่วมกันครั้งนี้ช่วยโลกอย่างไร พร้อมส่งคำขอบคุณให้เพื่อน, so that รู้สึกดีและมีกำลังใจในการใช้บริการเป็นประจำ

**Acceptance Criteria:**
- [ ] การ์ดสรุปแสดงหลังสไลด์ถึงที่หมายสำเร็จ (ต่อจาก label ถึงที่หมาย 2 แบบของ US-31/US-40 รอบ 6): ข้อความประมาณ "คุณและ [ชื่อเล่นเพื่อน] ร่วมกันลดก๊าซคาร์บอนไดออกไซด์ไป ~X kg CO₂ ในการเดินทางครั้งนี้!" พร้อมป้าย "โดยประมาณ" **และ footnote/disclaimer หนึ่งบรรทัด** (เช่น "ตัวเลขนี้เป็นค่าประมาณเพื่อสร้างแรงบันดาลใจ ไม่ใช่ค่าที่รับรองทางวิทยาศาสตร์") (PM ยืนยันแล้ว, Q9 — ไม่ต้องขอฝ่ายกฎหมายทบทวนเพิ่มรอบนี้)
- [ ] สูตรคำนวณ: ระยะทางที่เดินทางร่วมกัน × ~120 g/km (ค่าประมาณเพื่อสร้างความรู้สึกดี ไม่ใช่ตัวเลขอ้างอิงทางวิทยาศาสตร์/กฎหมาย)
- [ ] ปุ่มส่ง "สติกเกอร์ขอบคุณ" เป็นข้อความสำเร็จรูปเท่านั้น (ใช้รูปแบบ quick-reply แชทเดิมของ US-8/US-24) ไม่มีช่องพิมพ์อิสระ เช่น "ขอบคุณมากนะ!", "ขับปลอดภัยครับ", "เพลงเพราะมาก"
- [ ] Haptic feedback: สั่นเบา (selection) เมื่อลากการ์ด deck, สั่นยืนยัน (heavy impact) เมื่อ `SwipeToConfirmSlider` สำเร็จที่ 95% — ต่อยอด hook reduce-motion ที่มีอยู่แล้วใน slider ไม่สร้างระบบใหม่
- [ ] Haptics เคารพการตั้งค่า reduce-motion/haptics ของ OS: ปิดเมื่อผู้ใช้ตั้งค่าลดการเคลื่อนไหว/สั่นไว้ ไม่มีทางบังคับสั่นแทน
- [ ] การ์ดสรุปและปุ่มสติกเกอร์ไม่แสดงข้อมูลเกินสิทธิ์เดิม (ไม่มีพิกัด/ปลายทางจริงของอีกฝ่าย); ทริปที่ไม่มีคู่ตอบรับ (เดี่ยว/Peer) ไม่แสดงส่วนที่เกี่ยวกับเพื่อน

**Dependencies:** US-31/US-40 (รอบ 6, label ถึงที่หมาย), แชท quick-reply เดิม (US-8/US-24), `SwipeToConfirmSlider` reduce-motion hook เดิม

### US-48: บันทึกเสียงสั้นแบบ Hands-Free และวลีสำเร็จรูปพูดด้วยเสียง (Hands-Free Audio Notes & Quick-Voice Presets) [P1]

**หมายเหตุขอบเขต — มี 2 กลไกแยกกันโดยสิ้นเชิง อย่าปนกันทั้งใน AC/การทดสอบ/การสื่อสาร:**
- **(A) บันทึกเสียงสั้น (Recorded Voice Clip):** ไฟล์เสียงจริงที่บันทึกจากไมโครโฟน ส่งเป็นไฟล์ เก็บใน private storage bucket ลบอัตโนมัติภายใน 24 ชม.
- **(B) วลีสำเร็จรูปพูดด้วยเสียง (Preset Quick-Voice / On-Device TTS):** **ไม่ใช่ไฟล์เสียง** เป็นข้อความสำเร็จรูป (allow-list เดียวกับแนวทาง quick-reply เดิม) ที่ถูกอ่านออกเสียงด้วย text-to-speech **บนอุปกรณ์ของฝ่ายรับเท่านั้น** ไม่ผ่านการสังเคราะห์เสียงฝั่งเซิร์ฟเวอร์ ไม่มีไฟล์เสียงเกี่ยวข้องเลย

As a คนขับที่ต้องขับรถและมือไม่ว่างพิมพ์, I want ส่งข้อความเสียงสั้นหรือกดวลีสำเร็จรูปให้อีกฝ่ายได้ยินโดยไม่ต้องละสายตาจากถนน, so that สื่อสารกับผู้โดยสารได้อย่างปลอดภัยระหว่างขับรถ

**Acceptance Criteria:**

_(A) บันทึกเสียงสั้น:_
- [ ] ปุ่มกดค้างเพื่อบันทึก (hold-to-record) ขนาดใหญ่ **≥56dp** วางในตำแหน่งที่แตะได้โดยไม่ต้องมองจอหลังวางมือถือในตำแหน่งใช้งาน (สอดคล้องแนว hands-free ปุ่มใหญ่ของ `SwipeToConfirmSlider` เดิม); ปล่อยนิ้วหรือครบ 10 วินาที = หยุดบันทึกอัตโนมัติ (จำกัดความยาวสูงสุด **≤10 วินาที**)
- [ ] คำอธิบายขอสิทธิ์ไมโครโฟนภาษาไทยชัดเจนก่อนใช้งานครั้งแรก (เหตุผลการใช้ + ปฏิเสธแล้วยังใช้แอปได้ปกติ ไม่ block ฟีเจอร์อื่น)
- [ ] ไฟล์เสียงเก็บใน **private storage bucket** (signed URL ชั่วคราว รูปแบบเดียวกับ avatar bucket เดิมของรอบ 5) ผูกกับคู่จับคู่/ทริปนั้นเท่านั้น อีกฝ่ายเปิดฟังได้ (playback only)
- [ ] ลบไฟล์เสียงอัตโนมัติภายใน **24 ชั่วโมง** หลังบันทึก โดย **ใช้ pattern `storage_purge_queue`/Edge Function เดิมที่มีอยู่แล้ว** (ค้างรอบ 5/6) **ไม่สร้างกลไก cleanup ใหม่** (จะขยาย Edge Function เดิมให้ drain หลาย bucket หรือรับ bucket param เพิ่ม เป็นการตัดสินใจของ **/db-architect**)
- [ ] ไฟล์เสียง **ไม่ถูกนำไปแปลงเป็นข้อความ (speech-to-text) หรือวิเคราะห์เนื้อหาใด ๆ ทั้งสิ้น** — ใช้เพื่อ "เปิดฟัง" อย่างเดียว; ต้องมีข้อความ privacy note แจ้งผู้ใช้ทั้งสองฝ่ายให้ทราบข้อนี้ก่อนใช้งานครั้งแรก
- [ ] ไม่มีช่องพิมพ์/เล่นซ้ำไม่จำกัด — เล่นได้ตามปกติของไฟล์แนบแชทเดิม (ไม่ต่างจากรูปแนบ/ไฟล์แนบที่มีอยู่)

_(B) วลีสำเร็จรูปพูดด้วยเสียง (แยกจาก (A) โดยสิ้นเชิง):_
- [ ] รายการวลีสำเร็จรูปแบบ allow-list ตายตัว (เช่น "ถึงจุดนัดรับแล้ว", "ขอโทษที่มาช้านิดนึง", "รอสักครู่นะ", "เดี๋ยวถึงแล้ว") ใช้รูปแบบ allow-list เดียวกับ quick-reply แชทเดิม (US-8/US-24/US-47) — **ไม่มีข้อความอิสระ**
- [ ] เมื่อกดวลี ข้อความถูกส่งผ่านช่องแชท/แจ้งเตือนเดิม (เหมือน quick-reply ปกติ) **และ** เมื่ออีกฝ่ายได้รับ ข้อความจะถูกอ่านออกเสียงอัตโนมัติด้วย **on-device text-to-speech (TTS) ของอุปกรณ์ฝ่ายรับเอง** (ไม่ใช่ไฟล์เสียงที่ส่งมา ไม่ใช่ TTS ฝั่งเซิร์ฟเวอร์)
- [ ] ฝ่ายรับปิดการอ่านออกเสียงอัตโนมัติได้ในหน้าตั้งค่า (fallback แสดงเป็นข้อความ/แจ้งเตือนปกติเมื่อปิด)
- [ ] ไม่มีการบันทึก/แนบไฟล์เสียงใด ๆ เกี่ยวข้องกับกลไกนี้เลย (ต้องมีการทดสอบแยกจาก (A) อย่างชัดเจนเพื่อยืนยันว่าไม่มีการปนกัน)

**Dependencies:** private storage bucket ใหม่ (/db-architect), `storage_purge_queue`/Edge Function เดิม (รอบ 5/6, ขยาย ไม่สร้างใหม่ — ต้องขออนุมัติ deploy เช่นเดียวกับ US-42), allow-list quick-reply เดิม (US-8/US-24/US-47), push/local-notification เดิม (US-42) สำหรับแจ้งมีข้อความ/เสียงใหม่, on-device TTS (ความสามารถของแพลตฟอร์ม ไม่ใช่ service ใหม่)

### US-49: ตรวจจับความล่าช้าและยกเลิกแบบไม่เสียประวัติ (Lateness Detection & No-Fault Cancellation) [P1]
As a คนขับหรือคนนั่งที่กำลังรอเพื่อนร่วมทางแต่ล่าช้ากว่าที่ควร, I want ให้ระบบแจ้งเตือนเมื่อการเดินทางล่าช้าผิดปกติ และมีทางเลือกยกเลิกได้โดยไม่กระทบประวัติของฝั่งใดฝั่งหนึ่ง, so that ไม่ต้องรอเก้อโดยไม่รู้สถานะ และไม่ถูกลงโทษเมื่อความล่าช้าไม่ใช่ความผิดของฝ่ายใดฝ่ายหนึ่งชัดเจน

**Acceptance Criteria:**
- [ ] ระบบตรวจจับความล่าช้าโดยเงื่อนไขใดเงื่อนไขหนึ่ง: **เกินเวลานัด/ETA เดิมมากกว่า 10 นาที** หรือ **ETA ไม่ดีขึ้นเลย** ต่อเนื่องหลายครั้ง (สมมติฐาน: เทียบค่า ETA ล่าสุดกับค่าก่อนหน้าในรอบ poll เดิมที่มีอยู่แล้วของ live tracking; **ต้องยืนยันจำนวนครั้ง/นิยาม "ไม่ดีขึ้น" ที่แน่นอนกับ PM ก่อน implement** — ดูคำถามเปิด)
- [ ] เมื่อเข้าเงื่อนไข แสดงการ์ดสองตัวเลือกบน**ทั้งสองฝั่ง**พร้อมกัน: **"รอต่ออีก 10 นาที"** และ **"ยกเลิกการเดินทาง (ไม่เสียประวัติ)"**
- [ ] กด "รอต่ออีก 10 นาที": ปิดการ์ด นับเวลาใหม่ 10 นาที ถ้ายังล่าช้า/ETA ไม่ดีขึ้นอีก แสดงการ์ดเดิมซ้ำได้ (ไม่จำกัดจำนวนรอบ แต่ไม่รบกวนถี่เกินไปในระหว่างนับเวลา)
- [ ] กด "ยกเลิกการเดินทาง (ไม่เสียประวัติ)" จากฝั่งใดฝั่งหนึ่ง: ยกเลิกจับคู่/ทริปทันที โดย**ทำเครื่องหมายเป็นการยกเลิกแบบไม่มีความผิด (no-fault)** แยกจากการยกเลิกทั่วไป
- [ ] การยกเลิกแบบ no-fault **ต้องไม่ถูกนับรวม**ในสถิติ/ฟีเจอร์ "อัตราการยกเลิก" ใด ๆ ในอนาคต (ยังไม่มีฟีเจอร์นี้ในระบบตอนนี้ — เป็นข้อกำหนดเชิงป้องกันล่วงหน้า); **ต้องตรวจสอบกับ /db-architect ว่าการยกเลิกแบบนี้สร้าง reviewable `match_outcome`/แถวที่กระทบระบบรีวิวเหมือนการยกเลิกปกติหรือไม่** ถ้าใช่ต้องมีฟิลด์แยก (เช่น `cancel_reason`/`is_no_fault`) เพื่อกันไม่ให้ระบบรีวิว/สถิติในอนาคตปนกัน (คำถามเปิดสำหรับ /db-architect — ธงไว้ ยังไม่ปิด)
- [ ] อีกฝ่าย (ฝ่ายที่ไม่ได้กดยกเลิก) ได้รับการแจ้งเตือนแบบสุภาพว่าการเดินทางถูกยกเลิก (ใช้ push/local-notification channel เดิมของ US-42 **ไม่สร้างช่องทางใหม่**); ข้อความไม่กล่าวโทษฝ่ายใดฝ่ายหนึ่ง (เช่น "การเดินทางถูกยกเลิกเนื่องจากล่าช้ากว่าที่คาดไว้มาก" ไม่ใช่ "อีกฝ่ายยกเลิกคุณ")
- [ ] การ์ดสองตัวเลือกและการยกเลิกยังทำงานถูกต้องแม้ฝ่ายใดฝ่ายหนึ่งปิดแอป/ไม่ตอบสนอง (ฝ่ายที่เหลือยังกดยกเลิกได้เองฝ่ายเดียว ไม่ต้องรอ consent จากอีกฝ่าย)
- [ ] ไม่กระทบ SOS/emergency flow เดิม (US-9 ฯลฯ) การตรวจจับความล่าช้าเป็นกลไกแยกต่างหาก ไม่ลดระดับ/แทนที่ SOS

**Dependencies:** ETA/live tracking polling เดิม (รอบ 5/6), push/local-notification เดิม (US-42, ใช้ channel เดิมไม่สร้างใหม่), ระบบยกเลิกจับคู่/ทริปเดิม, ระบบรีวิว/`match_outcome` เดิม (ต้องตรวจสอบร่วมกับ /db-architect — คำถามเปิด)

### US-50: เส้นทางผ่าน — จับคู่แบบยอมรับระยะเบี่ยงเพิ่ม (Route Detour Tolerance) [P1]

**หมายเหตุขอบเขต — ปรับทิศทางใหม่ทั้งหมด (แทนที่การออกแบบก่อนหน้าโดยสิ้นเชิง):** ใช้คำตัดสินสุดท้ายของ orchestrator ทั้งหมด (หลังคุยกับผู้ใช้เพิ่มเติม ดู `docs/tasks-round7.md` หัวข้อ "คำตัดสิน (Orchestrator) — US-50 ปรับทิศทางใหม่ (ยกเลิกรายชื่อสถานี, ทำแบบทั่วไป)" ท้ายไฟล์) **ยกเลิกแนวคิด "จุดต่อรถขนส่งสาธารณะ/รายชื่อสถานีอ้างอิง (transit_hubs)" ทั้งหมด** เพราะใช้ได้แค่กรุงเทพฯ ไม่ครอบคลุมต่างจังหวัด และซ้ำซ้อนกับ flow ค้นหา/ปักหมุดปลายทางที่มีอยู่แล้ว — **ไม่มี UI ใหม่สำหรับ "เลือกสถานี" ไม่มีตารางอ้างอิง ไม่มี seed data ใด ๆ ทั้งสิ้น** กลไกนี้ใช้ "ระยะทางเบี่ยงเพิ่มที่ยอมรับได้" กับปลายทางของคนนั่ง**ที่ไหนก็ได้**ทั่วประเทศ ไม่ใช่ corridor ทั่วไป และไม่ใช่การบังคับให้อยู่บนเส้นทางหลักเป๊ะ:

As a คนขับ, I want ตั้งระยะทางเบี่ยงเพิ่มที่ฉันยอมให้รถวิ่งเพิ่มขึ้นจริงบนเส้นทางไป-กลับเพื่อรับ-ส่งคนนั่งที่ปลายทางอยู่นอกเส้นทางตรงของฉันเล็กน้อย, so that จับคู่กับคนนั่งที่ปลายทางไม่ตรงเป๊ะกับปลายทางของฉันได้สะดวกขึ้น โดยควบคุมระยะเบี่ยงที่ยอมรับได้ด้วยตัวเอง

**Acceptance Criteria:**
- [ ] คนขับตั้งค่า **สไลเดอร์ระยะทางเบี่ยงเพิ่มที่ยอมรับได้ต่อทริป** ช่วง **200–2,000 เมตร** ขยับทีละ 100 ม. ค่าเริ่มต้น **500 ม.**; เพดานสูงสุดกำหนดโดย **ค่า config ของระบบ 2,000 ม.** (ปรับได้จากฝั่งระบบ ไม่ใช่ hardcode ในแอป)
- [ ] ค่านี้เป็น**คอลัมน์ใหม่แยกจาก `trips.max_dropoff_m`** ของรอบ 5 เพราะวัดคนละอย่าง (`max_dropoff_m` = ระยะรับ-ส่งเบี่ยงทั่วไปจากปลายทางคนขับ, คอลัมน์ใหม่นี้ = ระยะทางถนนจริงไป-กลับที่ยอมให้เพิ่มขึ้นเมื่อ "เบี่ยงเส้นทาง" ไปแวะปลายทางของคนนั่งก่อนไปถึงปลายทางของคนขับ) — ต้องผ่าน **/db-architect**
- [ ] กลไกนี้**ใช้ได้กับปลายทางของคนนั่งที่ไหนก็ได้** เลือกผ่าน flow ค้นหา/ปักหมุดปลายทางที่มีอยู่แล้วตามปกติในการสร้างทริป (flow เดิม ไม่ออกแบบใหม่) — **ไม่มี UI/หมวดพิเศษสำหรับ "เลือกสถานี" ใด ๆ**, ไม่จำกัดเฉพาะสถานีขนส่งสาธารณะ, ไม่จำกัดเฉพาะกรุงเทพฯ/พื้นที่ใดพื้นที่หนึ่ง — ใช้ได้ทั่วประเทศทุกที่ที่ OSRM มีข้อมูลถนน
- [ ] กฎนี้เป็น**ทางเลือกที่สอง** คู่ขนานกับกฎ "ปลายทางใกล้กัน" (`max_dropoff_m`) ที่มีอยู่แล้ว — ทริปของคนนั่งจะจับคู่กับทริปของคนขับได้ถ้า**ผ่านเงื่อนไขใดเงื่อนไขหนึ่ง** ระหว่าง (ก) ปลายทางอยู่ในรัศมี `max_dropoff_m` หรือ (ข) ผ่านเช็คระยะเบี่ยงเพิ่มของ story นี้ (หรือกัน — match ได้ถ้าผ่านกฎใดกฎหนึ่ง ไม่ต้องผ่านทั้งคู่)
- [ ] คำนวณระยะเบี่ยงจาก **ระยะทางถนนจริงผ่าน OSRM** ด้วยสูตร: `route(origin→rider_dest→destination) − route(origin→destination)` (ผลต่างระยะทางถนนจริง ไม่ใช่เส้นตรง/haversine); ถ้าผลต่างเกินค่าที่คนขับตั้งไว้ ระบบไม่จับคู่ผ่านเงื่อนไขนี้ (แต่ยังจับคู่ผ่านเงื่อนไข `max_dropoff_m` ได้ตามปกติถ้าเข้าเกณฑ์นั้นแยกต่างหาก)
- [ ] **ไม่ต้องมีสวิตช์ยินยอมเพิ่มเติมแยกต่างหาก** เพราะตัวเลขระยะเบี่ยงที่คนขับตั้งเองถือเป็นการยินยอมอยู่แล้ว (พฤติกรรมเดียวกับ `max_dropoff_m` เดิม)
- [ ] ค่าระยะเบี่ยงนี้**ถูกล็อกไม่ให้แก้ไขเมื่อทริปมีสถานะ pending หรือ accepted** เช่นเดียวกับการตั้งค่าอื่นของทริปคนขับที่มีอยู่แล้ว — ต้องยกเลิก/สร้างทริปใหม่หากต้องการเปลี่ยนค่าระหว่างมีคำขอ/จับคู่ค้างอยู่
- [ ] การขยาย `find_matches`/RPC ที่เกี่ยวข้องเพื่อรองรับเงื่อนไขนี้ (คำนวณ OSRM delta + เทียบกับค่าที่คนขับตั้ง + OR กับ `max_dropoff_m`) ทำผ่าน **/db-architect** เท่านั้น และต้องคำนวณที่ **backend เท่านั้น** ไม่พึ่ง client คำนวณแล้วส่งผลมาเชื่อ; ต้องวัด performance การเรียก OSRM เพิ่ม (2 เส้นทางต่อการเช็คหนึ่งครั้ง) ไม่ให้ช้าเกินกรอบเดิมของ `find_matches`
- [ ] ถ้า OSRM ล้มเหลว/timeout ขณะคำนวณ route delta: **fail-closed เฉพาะเงื่อนไขนี้เท่านั้น** คือ predicate นี้แค่ไม่ให้ match ผ่านทางนี้ (ไม่เดา/ไม่ยอมรับแบบ fail-open เพราะเป็นตัวเลขที่ใช้ตัดสินใจจับคู่จริง) แต่**ไม่กระทบ/ไม่บล็อก**เงื่อนไข `max_dropoff_m` เดิมซึ่งเป็นอิสระต่อกัน — ทริปยังจับคู่ได้ตามปกติถ้าผ่านเงื่อนไขนั้น

**Dependencies:** OSRM routing เดิม (config เดียวกับ US-43/รอบก่อน), `trips.max_dropoff_m` เดิม (รอบ 5, ไม่แก้ แค่เพิ่มคอลัมน์ใหม่คู่ขนาน), flow ค้นหา/ปักหมุดปลายทางเดิม (ไม่แตะ, ไม่มี UI ใหม่, ไม่แตะ `PresetController`/Home-Office preset เดิม), /db-architect (คอลัมน์ใหม่ + ขยาย `find_matches`)

## แผนการแบ่งระยะการพัฒนา (Implementation Stages, อัปเดตตามร่างล่าสุดของผู้ใช้)

1. **Stage A (P0 Core Realtime & Map Interaction)**: US-42 (Push Notifications) + US-43 (Road-Snapped Pin)
2. **Stage B (P1 Identity, Delight & Communication)**: US-46 (Dark Mode) + US-48 (Hands-Free Audio Notes) + US-44 (Vibe Tags & Mood) + US-45 (ตัวกรองความปลอดภัย: เดินทางเฉพาะผู้หญิง)
3. **Stage C (P1/P2 Journey Safety & Transit)**: US-49 (Lateness & No-Fault Cancel) + US-50 (Route Detour Tolerance) + US-47 (Shared Impact & Haptics)

## NFR

### ความเป็นส่วนตัว / PDPA
- US-42: payload เป็น data-only/opaque เสมอ ไม่มี PII หรือแม้ข้อความไทยมาตรฐานในเนื้อหา push; `device_tokens` ลบเมื่อ sign-out และลบบัญชี
- US-44: mood/vibe ผูกกับทริป (ไม่ใช่โปรไฟล์ถาวร) เคลียร์อัตโนมัติภายใน 24 ชม./จบทริป เพื่อไม่ให้ค้างเป็นข้อมูลระยะยาวโดยไม่จำเป็น
- US-45: ฟิลด์เพศเป็นข้อมูลอ่อนไหวเชิง PDPA เก็บแบบตาตัวเองเห็น ใช้เพื่อจับคู่เท่านั้น ลบได้เองทุกเมื่อ ไม่ปรากฏใน partner-visible data; คอลัมน์ `trips.same_org_only` เป็น dead column ที่ตั้งใจไม่ใช้งาน ไม่มีข้อมูลใหม่เพิ่มเข้าไปอีก
- US-43: การ snap ไม่ส่งข้อมูลเพิ่มเติมนอกเหนือพิกัดที่ผู้ใช้เลือกอยู่แล้วไปยัง OSRM (ไม่มี PII ในคำขอ `nearest`)
- US-48: ไฟล์เสียงบันทึกเป็นข้อมูลอ่อนไหว (เสียงพูดของผู้ใช้) เก็บใน private bucket ผูกเฉพาะคู่จับคู่ ลบอัตโนมัติใน 24 ชม. **ไม่ถูกแปลง/วิเคราะห์เนื้อหาใด ๆ** (playback only); วลีสำเร็จรูปพูดด้วยเสียง (B) ไม่เก็บข้อมูลเสียงใด ๆ เพราะเป็นข้อความ preset ที่พูดสดฝั่งอุปกรณ์ผู้รับเท่านั้น
- US-49: ข้อความแจ้งยกเลิกแบบ no-fault ต้องไม่เปิดเผยเหตุผลส่วนตัว/พิกัดของอีกฝ่ายเกินกว่าที่จำเป็น
- US-50: **ไม่มีตาราง/ข้อมูลอ้างอิงสถานีใด ๆ อีกต่อไป** (ยกเลิกตามคำตัดสินสุดท้ายของ orchestrator) — ค่าระยะเบี่ยงที่คนขับตั้งเป็นเพียงตัวเลข config ต่อทริปเท่านั้น ไม่มี PII เพิ่มเติม; ไม่แตะ/ไม่เกี่ยวข้องกับ storage ส่วนตัวของ preset Home/Office เดิม
- ทุกฟิลด์/ตารางใหม่ผ่าน /db-architect ตามข้อกำหนดของผู้ใช้สำหรับงาน schema/migration

### การเข้าถึง (a11y)
- US-42: การแจ้งเตือนต้องมีข้อความชัดเจนอ่านได้ด้วย screen reader เมื่อแตะ; ไม่พึ่งเสียง/สั่นเป็นทางเดียว
- US-46: contrast ของ tone token มืดและหมุดแผนที่ (route casing 1.5–2dp, marker glow/shadow) ผ่าน WCAG AA; ไม่พึ่งสีอย่างเดียวสำหรับข้อมูลสำคัญ (สอดคล้อง US-32/US-34 รอบ 6)
- US-47: haptics เป็นส่วนเสริมเท่านั้น ไม่ใช่ทางเดียวที่สื่อผลสำเร็จ (มี label/ข้อความคู่กันเสมอ); เคารพ reduce-motion/haptics setting
- US-48: ปุ่มบันทึกเสียง ≥56dp ใหญ่พอสัมผัสได้โดยไม่มองจอ (hands-free safety framing); วลีสำเร็จรูปพูดด้วยเสียงช่วยผู้ใช้ที่ไม่สะดวกมองจอระหว่างขับ แต่ต้องปิดได้ (fallback เป็นข้อความ/แจ้งเตือนภาพเสมอ ไม่บังคับเสียงเป็นทางเดียว)
- US-49: การ์ดสองตัวเลือกต้องอ่านได้ด้วย screen reader และปุ่มมีขนาดแตะง่ายสอดคล้องแนวทาง a11y เดิม
- US-50: สไลเดอร์ตั้งค่าระยะเบี่ยงต้องอ่านค่า/หน่วยได้ชัดเจนด้วย screen reader (ไม่พึ่งการมองเห็นตำแหน่งบนสไลเดอร์อย่างเดียว) สอดคล้องแนวทาง a11y ของการตั้งค่าทริปอื่นที่มีอยู่แล้ว (เช่น `max_dropoff_m`)

### ประสิทธิภาพ
- US-43: การเรียก OSRM `nearest` ต้อง fail-open ไม่ทำให้ flow เสนอจุดรับช้าลงอย่างมีนัยสำคัญ; มี timeout สั้นและ fallback ทันที
- US-42: การ drain `push_outbox` เป็น background job แยกจาก request path ของผู้ใช้ ไม่เพิ่ม latency ให้ RPC เดิม (เช่น `request_match`, ส่งข้อความแชท)
- US-44: การ query แท็ก/mood ไม่ทำให้ `find_matches`/CommuteCardDeck ช้าลงเกินกรอบเดิม (สอดคล้อง NFR ของ US-36 รอบ 6)
- US-50: การเรียก OSRM 2 เส้นทาง (origin→ปลายทางคนนั่ง→ปลายทางคนขับ และ origin→ปลายทางคนขับ) ต่อการเช็คหนึ่งครั้งใน `find_matches` ต้องไม่ทำให้ query ช้าลงเกินกรอบเดิม — ต้องวัด perf จริงก่อนปล่อย; เนื่องจากกฎนี้ใช้ได้กับปลายทางคนนั่ง**ทุกที่** (ไม่จำกัดเฉพาะกรณีตรงสถานีเหมือนเวอร์ชันก่อนหน้า) จึงมีแนวโน้มถูกเรียกใช้บ่อยกว่าที่เคยประเมินไว้เดิม ต้องพิจารณา caching/rate-limit ของการเรียก OSRM เพิ่มถ้าจำเป็น

### ความปลอดภัย / ความถูกต้อง
- US-43: ผลลัพธ์ snap ที่เบี่ยงผิดปกติ (เช่น กลางแม่น้ำ/ทางด่วน) ต้องไม่ถูกยอมรับแบบเงียบ ๆ — มีเกณฑ์ตรวจระยะเบี่ยงก่อนใช้ผลลัพธ์
- US-42: การ deploy Edge Function ต้องขออนุมัติผู้ใช้ก่อนเสมอ (เช่นเดียวกับ `purge-storage-queue`); service_role key/cron secret ไม่ถูก expose ฝั่ง client
- US-45: การกรองต้องบังคับที่ backend (`find_matches`) ไม่ใช่แค่ UI; ห้ามคืนค่าฟิลด์เพศจริงของอีกฝ่ายผ่าน API ใด ๆ
- US-48: signed URL ของไฟล์เสียงมีอายุสั้นเหมือน avatar bucket เดิม; การ deploy/ขยาย Edge Function ของ `storage_purge_queue` ต้องขออนุมัติผู้ใช้ก่อนเสมอ (เหมือน US-42)
- US-49: การ auto-cancel no-fault ต้องบังคับที่ backend ไม่ใช่แค่ UI (กันกรณี client ส่งค่าไม่ตรง)
- US-50: การจับคู่เงื่อนไขระยะเบี่ยงเพิ่มต้องคำนวณที่ backend (`find_matches`) เท่านั้น ไม่พึ่ง client คำนวณแล้วส่งผลมาเชื่อ; เมื่อ OSRM ล้มเหลวต้อง **fail-closed เฉพาะ predicate นี้เท่านั้น** ไม่กระทบ/ไม่บล็อกเงื่อนไข `max_dropoff_m` ที่เป็นอิสระต่อกัน

## Edge cases ที่ควรพิจารณา
- US-42: ผู้ใช้ปิดสิทธิ์แจ้งเตือนหลังเคยเปิดไว้ (ต้องลบ/ไม่ใช้ token เก่าอย่างเงียบ ๆ), sign-out จากหลายอุปกรณ์ (ลบเฉพาะ token ของอุปกรณ์นั้นหรือทั้งหมด — ต้องตัดสินใจ), แตะ push ขณะแอปเปิดอยู่แล้วหน้าอื่น (deep link ไม่ทำให้ state ปัจจุบันหาย), token invalid/expired ที่ FCM ปฏิเสธ (ต้องล้างออกจาก `device_tokens` เมื่อ Edge Function ได้ error เฉพาะ เพื่อไม่ยิงซ้ำไปเรื่อย ๆ), เหตุการณ์เกิดถี่มาก (เช่น พิมพ์แชทรัว ๆ) ไม่ควรทำให้ push ถล่ม (อาจต้อง debounce ระดับ outbox — คำถามเปิดสำหรับ PM)
- US-43: ผู้ใช้อยู่ในพื้นที่ที่ OSRM ไม่มีข้อมูลถนน (ชนบท/ซอยเล็กมาก), เครือข่ายช้าขณะ snap (ต้อง feedback ระหว่างรอ ไม่ค้างจอ), ผู้ใช้ลากหมุดใหม่หลัง snap ไปแล้ว (ต้อง snap ใหม่หรือปล่อยตามที่ลากล่าสุด — คำถามเปิดสำหรับ PM)
- US-44: mood/tag ที่มีเนื้อหาไม่เหมาะสม — มี guard พื้นฐาน (เลขติดกัน ≥8 หลัก/blocklist คำหยาบขนาดเล็ก, PM ยืนยันแล้ว Q6) แต่ไม่ใช่ full moderation เนื้อหาไม่เหมาะสมรูปแบบอื่นยังหลุดได้ ยังต้องมีทางรายงาน/บล็อกอย่างน้อยแบบเดิมที่มีอยู่รองรับ escalate; ทริปที่ยังไม่จบแต่ผ่าน 24 ชม. พอดี (ต้องเคลียร์แม้ทริปยังดำเนินอยู่)
- US-45: ผู้ใช้ลบฟิลด์เพศขณะมีคำขอจับคู่ women-only ที่ pending อยู่ — **PM ตัดสินแล้ว (Q7)**: auto-cancel คำขอ/จับคู่ที่ pending ทันทีพร้อมข้อความสุภาพแจ้งทั้งสองฝ่าย (ไม่เปิดเผยเหตุผลเจาะจงเรื่องเพศ); การจับคู่ women-only ต้องเช็คสถานะเพศแบบสด (live) ทุกครั้งที่ `find_matches` ค้นหา ไม่ cache ค่าที่ตั้งไว้ตอนเปิดสวิตช์ (PM ตัดสินแล้ว, เดิม Q8 ครอบคลุมทั้งสถาบัน+เพศ ตอนนี้เหลือเฉพาะเพศเพราะสวิตช์สถาบันถูกตัดออกแล้ว — ดู Changelog)
- US-46: สลับ manual dark mode ขณะกำลังดูแผนที่ (ต้องไม่รีโหลด/กระตุกทั้งหน้าจอ); อุปกรณ์ที่ไม่รองรับ system dark mode API เก่า (fallback เป็น manual toggle เท่านั้น); เวลาเครื่องผู้ใช้ผิด/ตั้งเขตเวลาแปลก (auto-by-time ใช้เวลาเครื่องตรง ๆ — ความคลาดเคลื่อนยอมรับได้ ไม่ทำ server time sync เพิ่ม)
- US-47: ทริปที่ยกเลิกก่อนถึงที่หมาย (ไม่แสดงการ์ดสรุป); ทริปที่คู่ไม่ตอบรับ/บล็อกกันหลังจบ (ไม่แสดงชื่อเล่น/ปุ่มส่งสติกเกอร์ให้คนที่บล็อกไปแล้ว); ระยะทางที่เดินทางร่วมกัน = 0 หรือคำนวณไม่ได้ (ต้องซ่อนตัวเลข ไม่แสดง 0 kg CO₂ ที่ดูแปลก)
- US-48: ผู้ใช้ปฏิเสธสิทธิ์ไมโครโฟน (sub-feature (A) ใช้ไม่ได้ แต่ (B) ยังใช้ได้ปกติเพราะไม่ต้องใช้ไมค์); เล่นเสียงบันทึกไม่ได้เพราะไฟล์ถูกลบไปแล้ว (ครบ 24 ชม.) ก่อนอีกฝ่ายเปิดฟัง (ต้องแสดงข้อความว่าเสียงหมดอายุแล้ว ไม่ error ดิบ); TTS ของอุปกรณ์ฝ่ายรับไม่รองรับภาษาไทย/เสียงสังเคราะห์คุณภาพต่ำ (fallback แสดงข้อความอย่างเดียว); ผู้ใช้กดวลีรัว ๆ ติดกันหลายอัน (ต้องมีคิว/limit ไม่ให้ TTS พูดทับกันฝั่งผู้รับ — คำถามเปิด)
- US-49: ทั้งสองฝ่ายกด "ยกเลิก" พร้อมกัน (race condition — ต้องมีผลลัพธ์เดียวไม่ error ซ้อน); ฝ่ายหนึ่งกด "รอต่อ" อีกฝ่ายกด "ยกเลิก" พร้อมกัน (ยกเลิกควรชนะเสมอเพื่อความปลอดภัย — คำถามเปิดสำหรับ PM); ETA กลับมาดีขึ้นระหว่างที่การ์ดกำลังแสดงอยู่ (ควรซ่อนการ์ดอัตโนมัติหรือปล่อยให้ผู้ใช้ตัดสินใจเอง — คำถามเปิด); ทริปใกล้ถึงที่หมายมากแล้ว (เกือบ arrived) แต่ดันเข้าเงื่อนไขล่าช้า (ต้องกันไม่ให้การ์ดล่าช้าไปแย่งพื้นที่กับสไลด์ถึงที่หมาย)
- US-50: OSRM ล้มเหลว/timeout ขณะคำนวณ route delta (ต้อง fail-closed คือ predicate นี้แค่ไม่ให้ match ผ่านทางกฎระยะเบี่ยงเพิ่ม ไม่ใช่ fail-open ยอมรับแบบเดา เพราะเป็นตัวเลขที่ใช้ตัดสินใจจับคู่จริง — แต่ไม่บล็อกเงื่อนไข `max_dropoff_m` เดิมที่ยังทำงานได้อิสระ); ปลายทางของคนนั่งอยู่ในพื้นที่ที่ OSRM ไม่มีข้อมูลถนน (ชนบท/ซอยเล็กมาก) ทำให้คำนวณ route delta ไม่ได้ (fail-closed เหมือนกรณี OSRM ล้มเหลว); คนขับพยายามปรับค่าระยะเบี่ยงระหว่างมีคำขอ/จับคู่ pending หรือ accepted อยู่ (ต้องล็อกค่าไว้ ห้ามแก้ไขจนกว่าจะยกเลิก/จบทริป เหมือนการตั้งค่าทริปอื่นของคนขับที่มีอยู่แล้ว); ทั้งสองเงื่อนไข (`max_dropoff_m` และระยะเบี่ยงเพิ่ม) ผ่านพร้อมกัน (ไม่ต้องเลือก ให้ match ได้ตามปกติ เพราะเป็น OR ไม่ใช่ XOR)

## คำถามเปิดสำหรับ PM (ปิดแล้ว — PM ยืนยันแล้วทั้งหมด Q1-Q10; มีคำถามเปิดใหม่ Q11-Q17 สำหรับ US-48/49/50 — Q14/Q15 ตกไปแล้วดูหมายเหตุ; Q8 ตกไปบางส่วนแล้วดูหมายเหตุ)
- Q1: US-42 — sign-out จากอุปกรณ์หนึ่ง ควรลบ token เฉพาะอุปกรณ์นั้น หรือทุกอุปกรณ์ของผู้ใช้? — **PM ยืนยันแล้ว**: ลบเฉพาะอุปกรณ์นั้นเท่านั้น ไม่ลบทุกเครื่อง (token ผูกกับอุปกรณ์อยู่แล้ว sign-out จากเครื่องอื่นไม่ต้องพึ่งการลบ token เพื่อความปลอดภัย ไม่มีความเสี่ยงเพิ่ม)
- Q2: US-42 — ต้อง debounce/รวม push ที่เกิดถี่ (เช่น ข้อความแชทหลายข้อความติดกัน) เป็นการแจ้งเตือนเดียวหรือไม่ และภายในกรอบเวลาเท่าไร? — **PM ยืนยันแล้ว**: coalesce เฉพาะแชทภายในหน้าต่าง 60 วินาทีต่อ match เป็นการแจ้งเตือนเดียว ("มีข้อความใหม่..."); เหตุการณ์อื่น (คำขอจับคู่/ตอบรับ/ถึงจุดรับ/ยกเลิก) ไม่ coalesce ส่งทันที
- Q3: US-42 — ยืนยันการเลื่อน iOS/APNs เป็น P1 เนื่องจากต้องมี Apple Developer Program enrollment ที่ผู้ใช้อาจยังไม่มี — ยืนยันหรือมีทางอื่น? — **PM ยืนยันแล้ว**: เลื่อนเป็น P1 จริง ไม่ block รอบนี้ (Android+Web ผ่าน FCM ก่อน)
- Q4: US-43 — เมื่อผู้ใช้ลากหมุดใหม่หลังถูก snap ไปแล้ว ต้อง snap ซ้ำอัตโนมัติทุกครั้งที่ปล่อย หรือ snap แค่ครั้งสุดท้ายก่อนกดเสนอจริง? — **PM ยืนยันแล้ว**: snap เพียงครั้งเดียวตอนกด "เสนอจุดนี้" เท่านั้น ไม่ snap ทุกครั้งที่ปล่อยหมุดระหว่างลาก
- Q5: US-44 — ยืนยันว่า vibe tags/mood ผูกกับ "ทริป" ไม่ใช่ "โปรไฟล์" ตามสมมติฐาน — ถูกต้องหรือไม่? — **PM ยืนยันแล้ว**: ตามสมมติฐาน BA ถูกต้อง ผูกกับทริป เคลียร์อัตโนมัติเมื่อจบทริป/24 ชม.
- Q6: US-44 — ยอมรับความเสี่ยงที่ไม่มีการกรองคำหยาบ/PII อัตโนมัติในข้อความ mood รอบนี้หรือไม่ หรือให้เลื่อน/เพิ่ม allow-list เข้มงวดกว่านี้? — **PM ยืนยันแล้ว**: เปลี่ยนสมมติฐานเดิม ยังคง mood free text ≤35 ตัวอักษร แต่เพิ่ม guard ราคาถูกทั้ง client/server (ปฏิเสธเลขติดกัน ≥8 หลัก หรือชนกับ blocklist คำหยาบชุดเล็ก) ไม่ใช่ full moderation ความเสี่ยงที่เหลือยอมรับและบันทึกเป็นความเสี่ยงต่อ
- Q7: US-45 — เมื่อผู้ใช้ลบฟิลด์เพศขณะมีคำขอจับคู่ women-only ที่ pending อยู่ ระบบควรยกเลิกคำขอนั้นอัตโนมัติหรือปล่อยให้ดำเนินต่อ? — **PM ยืนยันแล้ว**: auto-cancel คำขอ/จับคู่ที่ pending นั้นทันที พร้อมข้อความสุภาพแจ้งทั้งสองฝ่าย (ไม่เปิดเผยเหตุผลจริงเจาะจงเรื่องเพศของอีกฝ่าย)
- ~~Q8 (เดิม) US-45~~ — org verification หมดอายุ/เปลี่ยนอีเมลระหว่างเปิดสวิตช์สถาบันเดียวกันอยู่ ควรปิดสวิตช์อัตโนมัติทันทีหรือรอจนครั้งค้นหาถัดไป? — **ตกไปแล้วบางส่วน (moot สำหรับส่วนสถาบัน):** สวิตช์ "หาเฉพาะเพื่อนในสถาบันเดียวกัน" ถูกตัดออกจาก US-45 ทั้งหมดตามการตัดสินใจของผู้ใช้ (ดู Changelog) จึงไม่มี org verification ให้พิจารณาอีกต่อไป; **หลักการที่ PM เคยยืนยันไว้ยังคงใช้กับฟิลด์เพศของ women-only ต่อไปตามปกติ**: บังคับที่ `find_matches` (server-side) ให้เช็คสถานะเพศแบบสด (live) ทุกครั้งที่ค้นหา ไม่ cache ผู้ใช้จะหลุดจากสระการค้นหานั้นในครั้งค้นหาถัดไปโดยอัตโนมัติถ้าลบฟิลด์เพศไป ไม่ต้องมี job แยกไปปิดสวิตช์ที่บันทึกไว้
- Q9: US-47 — ยืนยันว่าค่าคงที่ 120 g/km และป้าย "โดยประมาณ" เพียงพอเชิงกฎหมาย/การตลาด หรือควรมี disclaimer เพิ่มเติม? — **PM ยืนยันแล้ว**: ป้าย "(โดยประมาณ)" บวก footnote/disclaimer หนึ่งบรรทัด (เช่น "ตัวเลขนี้เป็นค่าประมาณเพื่อสร้างแรงบันดาลใจ ไม่ใช่ค่าที่รับรองทางวิทยาศาสตร์") เพียงพอแล้ว ไม่ต้องขอฝ่ายกฎหมายทบทวนเพิ่มรอบนี้
- Q10: ลำดับ Stage A/B/C ตามร่าง (Push+Pin → Vibe+Filters → Dark+Impact) ยืนยันตามนี้หรือ PM ต้องการสลับลำดับเพราะ dependency ต่อ /db-architect ของ US-44/US-45 อาจใช้เวลานานกว่า US-42? — **PM ยืนยันแล้ว**: คง Stage เดิมตามร่าง A (US-42+43) → B (US-44+45) → C (US-46+47); ทุก schema ใหม่/เปลี่ยนต้องผ่าน /db-architect และมีแนวโน้มเป็นคอขวดจริงของแต่ละ Stage ให้เริ่มงาน /db-architect ของแต่ละ Stage เร็วที่สุดขนานกับงาน UI ที่ไม่พึ่ง schema (**หมายเหตุ**: การจัดกลุ่ม Stage นี้ถูกแทนที่แล้วในรอบขยายล่าสุดโดยร่างผู้ใช้ — ดู Stage A/B/C ใหม่ที่รวม US-46/48/49/50 ด้วย ในหัวข้อ "แผนการแบ่งระยะการพัฒนา" ด้านบน)
- **Q11 (ใหม่, ยังไม่ปิด) US-49** — นิยาม "ETA ไม่ดีขึ้น" ที่แน่นอน (จำนวนครั้งติดกัน/หน้าต่างเวลา) คือเท่าไร?
- **Q12 (ใหม่, ยังไม่ปิด) US-49** — การยกเลิกแบบ no-fault ต้องตรวจสอบกับ /db-architect ว่ากระทบระบบรีวิว/`match_outcome` เดิมหรือไม่ (ธงไว้ในสมมติฐานข้อ 17)
- **Q13 (ใหม่, ยังไม่ปิด) US-49** — ถ้าฝ่ายหนึ่งกด "รอต่อ" แต่อีกฝ่ายกด "ยกเลิก" พร้อมกัน ผลลัพธ์ควรเป็นอย่างไร (แนะนำ: ยกเลิกชนะเสมอเพื่อความปลอดภัย แต่ต้อง PM ยืนยัน)
- ~~Q14 (เดิม) US-50 — รายการอ้างอิงสถานี: เลือกทาง (ก) seed list hardcode ที่ผู้ใช้จัดหา/อนุมัติพิกัด หรือ (ข) เลื่อนเป็นตาราง admin-managed ในอนาคต?~~ — **ตกไปแล้ว (moot):** orchestrator ยกเลิกแนวคิดรายชื่อสถานีอ้างอิงทั้งหมดตามคำตัดสินสุดท้าย (ดู `docs/tasks-round7.md`) กฎใหม่ใช้ได้กับปลายทางคนนั่งทุกที่ผ่าน flow ค้นหา/ปักหมุดเดิม จึงไม่ต้องมีรายการอ้างอิงสถานี/seed data/admin table อีกต่อไป

## Out of Scope (รอบ 7)
- การออกแบบ UI/แอนิเมชัน/ภาพ, การเขียนโค้ด, การเลือกเทคโนโลยี (หน้าที่แผนกอื่น)
- การสร้างระบบเลือก/เสนอ/ยืนยันจุดนัดรับใหม่ (มีอยู่แล้ว, US-43 เพิ่มเฉพาะการ snap)
- ขั้นตอนยืนยันอีเมลสถาบัน/OTP ใหม่ (มีอยู่แล้วและอัตโนมัติ ไม่เกี่ยวข้องกับ US-45 อีกต่อไป)
- **(ตัดออกทั้งหมดตามการตัดสินใจของผู้ใช้)** สวิตช์ค้นหา "หาเฉพาะเพื่อนในสถาบันเดียวกัน" ของ US-45 — ไม่ทำในรอบนี้และไม่มีแผนจะทำต่อ (เหตุผล: ไม่สำคัญเท่าที่คิด และใช้ได้เฉพาะผู้ใช้กลุ่มที่มี org verification เท่านั้น ไม่ global/ไม่ scale เท่า women-only ซึ่งเกี่ยวข้องกับผู้ใช้ทุกคนเป็นสากลกว่า)
- คอลัมน์ `trips.same_org_only` (migration 0012, apply ขึ้น live แล้ว) — **ถือเป็น dead/deprecated column โดยตั้งใจ** ปล่อยทิ้งไว้ในสคีมาไม่ลบ เพื่อเลี่ยง destructive migration ที่ไม่จำเป็น; ห้าม Dart/UI ใด ๆ อ่านหรือเขียนคอลัมน์นี้ในรอบนี้หรืออนาคตอันใกล้
- iOS push ผ่าน APNs (เลื่อนเป็น P1 รอบถัดไป, ต้องมี Apple Developer Program)
- Full moderation/การกรองคำหยาบ-PII อัตโนมัติแบบสมบูรณ์ในข้อความ mood (PM ยืนยันแล้ว, Q6: ทำเฉพาะ guard พื้นฐานราคาถูก — ปฏิเสธเลขติดกัน ≥8 หลักและ blocklist คำหยาบขนาดเล็กทั้ง client/server เท่านั้น ไม่ใช่การยกเว้นทั้งหมดอีกต่อไป; ความเสี่ยงเนื้อหาไม่เหมาะสมรูปแบบอื่นที่เหลือยังบันทึกไว้เป็นความเสี่ยงต่อ)
- การซิงก์ preset สถานที่โปรดขึ้น server (ค้างจากรอบ 6, ไม่เกี่ยวกับรอบนี้; **US-50 ฉบับปรับทิศทางใหม่ไม่แตะ `PresetController`/preset Home-Office เดิมเลย** — ไม่มีหมวด/ข้อมูลสถานีสาธารณะใด ๆ เกี่ยวข้องอีกต่อไป)
- ระบบธีมที่สามนอกเหนือจาก light/dark ของ rider/driver tone token เดิม
- ช่องพิมพ์ข้อความอิสระสำหรับสติกเกอร์ขอบคุณ (เฉพาะ preset)
- การเปลี่ยน/ผ่อนเกณฑ์การมองเห็นตัวตน (US-22 เดิม) จากรอบ 6 — ป้ายสถาบัน/women-only ยังคงกฎการมองเห็นเดิมทั้งหมด
- Turn-by-turn navigation, การ deploy ฟังก์ชัน purge-storage-queue ที่ค้างจากรอบ 5 (แยกเรื่องกัน แต่ US-48 ขยายใช้ pattern เดียวกันนี้ — การอนุมัติ deploy เป็นคนละเรื่องกับการขยายฟังก์ชัน)
- การแปลงเสียงเป็นข้อความ (speech-to-text) หรือการวิเคราะห์/ตรวจสอบเนื้อหาไฟล์เสียงที่บันทึกใน US-48 sub-feature (A) — ไม่ทำในรอบนี้และไม่มีแผนจะทำ (privacy by design)
- ฟีเจอร์ "อัตราการยกเลิก" (cancellation rate) เต็มรูปแบบ — ยังไม่มีอยู่ในระบบตอนนี้ US-49 เพียงกันไว้ล่วงหน้าไม่ให้ no-fault cancel ถูกนับถ้าฟีเจอร์นี้เกิดขึ้นในอนาคต
- **(ตัดออก/ยกเลิกทั้งหมด — superseded)** ตาราง/รายชื่ออ้างอิงสถานีขนส่งสาธารณะ (BTS/MRT/ท่ารถตู้) ของ US-50 ไม่ว่าจะเป็น seed data hardcode หรือตาราง admin-managed ในอนาคต — **ยกเลิกทั้งหมดตามคำตัดสินสุดท้ายของ orchestrator** (ไม่มีรายชื่อสถานีอีกต่อไปในการออกแบบนี้เลย งานหาพิกัดสถานีที่ทำค้างไว้ก่อนหน้าถูกยกเลิก ไม่เสียหาย ไม่ได้ใช้งานจริง)
- Sunset/sunrise-based auto dark mode หรือการใช้ตำแหน่ง GPS ในการคำนวณเวลามืด/สว่างของ US-46 — ใช้ช่วงเวลาคงที่ 18:00–06:00 ตามเวลาเครื่องเท่านั้น
