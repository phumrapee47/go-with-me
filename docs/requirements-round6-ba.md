# Requirements รอบ 6 (ฉบับ BA): Friendly & Frictionless Commute UX (ส่วนต่อของ requirements.md และ requirements-round5.md)

## สถานะเอกสารและลำดับความสำคัญ
- เอกสารนี้แปลงร่าง `docs/requirements-round6.md` (ไม่ได้แก้ไขไฟล์ร่าง) เป็น user story ทางการ ใช้เลข story ต่อจาก US-28 คือ US-29..US-41
- ถ้าข้อความขัดกับร่างของผู้ใช้ ให้ถือเอกสารนี้เป็นหลักตามตาราง "ส่วนที่ปรับจากร่าง" ท้ายเอกสาร (ทุกจุดที่ปรับมาจากคำตัดสินของ orchestrator)
- ไม่มีการออกแบบ UI ไม่มีโค้ด ไม่เลือกเทคโนโลยี (ชื่อ widget/หน้าจอ เช่น `UnifiedRideScreen`, `CommuteCardDeck`, `SwipeToConfirmSlider` ใช้เป็นชื่อเรียกอ้างอิงตามร่างของผู้ใช้เท่านั้น)
- ระดับความสำคัญ: P0 = ต้องมีก่อนปล่อย/ด้านความปลอดภัย, P1 = ควรมีในรอบนี้, P2 = ทำถ้ามีเวลา

## บริบท
แก่นของแอปคือ "กลับด้วยกันมั้ย" หาเพื่อนร่วมทางกลับบ้านในฟีลลิ่งเพื่อน ไม่ใช่แอปเรียกรถ รอบ 6 ลดจำนวนการแตะและ dialog ซ้ำซ้อน รวมหน้าเดินทางที่แยกกัน (ActiveTripScreen, LiveMapScreen, แชท) เป็นหน้าเดียวแบบ bottom sheet เปลี่ยนรายการ nearby เป็น card deck สร้างทริปกลับบ้านแบบ 1 แตะจากค่าที่จำไว้ และปรับโทนข้อความให้เป็นมิตร โดยไม่ลดระดับความปลอดภัยและความเป็นส่วนตัวที่มีอยู่ (US-9, US-10, US-12, US-18, US-21..24, US-26)

## สิ่งที่มีอยู่แล้ว (baseline ที่ต้องไม่ถดถอย)
- `ActiveTripScreen` (เริ่ม/ขึ้นรถ/ถึงแล้ว ด้วย confirm dialog), `LiveMapScreen` (`/matches/:id/live`), แชท (มี quick reply เรื่องจุดลง), รายการ nearby ที่มีคำอธิบายกฎ neighbourhood, ปุ่มนำทางภายนอก, wizard สร้างทริป 3 ขั้น (พร้อม `max_dropoff_m` ของ Driver), confirm dialog สำหรับยกเลิก/ลบ/รายงาน
- RPC จริงที่ใช้: `mark_boarded`, การอัปเดตสถานะทริป (start/arrive), `cancel_match`, `propose/confirm_meeting_point`, `request_match`, `find_matches` ฯลฯ (ชื่อ `trip_actions`, `board_passenger`, `complete_trip` ในร่างของผู้ใช้ไม่มีจริง)
- strings อยู่ที่ `lib/core/l10n/strings_trip.dart`, `strings_roles.dart`

## สมมติฐานและคำตัดสิน (รอบ 6)
คำตัดสินของ orchestrator บันทึกเป็นสมมติฐาน ทุกข้อมีเครื่องหมาย "สมมติฐาน:" ข้อที่ PM ตัดสินแล้ว (Q1-Q10 ใน `docs/tasks-round6.md`) ทำเครื่องหมาย "PM ยืนยันแล้ว"
1. สมมติฐาน: ปุ่ม SOS ต้องเข้าถึงได้ในทุกระดับของ sheet ใน `UnifiedRideScreen` (Collapsed, Half, Full) ไม่ใช่เฉพาะ Full (ความปลอดภัย P0; ร่างเดิมวางไว้เฉพาะ Full)
2. สมมติฐาน (PM ยืนยันแล้ว, Q2): สถานที่โปรด (บ้าน/จุดเริ่มประจำ) เก็บ "ในเครื่องเท่านั้น" (secure/local storage ผูก user id) ในรอบ 6 ไม่เก็บที่ server (ที่อยู่บ้านเป็นข้อมูลอ่อนไหวตาม PDPA); ล้างเมื่อออกจากระบบและเมื่อลบบัญชี; การซิงก์ server = นอกรอบนี้ และต้องผ่านฝ่ายกฎหมายก่อนเสมอ
3. สมมติฐาน: การปัดขวาบนการ์ดคือการ "ส่งคำขอ" จึงต้องยกเลิกได้ (undo) ประมาณ 5 วินาที และทุกการปัดมีปุ่มทางเลือก (✕ / 💚) ที่ใช้ได้กับ screen reader และผู้ใช้ที่มีข้อจำกัดด้านการเคลื่อนไหว; เคารพเพดานเดิม (คำขอค้างสูงสุดต่อทริป) และ throttle เดิม; card deck ไม่ใช่ UI หาคู่แบบ dating: ห้ามตัดสินจากรูปอย่างเดียว ต้องแสดงข้อมูลความปลอดภัย (ป้าย บทบาท ระยะรับส่ง) ตลอด (วิธีทำงานของ undo และผลต่อเพดาน/throttle: PM ตัดสินแล้วใน Q6 ดู US-35)
4. สมมติฐาน: `SwipeToConfirmSlider` แทน confirm dialog เฉพาะการเปลี่ยนสถานะปกติ (เริ่มทริป, ขึ้นรถแล้ว, ถึงแล้ว) ต้องมีทางเลือกที่เข้าถึงได้ (กดค้าง หรือ semantics action) และห้ามใช้กับ SOS, ยกเลิก, รายงาน, ลบ (ยังใช้ dialog/ขั้นยืนยันเดิม)
5. สมมติฐาน: การไฮไลต์ geofence 150 ม. เป็น "การนำเสนอเท่านั้น" ไม่กำกับหรือกระตุ้นการเปลี่ยนสถานะอัตโนมัติ; คำนวณบนเครื่องจากปลายทาง/จุดรับ "ของผู้ใช้เอง"; Driver ไม่ได้รับปลายทางของ Rider (สอดคล้อง US-24)
6. สมมติฐาน: RPC เดิมไม่เปลี่ยน ไม่มีการแก้ RLS (ยกเว้นข้อ 10 ที่ต้องขยาย `find_matches` ผ่าน /db-architect)
7. สมมติฐาน (PM ยืนยันแล้ว, Q1): "คนขับมาถึงจุดรับ" ยังไม่มี event ใน backend; รอบนี้ให้ Driver กดปุ่มเดียว "ถึงจุดรับแล้ว" ส่งข้อความสำเร็จรูป "คนขับมารอที่จุดรับแล้วนะ" ในแชทเดิม + แจ้งเตือนในแอป/local notification ฝั่ง Rider (ไม่มีสถานะทริปใหม่ ไม่มี DB ใหม่); throttle 1 ครั้ง/นาที
8. สมมติฐาน: "จำนวนที่นั่งว่าง" ของ Driver เป็น 1 เสมอ (ที่นั่งคงที่) แสดง "รับได้ 1 คน"
9. สมมติฐาน: emoji ในข้อความต้องมีข้อความทางเลือกสำหรับ screen reader และข้อความเป็นมิตรต้องไม่ซ่อนข้อความ error/ความปลอดภัย
10. สมมติฐาน (PM ยืนยันแล้ว, Q7): รวมรายการค้างรอบ 5 R5-1 (ค่ารวมคะแนนบนการ์ดค้นหา) เข้ารอบนี้เป็น P1; ต้องขยาย `find_matches` (ผ่าน /db-architect) คืนค่ารวมแบบไม่ระบุตัวตน ห้ามคืน user id และผูกกับ `review.show_in_search`; แสดงเมื่อรีวิวที่เปิดเผยแล้ว ≥ 3 เท่านั้น; ถ้า DB ไม่ทัน เลื่อนเฉพาะ US-36 (US-34/35 ไม่ถูกบล็อก; UI ต้องซ่อนช่องเมื่อไม่มีค่า)
11. สมมติฐาน: "หาเพื่อนกลับบ้าน" 1 แตะต้องสร้างทริปที่ถูกต้องตามกฎเดิม: บทบาท Driver ต้องมีข้อมูลรถ/ลงทะเบียนคนขับแล้ว และมี `max_dropoff_m` (ค่าเริ่มต้น 2,000 ม. จำค่าที่ใช้ล่าสุด); เคารพกฎ "ทริปที่ใช้งานได้สูงสุด 1 ทริป"; ถ้า preset ไม่ครบ ตกไปที่ wizard เต็ม; ใช้เฉพาะ car (Rider/Driver) ตาม Q9 (ดู US-39)
12. สมมติฐาน: ค้างรอบ 5 อื่น ๆ อยู่นอก scope: จุดลงสาธารณะ (US-24 P1), รายการเลี้ยว turn-by-turn, การ deploy ฟังก์ชัน purge
13. สมมติฐาน: ปุ่ม "ทักทายนัดจุดรับ" ใส่ข้อความทักทายลงช่องพิมพ์ให้ผู้ใช้กดส่งเอง (สอดคล้อง quick reply รอบ 5 ที่ไม่ส่งอัตโนมัติ) ไม่แนบพิกัดหรือชื่อสถานที่
14. สมมติฐาน: "รูปคู่" ใน Match Moment ใช้กฎการมองเห็นรูปเดิม (US-22): เห็นรูปได้เฉพาะเมื่อจับคู่ตอบรับแล้ว ไม่มีรูปแสดง avatar ตัวอักษรย่อ
15. สมมติฐาน (PM ยืนยันแล้ว, Q3): บนการ์ด deck (ยังไม่จับคู่) ไม่แสดงรูปโปรไฟล์จริง (ตาม US-22: ไม่เห็นรูปในผลค้นหา) ใช้ตัวอักษรย่อ + ชื่อเล่น; รูปโปรไฟล์แสดงหลังจับคู่ตอบรับเท่านั้น (Match Moment/แชท/UnifiedRide); คำว่า "รูปโปรไฟล์" ในร่างตีความตามนี้ **ข้อนี้ต่างจากร่างของผู้ใช้โดยตั้งใจ** (ร่างต้องการรูปบนการ์ด) ดูตาราง "ส่วนที่ปรับจากร่าง"
16. สมมติฐาน: ETA ที่ Collapsed ใช้ข้อมูลและกฎเดียวกับ LiveMapScreen เดิม (ป้าย "โดยประมาณ", fallback เส้นตรง)

## User Stories

### US-29: หน้าเดินทางรวม UnifiedRideScreen (แผนที่พื้นหลัง + sheet 3 ระดับ) [P0]
As a คนขับหรือคนนั่งที่ทริปกำลังดำเนินอยู่, I want ดูแผนที่สด ข้อมูลทริป และแชท ในหน้าเดียว, so that ไม่ต้องสลับหลายหน้าระหว่างเดินทาง

**Acceptance Criteria:**
- [ ] แผนที่เต็มจอเป็นพื้นหลังถาวร แสดงตำแหน่งตนเอง คู่เดินทาง (ตามสิทธิ์ US-23) เส้นทาง และจุดรับ/ส่งที่ตกลงแล้ว; กติกาการมองเห็นตำแหน่งสด, stale > 45 วินาที, follow/recenter/fit-both ตาม US-23 คงเดิม
- [ ] มี bottom sheet ลากได้ 3 ระดับ: Collapsed (รูป/ตัวอักษรย่อและชื่อเล่นของคู่, ETA โดยประมาณ, แถบสไลด์หลัก, ทางเข้า SOS), Half (ข้อมูลรถทะเบียน/รุ่นเมื่อมีสิทธิ์ตาม US-17, ชิปแชทด่วน, ปุ่มนำทางภายนอก), Full (รายละเอียดทริปทั้งหมด, แชร์ทริป, SOS, แชท)
- [ ] ข้อมูลรถแสดงเฉพาะเมื่อมีสิทธิ์เห็นตามกฎเดิม (การจับคู่ตอบรับ, ตามสวิตช์ยินยอมของ Driver); ไม่มีข้อมูลรถของทริปที่ไม่จับคู่
- [ ] ปุ่มนำทางภายนอกที่ Half ใช้กติกา US-24 เดิมทั้งหมด (รวม dialog แจ้งครั้งแรก, คำเตือนขับรถ, ซ่อนปุ่มจุดรับเมื่อ ≤ 50 ม.) (PM ยืนยันแล้ว, Q10)
- [ ] แชทใช้ข้อความ/สิทธิ์/quick reply จุดลงเดิม (US-8, US-24) ไม่มีการเปลี่ยนเงื่อนไขเปิด-ปิดแชท
- [ ] ระดับ sheet ที่เลือกจำไว้ตลอดการอยู่ในหน้านั้น และเมื่อหมุนหน้าจอ/กลับจากแอปนำทางภายนอกไม่รีเซ็ตสถานะทริป; แชทที่กำลังพิมพ์ไม่หายเมื่อเปลี่ยนระดับ
- [ ] ทริปที่ไม่มีคู่ตอบรับ (ทริปเดี่ยวหรือ Peer) แสดงเนื้อหาเท่าที่เกี่ยวข้อง (ไม่มีส่วนคู่/แชท) และไม่ error
- [ ] ปลายทาง/สถานะเมื่อคู่ยกเลิก, no-show, จบทริป, บล็อก แสดงข้อความเป็นกลางตามกฎเดิม (US-18, US-23) และไอคอนคู่หายทันที
- [ ] ไม่มีการเปลี่ยน RPC, ไม่มีการแก้ RLS; ข้อมูลที่ Driver ได้รับไม่มีปลายทางของ Rider (ทดสอบเรียก API ตรงเหมือนรอบ 5)

**Dependencies:** US-9, US-12, US-17, US-18, US-23, US-24; ฝ่ายออกแบบกำหนดรายละเอียดขนาด/แอนิเมชันของ sheet

### US-30: SOS เข้าถึงได้ทุกระดับ sheet [P0]
As a ผู้ใช้ที่กำลังเดินทาง, I want กด SOS ได้จากทุกระดับของ sheet, so that ขอความช่วยเหลือได้ทันทีโดยไม่ต้องดึง sheet ขึ้นก่อน

**Acceptance Criteria:**
- [ ] ปุ่ม/ทางเข้า SOS มองเห็นและกดได้ที่ Collapsed, Half และ Full (ไม่เกิน 2 การแตะจากหน้านี้ ตาม US-10) ตลอดขณะทริป "กำลังเดินทาง" ไม่ขึ้นกับการกด "ขึ้นรถแล้ว"
- [ ] ขั้นตอนยืนยันกันกดพลาดของ SOS คงเดิม (ไม่ใช้ `SwipeToConfirmSlider`); เนื้อหา SOS, การรวมชื่อ/ทะเบียนตามสวิตช์ยินยอม (R3-1), การบันทึกเหตุการณ์ ไม่เปลี่ยน
- [ ] SOS ไม่ถูกบังโดย sheet, แป้นพิมพ์แชท, หรือแถบสไลด์ และไม่เลื่อนหายเมื่อลาก sheet; ขนาดพื้นที่แตะไม่เล็กกว่าปัจจุบัน
- [ ] ใช้ได้ทั้งสองบทบาท/ทุกโทน (US-20) และเมื่อออฟไลน์ยังโทร 191/1669 ได้ (US-10)
- [ ] มี widget test ตรวจว่ามี SOS ทั้ง 3 ระดับ และ test เดิมของ SOS ผ่านโดยไม่แก้เงื่อนไข

**Dependencies:** US-10, US-29

### US-31: SwipeToConfirmSlider แทน confirm dialog ของการเปลี่ยนสถานะปกติ [P0]
As a คนขับหรือคนนั่ง, I want สไลด์เพื่อยืนยันเริ่มทริป ขึ้นรถแล้ว และถึงแล้ว, so that กดได้เร็วโดยไม่มี dialog ซ้ำซ้อนและกดพลาดยาก

**Acceptance Criteria:**
- [ ] ตัด confirm dialog ออกจากเฉพาะ 3 การกระทำ: เริ่มทริป (Driver) "สไลด์เพื่อเริ่มออกเดินทาง", ขึ้นรถแล้ว (Rider เมื่อถึงจุดรับ) "สไลด์เพื่อขึ้นรถแล้ว", ถึงแล้ว (label มี 2 แบบตาม Q5): "สไลด์เมื่อถึงบ้านปลอดภัย" เมื่อปลายทางของทริปตรงกับ preset "บ้าน" ที่บันทึกไว้ในเครื่อง, มิฉะนั้น (ปลายทางอื่น, ทริป Peer, ไม่มี preset) "สไลด์เมื่อถึงที่หมายปลอดภัย"
- [ ] การเทียบ "ปลายทาง = บ้าน" ทำบนเครื่องเท่านั้น ไม่ส่ง preset/ผลเทียบไป server ใช้รัศมีเดียวกับที่ตั้งค่าเมื่อสร้างทริปจาก quick card (US-39); ถ้าเทียบไม่ได้หรือไม่แน่ใจ ใช้ label ทั่วไป "ที่หมาย" เป็น fallback ปลอดภัย; label และ semantics ของสไลเดอร์ใช้ตรรกะเดียวกับข้อความถึงที่หมายใน US-40
- [ ] การสไลด์ครบระยะเท่านั้นจึงเรียก RPC/การอัปเดตสถานะเดิม; ปล่อยก่อนถึงปลายทางแล้วเด้งกลับ ไม่ส่งคำสั่ง; แตะเฉย ๆ ไม่ทำงาน; เรียกซ้ำไม่ได้ขณะรอผล (ไม่มีการเรียกซ้ำสองครั้ง)
- [ ] มีทางเลือกที่เข้าถึงได้: กดค้างเพื่อยืนยัน หรือ semantics action ที่ screen reader ใช้ได้ (เช่น "ดับเบิลแตะเพื่อยืนยัน") และรองรับผู้ใช้ที่ไม่สามารถลากได้; ค่า label อ่านออกเสียงชัดเจนว่าทำอะไร
- [ ] เงื่อนไขเปิดใช้เดิมคงเดิมทั้งหมด (ขึ้นรถแล้วต้องเมื่อทริปทั้งสองกำลังเดินทางและมีการจับคู่ตอบรับ, กดซ้ำไม่ได้; บังคับที่ backend); เมื่อ RPC ล้มเหลวแสดงข้อความไทยและสไลเดอร์กลับสถานะเริ่มต้น พร้อมลองใหม่ได้
- [ ] ห้ามใช้กับ SOS, ยกเลิกทริป/การจับคู่, รายงาน, ลบรูป/ลบบัญชี, ออกจากระบบ: ยังใช้ dialog/ขั้นยืนยันเดิม (ทดสอบว่ายังมี dialog ที่ทริกเกอร์เหล่านี้)
- [ ] รองรับโหมดลดแอนิเมชัน (reduce motion): ไม่พึ่งแอนิเมชันในการสื่อสถานะ
- [ ] Widget test ที่เคยคาดหวัง dialog ยืนยันของ 3 การกระทำนี้ ถูกแก้เป็นทดสอบ drag ครบ/ไม่ครบ และทางเลือกเข้าถึงได้; test ของ dialog อื่นไม่ถูกแก้; มี test ของ label 2 แบบ (บ้าน/ทั่วไป)

**Dependencies:** US-9, US-12, US-29; US-38 (preset บ้านสำหรับเทียบปลายทาง)

### US-32: ไฮไลต์เมื่อใกล้จุดหมาย (geofence 150 ม.) [P1]
As a ผู้ที่ใกล้ถึงจุดหมาย, I want สไลด์เปลี่ยนเป็นสีเขียวพร้อมข้อความแนะนำเมื่ออยู่ใกล้, so that จบทริปได้เร็วและรู้ว่าถึงแล้ว

**Acceptance Criteria:**
- [ ] เมื่อระยะจากตำแหน่งปัจจุบันถึงปลายทางของผู้ใช้เอง (หรือจุดรับสำหรับสไลด์ "ขึ้นรถแล้ว") < 150 ม. แถบสไลด์เปลี่ยนเป็นสีเขียวพร้อมข้อความแนะนำ; ห่าง ≥ 150 ม. กลับสถานะปกติ (ขอบเขต 150 ม. พอดี = ไม่ไฮไลต์)
- [ ] การไฮไลต์เป็นการนำเสนอเท่านั้น: ไม่ทำให้เปลี่ยนสถานะอัตโนมัติ ไม่เปิดหรือปิดปุ่ม/สไลด์ ผู้ใช้สไลด์ได้ทุกเมื่อแม้อยู่นอกรัศมี (ตรงกับ US-12 "กดเองได้ทุกเมื่อ")
- [ ] ไม่พึ่งสีอย่างเดียว: มีข้อความและ semantics label ("ใกล้ถึงแล้ว") อ่านออกเสียงได้; สีผ่านเกณฑ์คอนทราสต์
- [ ] คำนวณบนเครื่องเท่านั้น ไม่ส่งพิกัดหรือผลคำนวณไป server; ใช้ปลายทางของผู้ใช้เอง ไม่ใช้ปลายทางของคู่ (Driver ไม่ได้ปลายทางของ Rider)
- [ ] ไม่มีสิทธิ์ตำแหน่ง/ไม่มีสัญญาณ GPS/ตำแหน่งไม่แม่น: ไม่ไฮไลต์ ไม่ error และไม่มีข้อความค้าง; ไม่กระพริบเข้าออกถี่ตามสัญญาณ GPS แกว่ง (ต้องมี hysteresis ที่ระดับข้อกำหนด: ไม่สลับสถานะเร็วกว่าที่ผู้ใช้สังเกตได้; ค่าที่แน่นอนเป็นหน้าที่นักพัฒนา)
- [ ] ไม่เพิ่มการรับ/ส่งตำแหน่งหรือการติดตามเบื้องหลังนอกกติกาเดิม (US-15, US-23 P1)

**Dependencies:** US-12, US-31

### US-33: คนขับแจ้ง "ถึงจุดรับแล้ว" [P1]
As a คนขับ, I want กดปุ่มเดียวเพื่อบอก Rider ว่ามาถึงจุดรับแล้ว, so that Rider รู้ตรงกันและไม่ต้องพิมพ์ข้อความ

**Acceptance Criteria:**
- [ ] ทริป car ที่จับคู่ตอบรับแล้วและมีจุดรับที่ตกลงแล้ว: Driver เห็นปุ่ม "ถึงจุดรับแล้ว" (ทางเลือกเดียว ไม่ใช้สไลเดอร์) กดครั้งเดียวส่งข้อความในแชท/แจ้งเตือนถึง Rider ด้วยข้อความ "คนขับมารอที่จุดรับแล้วนะ"
- [ ] ไม่มีสถานะทริปใหม่และไม่มีคอลัมน์/RPC ใหม่ (ใช้ช่องทางส่งข้อความเดิม); ไม่แนบพิกัดสดหรือปลายทาง
- [ ] กดซ้ำถูกจำกัด (ส่งซ้ำได้ไม่ถี่กว่าช่วงที่กำหนด เช่น 1 ครั้ง/นาที) ป้องกันสแปม; ปุ่มปิดเมื่อการจับคู่สิ้นสุด/ยกเลิก หรือหลัง Rider ขึ้นรถแล้ว
- [ ] Rider ที่ได้รับข้อความเห็นในแชทและ (ถ้ามีระบบเดิม) การแจ้งเตือนในแอป; ข้อความมีข้อความทางเลือกสำหรับ emoji ถ้ามี
- [ ] ไม่ตัดสินสถานะการมาถึงจากพิกัด GPS (ไม่ใช่การยืนยันอัตโนมัติ) และข้อความไม่ระบุว่าเป็นการยืนยันของระบบ

**Dependencies:** US-8, US-18; สมมติฐานข้อ 7 (PM ยืนยันแล้ว, Q1)

### US-34: หน้ารวมการ์ดเพื่อนร่วมทาง CommuteCardDeck [P0]
As a คนที่กำลังหาเพื่อนกลับบ้าน, I want ดูผู้ที่เข้าเกณฑ์เป็นการ์ดใบใหญ่ทีละคน, so that ตัดสินใจได้เร็วและรู้สึกเป็นเพื่อน ไม่ใช่รายการราชการ

**หมายเหตุ (Q3 ต่างจากร่างผู้ใช้โดยตั้งใจ):** ร่างของผู้ใช้ต้องการ "รูปโปรไฟล์" บนการ์ด แต่ PM ตัดสินให้การ์ด deck ใช้ตัวอักษรย่อ + ชื่อเล่น และแสดงรูปหลังจับคู่ตอบรับเท่านั้น (Match Moment/แชท/UnifiedRide) เพื่อคง US-22 เป็นผลกระทบต่อผู้ใช้โดยตรงที่ orchestrator ต้องแจ้งผู้ใช้; ถ้าผู้ใช้ต้องการให้แสดงรูปบนการ์ด ต้องเปลี่ยนกฎ US-22 + ผ่านฝ่ายกฎหมาย + แก้ `find_matches`/signed URL policy (ไม่ทำในรอบนี้)

**Acceptance Criteria:**
- [ ] แสดงผลลัพธ์จาก `find_matches` (กฎจับคู่ US-6/US-21 คงเดิม ไม่ผ่อนเกณฑ์) เป็นการ์ดเดี่ยวขนาดใหญ่ทีละใบ; ลำดับตามคะแนนเดิม
- [ ] องค์ประกอบบนการ์ด: ตัวอักษรย่อ + ชื่อเล่นเด่นชัด (ไม่ใช้รูปจริงตามสมมติฐานข้อ 15 / Q3), ป้ายยืนยันตัวตน/สถาบัน/บริษัท (เช่น "นิสิตจุฬาฯ", "บุคคลทั่วไป") ตามสิทธิ์เปิดเผยเดิม, ความเข้ากัน ("ทางเดียวกัน ~N%", เวลาออกเดินทาง), บทบาท (Driver/Rider)
- [ ] ถ้าเป็นการ์ด Driver: แสดงไอคอนรถ + "รับได้ 1 คน" (ที่นั่งคงที่ = 1) + "คนขับรับส่งได้ไม่เกิน X จากปลายทางของเขา" (รูปแบบตาม US-21)
- [ ] ข้อมูลความปลอดภัย (ป้าย, บทบาท, ระยะรับส่ง) แสดงบนการ์ดตลอด ไม่ถูกซ่อนหลังการโต้ตอบเพิ่ม; ไม่มีการตัดสินจากรูปอย่างเดียว; ไม่ใช้ภาษาแนว dating/คะแนนความน่าดึงดูด
- [ ] ความเป็นส่วนตัวเท่าเดิม: ไม่แสดงพิกัด ปลายทางจริง ระยะปลายทางจริงระหว่างสองทริป หรือตัวตนที่ไม่อยู่ในสิทธิ์; ไม่ส่งรูปโปรไฟล์ในผลค้นหา (US-22)
- [ ] สถานะว่าง: ไม่มีผล แสดงคำอธิบายหมวดเดิม (`NoMatchHint`: none_found/far_destination/far_origin) และทางไปแก้ทริป; สถานะโหลด/ผิดพลาดมีข้อความไทยและลองใหม่ได้ ไม่ค้าง; เมื่อการ์ดหมด แสดงหน้าสรุปพร้อมลิงก์ไปรายการเดิม
- [ ] มีปุ่มสลับ deck/รายการ กลับไปมองแบบรายการ (หน้า nearby เดิมเก็บไว้เป็นมุมมองทางเลือก) เพื่อ a11y และผู้ใช้ที่ต้องการเปรียบเทียบหลายคน (PM ยืนยันแล้ว, Q4)
- [ ] คำขอที่ส่งไปแล้ว/ถูกปฏิเสธ/ทริปที่ไม่ผ่านกฎ ไม่กลับมาปรากฏซ้ำในสำรับเดียวกัน (ไม่มีการ์ดซ้ำ)
- [ ] ประสิทธิภาพ: การ์ดถัดไปโหลดล่วงหน้า การเลื่อนไม่กระตุกบนอุปกรณ์ระดับกลาง (NFR)

**Dependencies:** US-6, US-7, US-21; `NoMatchHint` (รอบ 5)

### US-35: การโต้ตอบบนการ์ด (ข้าม / ชวนกลับด้วยกัน) พร้อม undo และทางเลือกเข้าถึงได้ [P0]
As a ผู้ใช้ของ card deck, I want ปัดหรือกดปุ่มเพื่อข้าม/ชวน และยกเลิกได้ถ้าพลาด, so that ไม่ส่งคำขอโดยไม่ตั้งใจ

**Acceptance Criteria:**
- [ ] ปัดซ้าย หรือกดปุ่ม ✕ = ข้ามไปคนถัดไป (ไม่ส่งอะไรถึงอีกฝ่าย และไม่บอกอีกฝ่ายว่าถูกข้าม)
- [ ] ปัดขวา หรือกดปุ่ม 💚 = "ชวนกลับด้วยกัน" คือส่งคำขอจับคู่ผ่าน `request_match` เดิม "ทันที" (ไม่หน่วงส่ง; บังคับกฎ predicate เดียวกันที่ server)
- [ ] หลังส่งสำเร็จ แสดง snackbar "ชวนเพื่อนแล้ว" พร้อมปุ่ม "เลิกชวน" 5 วินาที (Q6): undo = คำขอนั้น "ถูกส่งไปแล้ว" และการกด "เลิกชวน" คือการยกเลิกคำขอ pending ผ่านช่องทางยกเลิกเดิม (ไม่ใช่การหน่วงส่ง); เมื่อยกเลิกสำเร็จการ์ดกลับมา
- [ ] คำขอที่ถูก undo แล้ว "ไม่นับ" เพดานคำขอค้าง (เพราะไม่ pending แล้ว) แต่ "ยังนับ" throttle การส่งคำขอ (กันการส่ง-ยกเลิกรัว ๆ); เมื่อชน throttle แสดงข้อความไทยที่ชัดเจนว่ารอสักครู่ ไม่ทำให้ผู้ใช้สับสน
- [ ] ห้าม undo หลังอีกฝ่ายตอบรับแล้ว: ถ้าอีกฝ่ายตอบรับไปก่อน (หรือคำขอไม่ใช่ pending แล้ว) การกด "เลิกชวน" ต้องไม่ยกเลิกการจับคู่ที่ตอบรับแล้ว และแสดงข้อความสุภาพ (เช่น เพื่อนตอบรับแล้ว ยกเลิกได้จากหน้าจับคู่ตามปกติ); การป้องกันบังคับที่ backend ไม่ใช่แค่ UI
- [ ] ปุ่ม "เลิกชวน" ปิดใช้ระหว่างรอผลการส่งคำขอ (ยังไม่สำเร็จ) และกดซ้ำไม่ได้ขณะกำลังยกเลิก
- [ ] ปุ่ม ✕ และ 💚 เป็นปุ่มจริงที่ focus ได้ ป้าย semantics ชัดเจน ("ข้าม" / "ชวนกลับด้วยกัน") ผู้ใช้ screen reader และผู้ใช้ที่ปัดไม่ได้ใช้งานครบทุกฟังก์ชัน; ผู้ใช้ไม่ต้องปัดเพื่อใช้ฟีเจอร์ใดเลย
- [ ] เคารพเพดานเดิม: คำขอค้างสูงสุดต่อทริป และ throttle การส่งคำขอ; เมื่อเต็ม ปุ่ม 💚 ปิด/แจ้งข้อความไทยชัดเจน และการปัดขวาเด้งกลับโดยไม่ส่ง
- [ ] ปัดขวารัว ๆ ไม่ส่งซ้ำ (ต่อ 1 การ์ด = 1 คำขอ); ข้อผิดพลาดจาก server (เช่น ไม่ผ่านกฎ, มีคู่แล้ว, ทริปหมดอายุ) แสดงข้อความไทยและการ์ดกลับมา/ข้ามอย่างสุภาพ ไม่ค้าง
- [ ] มีทางเข้าดูรายละเอียดเต็มของการ์ดก่อนตัดสินใจ (ข้อมูลปัจจุบันจากหน้ารายละเอียดผู้สมัคร) ไม่ต้องตัดสินจากการ์ดอย่างเดียว
- [ ] ใช้ได้เมื่อ reduce motion: การปัดไม่ต้องอาศัยแอนิเมชัน; มีการสื่อผลด้วยข้อความ
- [ ] snackbar undo ไม่หายขณะมี focus (a11y) และไม่บันทึกพฤติกรรมการปัด

**Dependencies:** US-7, US-34; เพดาน/throttle เดิมของ `request_match`

### US-36: ค่ารวมคะแนนบนการ์ดค้นหา (R5-1) [P1]
As a ผู้ที่ดูการ์ดเพื่อนร่วมทาง, I want เห็นคะแนนรวมของอีกฝ่ายเมื่อมีรีวิวเพียงพอ, so that ตัดสินใจชวนได้มั่นใจขึ้น

**Acceptance Criteria:**
- [ ] แสดงค่าเฉลี่ย + จำนวนตามบทบาทของอีกฝ่ายบนการ์ด deck เฉพาะเมื่อมีรีวิวที่เปิดเผยแล้ว ≥ 3; ต่ำกว่านั้นซ่อนองค์ประกอบทั้งหมด ไม่มีข้อความแทน (คำตัดสินรอบ 5)
- [ ] ควบคุมด้วยค่า config `review.show_in_search`: ปิด = ไม่แสดงและ backend ไม่ส่งค่ารวมออก
- [ ] ค่ารวมไม่เปิดเผยตัวตนผู้รีวิว และการเปลี่ยน `find_matches` ห้ามเพิ่ม user id ของผู้สมัครในผลค้นหา (ความเป็นส่วนตัวเดิม; ต้องคืนเฉพาะค่ารวมแบบไม่ระบุตัวตน) ทดสอบเรียก API ตรง
- [ ] ไม่กระทบเวลา/กติกาเดิมของ `find_matches` (เกณฑ์จับคู่ ลำดับ คำอธิบาย) และไม่ทำให้ผลช้าเกินกรอบเดิม
- [ ] การ์ดที่ไม่ผ่านเกณฑ์ไม่มีช่องว่างเปล่าที่ผู้ใช้เห็นเป็นข้อบกพร่อง (layout ปกติ)

### US-37: โมดอลฉลองเมื่อจับคู่สำเร็จ (Match Moment) [P1]
As a ผู้ที่คำขอถูกตอบรับ (หรือผู้ตอบรับ), I want เห็นการฉลองสั้น ๆ พร้อมทางไปต่อทันที, so that รู้ว่าจับคู่สำเร็จและนัดจุดรับได้เร็ว

**Acceptance Criteria:**
- [ ] แสดงเมื่อการจับคู่เปลี่ยนเป็น "ตอบรับแล้ว" (ทั้งผู้ส่งคำขอและผู้ตอบรับ) ครั้งเดียวต่อการจับคู่ ไม่โผล่ซ้ำเมื่อเปิดแอปใหม่/ย้อนกลับ
- [ ] ข้อความหลัก "ได้เพื่อนกลับบ้านแล้ว!" (emoji 🎉 มีข้อความทางเลือก/ไม่ถูกอ่านซ้ำแบบงง) แสดงตัวอักษรย่อหรือรูปคู่ตามกฎการมองเห็นรูป (US-22) หลังจับคู่ตอบรับแล้ว
- [ ] 2 ปุ่ม: "ทักทายนัดจุดรับ" เปิดแชทพร้อมข้อความทักทายที่ใส่ไว้ในช่องพิมพ์ (ไม่ส่งอัตโนมัติ ไม่แนบพิกัด/ชื่อสถานที่); "ดูแผนที่การเดินทาง" ไปยัง `UnifiedRideScreen` (ถ้ายังไม่ถึงเวลาเดินทาง/เงื่อนไขหน้าไม่ครบ ให้ไปหน้าการจับคู่เดิมพร้อมข้อความอธิบายสุภาพ)
- [ ] ปิดโมดอลได้ (ปุ่มปิด/แตะนอก/back) โดยไม่สูญเสียการจับคู่; focus ถูกย้ายเข้า/ออกโมดอลอย่างถูกต้องสำหรับ screen reader; แอนิเมชันปิดได้เมื่อ reduce motion
- [ ] ข้อมูลที่แสดงไม่เกินสิทธิ์เดิม (ไม่แสดงปลายทางของอีกฝ่าย); ไม่บดบังข้อความความปลอดภัยที่ต้องแสดงตามกฎเดิม
- [ ] การจับคู่ที่ถูกยกเลิกก่อนที่ผู้ใช้เห็นโมดอล ไม่แสดงโมดอลผิดพลาด

**Dependencies:** US-7, US-8, US-22, US-29

### US-38: สถานที่โปรด (บ้าน / จุดเริ่มประจำ) เก็บในเครื่อง [P1]
As a ผู้ใช้ที่กลับบ้านเป็นประจำ, I want บันทึกบ้านและจุดเริ่มประจำ (มหาวิทยาลัย/ที่ทำงาน) ไว้ใช้ซ้ำ, so that ไม่ต้องกรอกพิกัดทุกวัน

**Acceptance Criteria:**
- [ ] ตั้ง/แก้/ลบ "บ้าน" และ "จุดเริ่มประจำ" ได้ พร้อมชื่อเรียกที่ผู้ใช้ตั้ง; ตั้งจากตำแหน่งบนแผนที่/ค้นหาด้วยเครื่องมือเลือกสถานที่เดิม
- [ ] เก็บในเครื่องเท่านั้น (secure/local storage ผูก user id) ไม่ส่งไป server ไม่ปรากฏใน log/analytics/crash report; ไม่ผ่านโปรไฟล์ที่คู่เห็น
- [ ] ก่อนบันทึกครั้งแรก แจ้งผู้ใช้ว่าเก็บบนเครื่องนี้เท่านั้น และไม่ซิงก์ข้ามอุปกรณ์ (ผู้ใช้เปลี่ยนเครื่องต้องตั้งใหม่)
- [ ] ล้างทั้งหมดเมื่อออกจากระบบ และเมื่อลบบัญชี (US-15); สลับบัญชีบนเครื่องเดียวไม่รั่วข้อมูลข้ามบัญชี (เก็บผูกกับ user id หรือถูกล้างเมื่อออก)

- [ ] ทริปที่สร้างจาก preset ยังคงเก็บพิกัดจุดเริ่ม/ปลายทางที่ server ตามกฎเดิมของ US-5 (ไม่เปลี่ยนสิ่งที่ server ได้รับ) และใช้พิกัดจุดเริ่มที่ผู้ใช้เลือกเองเท่านั้น
- [ ] มีฟังก์ชันเทียบปลายทางของทริปกับ preset "บ้าน" บนเครื่อง สำหรับ label/ข้อความถึงที่หมาย 2 แบบ (US-31, US-40)

**Dependencies:** US-5, US-15; สมมติฐานข้อ 2 (PM ยืนยันแล้ว, Q2; การซิงก์ server ต้องผ่านฝ่ายกฎหมายก่อนเสมอ)

### US-39: การ์ดหน้าแรก "กำลังจะกลับบ้านใช่ไหม?" และปุ่ม "หาเพื่อนกลับบ้าน" [P1]
As a ผู้ใช้ที่ตั้งสถานที่โปรดไว้แล้ว, I want สร้างทริปกลับบ้านด้วยการกดปุ่มเดียวจากหน้าแรก, so that หาเพื่อนได้เร็วโดยไม่ผ่าน wizard 3 ขั้น

## NFR

### การเข้าถึง (a11y)
- ทุกการกระทำที่ต้องลาก/ปัด/สไลด์มีทางเลือกแบบแตะ/กดค้าง/semantics action (US-31, US-35)
- ปุ่มและ target แตะขนาดตามแนวทางมาตรฐานของแพลตฟอร์ม; คอนทราสต์ข้อความ/สีเขียว geofence ผ่านเกณฑ์; ไม่พึ่งสีอย่างเดียว; emoji มีข้อความทางเลือก
- ลำดับ focus และการอ่านของ screen reader ถูกต้องเมื่อ sheet เปลี่ยนระดับ, โมดอล Match Moment, snackbar undo (ประกาศและเข้าถึงได้ภายใน 5 วินาที; ผู้ใช้ screen reader ต้องมีเวลาพอ จึงแนะนำ snackbar ไม่หายเมื่อมี focus)
- รองรับ reduce motion, ตัวอักษรขนาดใหญ่ (text scale) โดยไม่ทำให้ SOS/สไลเดอร์ถูกตัด/บัง; หน้าจอแคบ 390 px ใช้งานได้ (ตามที่ตรวจในรอบก่อน)

### ประสิทธิภาพ
- การลาก sheet และการเลื่อนแผนที่ลื่น ไม่ถ่วงจากการอัปเดตตำแหน่งสด (ตาม US-23); การคำนวณ geofence เบา ไม่เพิ่มความถี่ GPS/การเรียก routing เกิน rate limit เดิม
- การ์ดถัดไป prefetch; เวลาแสดงการ์ดใบแรกหลังกดสร้างทริปอยู่ในเกณฑ์เดียวกับการค้นหาเดิม; ไม่เพิ่มการเรียก `find_matches` ที่ทำให้ชน rate limit
- ค่ารวมคะแนน (US-36) ไม่ทำให้ `find_matches` ช้ากว่ากรอบเดิมอย่างมีนัยสำคัญ

### ความเป็นส่วนตัว / PDPA
- ที่อยู่บ้าน/จุดเริ่มประจำเป็นข้อมูลอ่อนไหว: เก็บในเครื่องเท่านั้น ล้างเมื่อออกจากระบบ/ลบบัญชี ไม่เข้า log (US-38); การเทียบ "ปลายทาง = บ้าน" ทำบนเครื่อง ไม่ส่ง server
- geofence คำนวณบนเครื่อง ไม่ส่งไป server; Driver ไม่ได้ปลายทางของ Rider; deep link นำทางส่งเฉพาะพิกัดที่ผู้ใช้เห็นอยู่แล้ว (US-24)
- การ์ด deck ไม่เปิดเผยข้อมูลเกินผลค้นหาเดิม; ค่ารวมคะแนนไม่เปิดเผยตัวตนผู้รีวิว (US-36); การข้ามไม่ถูกบันทึกเป็นข้อมูลที่อีกฝ่ายเห็น
- ไม่เก็บข้อมูลพฤติกรรมการปัด (ปัดซ้าย/ขวา) เพื่อทำโปรไฟล์ผู้ใช้ นอกเหนือจากคำขอจับคู่ที่ส่งจริง (สมมติฐาน)

### ความปลอดภัย / ความถูกต้อง
- SOS ทุกระดับ (US-30); สถานะทริปเปลี่ยนได้เฉพาะตามกฎ backend เดิม; การส่งคำขอบังคับเพดาน/throttle ที่ server ไม่ใช่แค่ UI
- ป้องกันการเรียกซ้ำ (double submit) ของสไลเดอร์, ปุ่มชวน, และปุ่ม "หาเพื่อนกลับบ้าน"

## Edge cases ที่ควรพิจารณา
- ปัดขวาเมื่อคำขอค้างเต็มเพดาน, เมื่อครบ throttle, เมื่อเครือข่ายหลุด, เมื่อทริปของอีกฝ่ายหมดอายุ/ถูกจับคู่ไปแล้วระหว่างดูการ์ด
- ส่ง-undo รัว ๆ: คำขอที่ undo ไม่นับเพดานแต่นับ throttle จึงอาจชน throttle; ต้องมีข้อความไทยชัดเจน
- undo ช้าเกินไปหรือหลังอีกฝ่ายตอบรับแล้ว (เกิดการแข่งกัน): undo ต้องไม่ยกเลิกการจับคู่ที่ตอบรับแล้ว; แจ้งข้อความสุภาพ
- สไลด์ "ขึ้นรถแล้ว" ก่อนเงื่อนไขครบ (ทริปยังไม่กำลังเดินทาง): ต้องถูกปฏิเสธที่ backend และ UI แจ้งสาเหตุ; สไลด์ "ถึงแล้ว" ขณะออฟไลน์: แจ้งไม่สำเร็จ ไม่แสดงว่าจบทริป
- Driver กดสไลด์ถึงแล้ว ขณะ Rider ยังนั่งอยู่ (US-12): Rider ยังเห็นทริปกำลังเดินทาง มี SOS ใช้ได้
- ตำแหน่ง GPS แกว่งรอบขอบ 150 ม.; ไม่มีสิทธิ์ตำแหน่ง; อยู่ในอาคาร/ตำแหน่งไม่แม่น
- การเทียบ "ปลายทาง = บ้าน" คลาดเคลื่อนใกล้ขอบรัศมี: ใช้ข้อความ/label ทั่วไป "ที่หมาย" เป็น fallback ปลอดภัย
- เวลาปัจจุบันเลย 18:00 แล้ว: ตัวเลือกเวลาเหลือ "ตอนนี้เลย" + ช่วงถัดไปที่ปัดขึ้น 30 นาที ให้ครบอย่างน้อย 3 ตัวเลือก
- sheet ถูกลากไประดับอื่นขณะสไลด์อยู่ครึ่งทาง; แป้นพิมพ์แชทเปิดแล้ว SOS/สไลเดอร์ถูกบัง; หมุนจอ; text scale ใหญ่
- preset เดียวกันของ "บ้าน" และ "จุดเริ่ม" (พิกัดเหมือนกัน หรือใกล้กันมาก): ไม่ให้สร้างทริปที่จุดเริ่มเท่าปลายทาง; ตามกฎ validation เดิม
- ผู้ใช้มีทริปที่ใช้งานอยู่แล้ว กดปุ่ม 1 แตะ: ปฏิเสธพร้อมพาไปทริปเดิม; ผู้ใช้สลับบทบาทระหว่างสร้าง; Driver ยกเลิกลงทะเบียนแล้วแต่สวิตช์จำค่า "ขับรถเอง"
- ล้างข้อมูลเครื่อง/เปลี่ยนเครื่อง: preset หาย; ออกจากระบบแล้ว preset ต้องหาย; ลบบัญชี
- Driver รับได้ 1 คน: Driver ที่มีคำขอที่ตอบรับแล้ว ไม่ควรถูกเสนอเป็นการ์ดว่างให้คนอื่น (ตามกฎ 1 คู่ต่อทริปเดิม)
- การ์ดที่ไม่มีค่ารวมคะแนน/ไม่มีป้ายสถาบัน: layout ยังสมบูรณ์
- มีเฉพาะการ์ดของตัวเอง (สลับบทบาท) ไม่แสดงตัวเอง
- โหมดเดโม/ไม่มี Supabase ทำงานได้ตามเดิม

## คำถามเปิดสำหรับ PM
ปิดครบทั้ง 10 ข้อแล้ว (PM ตัดสิน ดู `docs/tasks-round6.md` หัวข้อ "คำตัดสิน PM (Q1-Q10)"):
- Q1 (ปิดแล้ว): คนขับมาถึงจุดรับ = ปุ่มเดียว "ถึงจุดรับแล้ว" ส่งข้อความสำเร็จรูปในแชทเดิม + แจ้งเตือนในแอป/local notification ฝั่ง Rider; ไม่มีสถานะทริปใหม่/DB ใหม่; throttle 1 ครั้ง/นาที (US-33, สมมติฐานข้อ 7)
- Q2 (ปิดแล้ว): preset เก็บในเครื่องเท่านั้น (secure storage ผูก user id) ล้างเมื่อออกจากระบบ/ลบบัญชี; ซิงก์ server = นอกรอบนี้ ต้องผ่านกฎหมายก่อนเสมอ (US-38, สมมติฐานข้อ 2)
- Q3 (ปิดแล้ว): การ์ด deck ใช้ตัวอักษรย่อ + ชื่อเล่น; รูปโปรไฟล์แสดงหลังจับคู่ตอบรับเท่านั้น คง US-22; **ต่างจากร่างผู้ใช้โดยตั้งใจ** ต้องแจ้งผู้ใช้ (US-34, สมมติฐานข้อ 15)
- Q4 (ปิดแล้ว): เก็บหน้ารายการ nearby เดิมเป็นมุมมองทางเลือก (ปุ่มสลับ deck/รายการ) (US-34)
- Q5 (ปิดแล้ว): ข้อความ/label ถึงที่หมาย 2 แบบ: "ถึงบ้านปลอดภัยแล้ว" เมื่อปลายทางตรง preset บ้าน, มิฉะนั้น "ถึงที่หมายปลอดภัยแล้ว" (US-31, US-40)
- Q6 (ปิดแล้ว): ส่งทันทีแล้ว undo 5 วินาที = ยกเลิกคำขอ pending; ไม่นับเพดานคำขอค้าง แต่นับ throttle; ห้ามยกเลิกคู่ที่ตอบรับแล้ว; ปุ่ม "เลิกชวน" ปิดระหว่างรอผลส่ง (US-35)
- Q7 (ปิดแล้ว): ขยาย `find_matches` (P1, /db-architect) คืนค่ารวมไม่ระบุตัวตน ควบคุมด้วย `review.show_in_search` รีวิวเปิดเผย ≥ 3 ห้ามคืน user id; ถ้า DB ไม่ทันเลื่อนเฉพาะ US-36 (US-36, สมมติฐานข้อ 10)
- Q8 (ปิดแล้ว): ตัวเลือกเวลาค่าคงที่ "ตอนนี้เลย" + 17:30 + 18:00; ตัดค่าที่ผ่านแล้ว; เหลือ < 3 เติมช่วงถัดไปปัดขึ้น 30 นาที; ไม่เรียนรู้พฤติกรรม (US-39)
- Q9 (ปิดแล้ว): 1 แตะเฉพาะ car (Rider/Driver); Peer ใช้ wizard เดิม (US-39)
- Q10 (ปิดแล้ว): ปุ่มนำทางภายนอกที่ Half ใช้กติกา US-24 เดิมทั้งหมด (รวม dialog แจ้งครั้งแรก) (US-29)

## Out of Scope (รอบ 6)
- การออกแบบ UI/แอนิเมชัน/ภาพ, การเขียนโค้ด, การเลือกเทคโนโลยี (หน้าที่แผนกอื่น)
- การเก็บ preset ที่ server / ซิงก์ข้ามอุปกรณ์; แนะนำสถานที่โปรดอัตโนมัติจากประวัติการเดินทาง
- รูปโปรไฟล์บนการ์ด deck (Q3; ต้องเปลี่ยนกฎ US-22 + ผ่านฝ่ายกฎหมายก่อน)
- 1 แตะสำหรับทริป Peer (Q9)
- ปุ่ม "ไม่ชอบ/ซ่อนผู้ใช้ถาวร" บนการ์ด, การบล็อกจากการ์ด, ระบบแนะนำแบบเรียนรู้จากการปัด
- สถานะทริปใหม่, RPC ใหม่ (ยกเว้นการขยาย `find_matches` ของ US-36), การแก้ RLS, การแก้ state machine
- ค้างรอบ 5 ที่ไม่รวม: จุดลงสาธารณะ (US-24 P1), รายการเลี้ยว turn-by-turn, การ deploy ฟังก์ชัน purge, US-25 (ตรวจรถ/ใบขับขี่), เลเยอร์แผนที่ P2, ตัวตัดรูป S-36
- การนำทางด้วยเสียง, push notification, หลายภาษา/ธีมมืด (PR-2, PR-9, PR-10 ตามเดิม)
- การใช้ SwipeToConfirmSlider กับ SOS/ยกเลิก/รายงาน/ลบ
- geofence ที่กระตุ้นสถานะอัตโนมัติ (เช่น auto-arrive)
- จำนวนที่นั่งมากกว่า 1 ต่อ Driver
