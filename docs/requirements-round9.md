## สมมติฐาน (ต้องระบุให้ PM ตัดสินใจ — ห้ามให้โปรแกรมเมอร์เดาเอง)

### สมมติฐาน A (สำคัญ — บล็อก US-1): โมเดลข้อมูลปัจจุบันไม่มีรูปภาพผู้ใช้เลย ไม่ใช่แค่ "รูปเดียว"
ตรวจสอบ `lib/features/matching/domain/match_models.dart` แล้วพบว่า `MatchCandidate` **ไม่มีฟิลด์รูปภาพใดๆ เลย** (ไม่มี `photoUrl`/`avatarUrl`/`imageUrl`) ทั้งใน matching, profile repository, และ demo data — ค้นทั้งโปรเจกต์ไม่พบการอ้างอิง photo URL ที่มาจาก backend เลยแม้แต่จุดเดียว
- **ผลกระทบ:** ask #1 (Tinder-style card) ต้องการ "รูปที่ 1 โปรไฟล์, รูปที่ 2 รถ/บรรยากาศ, รูปที่ 3 mini route snapshot" ซึ่งเป็น **3 รูปต่อผู้ใช้** แต่ระบบปัจจุบันไม่มี "รูปแม้แต่รูปเดียว" ต่อผู้ใช้ในโมเดลข้อมูล/DB ที่ UI อ่านได้
- **สมมติฐานที่ใช้เขียน requirement รอบนี้:** เนื่องจากนี่คือรอบ UI/UX-only ไม่แตะ schema/backend จึงตั้งสมมติฐานว่า **รอบนี้ทำเฉพาะ UI/placeholder** — ทุกช่อง "รูปโปรไฟล์"/"รูปรถ" ให้ใช้ fallback แบบถาวร (ไม่ใช่ fallback ชั่วคราวตอน error) คือ vector avatar เริ่มต้น (initial ตัวอักษรชื่อ) และ vector รถ 3D มินิมอล ตามที่ระบุไว้ใน spec เดิมสำหรับ "รูปรถ" อยู่แล้ว ส่วน "mini route snapshot" (รูปที่ 3) ให้ใช้ static map snapshot ที่ render จากพิกัด origin/dest ที่มีอยู่แล้วในระบบ (ไม่ใช่รูปถ่ายจริง) — จึงไม่ต้องพึ่งฟิลด์รูปใหม่จาก backend
- **คำถามเปิดสำหรับ PM/Architect:** ต้องตัดสินใจว่าจะเพิ่ม photo upload/storage feature (schema ใหม่ + storage bucket) ในรอบถัดไปหรือไม่ — ถ้าไม่ทำ ระบบการ์ดจะเป็น "vector/placeholder-only" ถาวร ไม่ใช่รูปถ่ายจริงของผู้ใช้ ซึ่งอาจไม่ตรงกับ vision ของ "รูปภาพเต็มจอ" ที่ตั้งใจไว้ในระยะยาว — **ประเด็นนี้ต้องถูกยกไปตัดสินใจนอกรอบนี้ ไม่ใช่ให้โปรแกรมเมอร์เดาเอง**

### สมมติฐาน B: ขอบเขตของ "ตัดระบบยืนยันสถาบัน/มหาวิทยาลัย" คือชั้น UI/label เท่านั้น
ตรวจสอบพบว่า badge kind `organization` (มาจาก `verifications` table ผ่าน `org_domains`, ดู `lib/features/profile/data/supabase_profile_repository.dart:105-107` และ `lib/features/profile/domain/profile_repository.dart:31`) คือกลไกที่ทำหน้าที่ "ยืนยันสถาบัน/องค์กร" ในปัจจุบัน (เช่น ยืนยันด้วยอีเมลโดเมนมหาวิทยาลัย/บริษัท)
- **สมมติฐานที่ใช้:** เนื่องจากรอบนี้เป็น UI-only ไม่แตะ backend/schema — "ตัดออกทั้งหมด" หมายถึง **ตัดการแสดงผลใน UI ทุกจุด** (การ์ดจับคู่, โปรไฟล์) ไม่แสดง badge/label `organization` อีกต่อไป และไม่แสดง `orgName` แม้ backend จะยังส่งข้อมูลนี้มาอยู่ก็ตาม — logic การเก็บ/คำนวณ badge ฝั่ง backend ยังคงอยู่เหมือนเดิม (เพียงแต่ UI เลือกไม่แสดง)
- **คำถามเปิดสำหรับ PM:** ต้องการ "ตัดทิ้งถาวร" ถึงระดับลบ flow การยืนยันสถาบันออกจากหน้าจอยืนยันตัวตน (ถ้ามี) ด้วยหรือไม่ หรือแค่ไม่แสดงผลใน badge/การ์ด — รอบนี้ถือว่าเป็นอย่างหลัง (ไม่แสดงผลเท่านั้น) เพราะเป็นรอบ UI-only; ถ้าต้องการลบ flow การสมัคร/ยืนยันสถาบันทั้งหมดจริง (รวม UI หน้ากรอกอีเมลองค์กร ถ้ามี) ต้องแจ้งเป็นงานแยกที่ชัดเจนกว่านี้

### สมมติฐาน C: "Global Verified" badge คือการรวม badge kind `email` และ `phone` เดิม ไม่ใช่ badge ใหม่จาก backend
เพื่อไม่ให้ต้องเพิ่ม field ใหม่ สมมติฐานคือ: ผู้ใช้ที่มี badge `email` และ/หรือ `phone` (อย่างน้อย 1 อย่าง, ไม่นับ `organization`) จาก `parseBadges()` เดิม จะถูกแสดงเป็นป้ายเดียวรวม "✓ ยืนยันตัวตนแล้ว" สีฟ้าอ่อนใน UI ใหม่ แทนที่จะแสดงแยกทีละ badge เหมือนเดิม — ไม่มีการเพิ่ม field/logic ฝั่ง backend

### สมมติฐาน D: dark mode ของหน้าที่ overhaul ต้องสอดคล้องกับ 4 ธีมเดิม
ทุกหน้าที่ถูกปรับใน US-1 ถึง US-5 ต้องใช้งานได้ถูกต้องทั้ง 4 ชุดสี (`rider` / `driver` / `riderDark` / `driverDark`) ตาม `lib/core/theme/tone.dart` ที่มีอยู่แล้วจาก round 7 — ไม่ hardcode สีขาว/ดำแบบตายตัวในจุดที่ควรเปลี่ยนตามธีม (เช่น gradient ดำโปร่งแสงบนการ์ดรูปภาพใน US-1 ยังคงใช้ดำ/ขาวได้เพราะอยู่บนรูปภาพเสมอ แต่พื้นหลัง #F8F9FC ของ US-2/3/4/5 ต้องมี dark-mode equivalent ที่นิยามไว้แล้วหรือกำหนดใหม่ให้สอดคล้อง)

## User Stories

### US-1: Tinder-Style Commute Card Deck สำหรับหน้าจับคู่เพื่อนร่วมทาง
As a ผู้ใช้ที่กำลังมองหาเพื่อนร่วมทาง,
I want เห็นการ์ดผู้สมัคร/คนขับแบบรูปภาพเต็มจอ ปัดซ้าย-ขวาได้แบบ Tinder พร้อมข้อมูลสำคัญอ่านง่าย,
so that ฉันตัดสินใจเลือก/ข้ามคนร่วมทางได้เร็วและรู้สึกเหมือนแอปไลฟ์สไตล์สมัยใหม่ ไม่ใช่ฟอร์มราชการ

**ไฟล์เป้าหมาย:** `lib/features/matching/presentation/commute_card_deck.dart` และคอมโพเนนต์ย่อยที่เกี่ยวข้อง

**Acceptance Criteria:**
- [ ] การ์ดมีรูปภาพ/vector เต็มพื้นที่ 80-85% ของการ์ด มุมโค้งแบบ squircle รัศมี 24dp (ใช้ `AppShape`/`AppRadius` ที่มีอยู่แล้ว ไม่สร้างระบบมุมมนใหม่)
- [ ] ด้านบนการ์ดมี story indicator bar (แถบขีดแนวนอนสไตล์ Instagram) จำนวนขีด = จำนวนภาพที่มีจริงในการ์ดนั้น (ไม่ fix 3 เสมอ); แตะครึ่งซ้าย/ขวาของการ์ดสลับภาพก่อนหน้า/ถัดไปได้ ไม่ไปกระทบ gesture ปัดซ้าย-ขวาเพื่อ skip/like เดิม
- [ ] ภาพที่ 1 = รูปโปรไฟล์ (หรือ vector avatar ตัวอักษรชื่อ ถ้าไม่มีรูปจริงตามสมมติฐาน A), ภาพที่ 2 = รูปรถ/บรรยากาศในรถ (หรือ vector รถ 3D มินิมอล ถ้าไม่มีรูปจริง), ภาพที่ 3 = mini route snapshot (static map แสดง origin→dest ที่มีอยู่แล้วในข้อมูล)
- [ ] กรณีเป็นทริปโหมด peer (ไม่มี role driver/rider ตาม `MatchCandidate.role == null`) หรือ candidate ที่เป็น rider (ไม่มีข้อมูลรถ) ต้องไม่แสดงภาพที่ 2 หรือแสดง fallback ที่เหมาะสมโดยไม่ error/ว่างเปล่า
- [ ] Gradient ดำโปร่งแสง (ประมาณ 35% opacity) อยู่ด้านล่างการ์ด ตัวอักษรสีขาว อ่านชัดเจนบนพื้นหลังทุกแบบ (ทดสอบกับรูป/vector ที่มีทั้งโทนสว่างและมืด) โดยไม่มีกรอบกล่อง/พื้นหลังทึบซ้อนบนข้อความ
- [ ] บรรทัดข้อมูลแสดงครบตามลำดับ: (1) ชื่อเล่น + อายุ (ถ้ามีข้อมูลอายุในระบบ; ถ้าไม่มีให้ซ่อนส่วนอายุโดยไม่ทำให้ layout เพี้ยน) + ป้าย "✓ ยืนยันตัวตนแล้ว" ตามสมมติฐาน C + คะแนนรีวิว "★ x.x (n ทริป)" เฉพาะเมื่อ `MatchCandidate.hasRating == true` เท่านั้น (ถ้า `hasRating == false` ต้องไม่แสดงตัวเลขคะแนน/ทริปปลอมหรือ 0); (2) ข้อมูลรถเฉพาะกรณี `role == TripRole.driver`; (3) ต้นทาง➜ปลายทาง + เวลา + `overlapPct`; (4) แท็ก vibe จาก `vibeTags` เป็น frosted-glass chip โปร่งแสง — ถ้า `vibeTags` ว่าง ต้องซ่อนแถวนี้ทั้งแถว ไม่แสดงกล่องว่าง
- [ ] ปุ่มลอยวงกลม 3 ปุ่ม: ✕ ข้าม, 💚 ชวนกลับด้วยกัน (ขนาดใหญ่เด่นกว่าปุ่มอื่นอย่างชัดเจน), ℹ️ เปิด bottom sheet รายละเอียด — ทั้ง 3 ปุ่มยังคงเรียก action เดิม (skip / request match / view detail) ที่มีอยู่แล้วในโค้ด โดยไม่เปลี่ยน business logic การจับคู่
- [ ] ป้าย "✓ ยืนยันตัวตนแล้ว" **ต้องไม่แสดง badge/ข้อความที่เกี่ยวกับสถาบัน/มหาวิทยาลัย/องค์กร** (`kind == 'organization'`) อีกต่อไป ตามสมมติฐาน B
- [ ] แสดงผลถูกต้องครบทั้ง 4 ธีม (rider/driver × light/dark) ตามสมมติฐาน D
- [ ] `flutter analyze` และ `flutter test` เดิมที่เกี่ยวข้องกับ matching ต้องผ่าน ไม่มี regression ด้าน logic การจับคู่/ปัด/ส่งคำขอ

### US-2: ยกเครื่องหน้าแรก (Home Screen & Map Zoom Level)
As a ผู้ใช้ที่เปิดแอปครั้งแรกในแต่ละวัน,
I want เห็นแผนที่ซูมเข้าใกล้ตำแหน่งจริงของตัวเองทันที พร้อม UI ค้นหาที่ลอยเรียบไม่เทอะทะ,
so that ฉันรู้สึกว่าแอปเข้าใจตำแหน่งฉันจริงๆ และเริ่มหาเพื่อนร่วมทางได้เร็วโดยไม่ต้อง pinch-zoom เอง

**ไฟล์เป้าหมาย:** `lib/features/home/presentation/home_tab.dart`, `quick_home_card.dart`, `lib/core/map/app_map.dart`

**Acceptance Criteria:**
- [ ] เมื่อเปิดหน้าแรกและ location permission ได้รับอนุญาตแล้ว แผนที่ต้อง animate camera ไปยังตำแหน่ง GPS ปัจจุบันที่ zoom level 15.0-15.5 (ไม่ใช่ระดับจังหวัด ~10-11 แบบเดิม) ด้วย transition ที่นุ่มนวล (ไม่กระโดดทันที)
- [ ] มีจุดสีฟ้าพร้อม animation กระพริบ/เต้น (pulse) แสดง "ตำแหน่งของคุณ" ที่ตำแหน่ง GPS จริง
- [ ] กรณี location permission ถูกปฏิเสธหรือไม่สามารถอ่านตำแหน่งได้ ต้องมี fallback zoom level ที่สมเหตุสมผล (ระบุ default) และไม่ error/ค้าง — พฤติกรรม error handling เดิม (ถ้ามี) ต้องยังทำงาน ไม่ regression กับ BUG-2 (round 8, timeout การขอตำแหน่ง) ที่เพิ่งแก้ไป
- [ ] มีปุ่มลอยวงกลม 🧭 recenter อยู่มุมขวาล่างของแผนที่ กดแล้ว camera กลับไปที่ตำแหน่งผู้ใช้ปัจจุบันที่ zoom level เดิม (15.0-15.5)
- [ ] แผนที่แสดงเต็มจอเป็นพื้นหลัง (ไม่มีกรอบ/การ์ดครอบแผนที่อีกต่อไป)
- [ ] Header ลอยด้านบน: ซ้ายบนแสดง "สวัสดี, [ชื่อเล่น]" แบบไม่มีพื้นหลังทึบ/กล่องขาว (ข้อความอ่านง่ายบนแผนที่ทุกโทนสี); ขวาบนมีสวิตช์แคปซูล [🚗 คนขับ | 🎒 คนนั่ง] ที่ยังคงสลับ role state เดิมของระบบ (ไม่เปลี่ยน logic การสลับโหมด)
- [ ] การ์ดค้นหาด้านล่างเป็นการ์ดขาวนวลลอย เงาจาง (ambient shadow) ไร้เส้นขอบเทา และ **ต้องไม่มีกล่องซ้อนกล่อง** (ลบโครงสร้างกล่องเขียวซ้อนกล่องฟ้า + ปุ่มเรียงแถวเดิมออกทั้งหมด) ประกอบด้วย: ช่องค้นหา placeholder "วันนี้กลับไหนดี?", ชิปทางลัด [🏠 บ้าน][🏢 ที่ทำงาน] ที่ยังคงเรียก action เดิม (ไปที่บ้าน/ที่ทำงานที่บันทึกไว้), ปุ่มหลักทรงแคปซูลข้อความ "หาเพื่อนร่วมทาง" ที่เรียก flow ค้นหาเดิม
- [ ] Regression: ทุก action เดิมบนหน้าแรก (ค้นหา, ไปหน้าสร้างทริป, สลับ role, ทางลัดบ้าน/ที่ทำงาน) ต้องยังทำงานถูกต้อง มีแค่ visual/layout ที่เปลี่ยน

## Out of Scope (รอบนี้)
- ไม่เพิ่ม schema/field ใหม่สำหรับรูปภาพผู้ใช้ (photo upload/storage) — ตามสมมติฐาน A, การ์ดจับคู่รอบนี้ใช้ vector/placeholder + route snapshot เท่านั้น ไม่ใช่รูปถ่ายจริงของผู้ใช้
- ไม่ลบ/แก้ไข backend logic ของระบบยืนยันสถาบัน/องค์กร (`verifications`/`org_domains`) — เป็นเพียงการซ่อนใน UI ตามสมมติฐาน B
- ไม่เปลี่ยนกฎ/สูตรคำนวณการจับคู่ (matching algorithm), การนับ unread message, หรือ business logic ของทริป/สถานะทริปใดๆ
- ไม่เพิ่ม third-party service หรือ API ใหม่ (การแปลงพิกัดเป็นชื่อสถานที่ใน US-4 ใช้กลไก reverse-geocode ที่มีอยู่แล้วในระบบเท่านั้น)
- ไม่ทำ CI/CD หรือ automated visual regression testing (โปรเจกต์นี้ไม่มี git repo และไม่มี CI infra ในปัจจุบัน)
- ไม่ครอบคลุมหน้าจออื่นนอกเหนือจาก 5 หน้า + design tokens ที่ระบุไว้ (เช่น หน้าสร้างทริป, หน้า login/onboarding) แม้จะมีสไตล์เก่าอยู่ก็ตาม — เก็บไว้รอบถัดไป
