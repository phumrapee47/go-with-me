## นิยามระดับความสำคัญ
[RECONSTRUCTED FROM: `docs/requirements-round6-ba.md:7` และ `docs/requirements-round7-ba.md:8` (ข้อความ verbatim ที่ยังไม่เสียหาย, ไม่ใช่การอนุมาน)]

**[แก้ไขหลังตรวจสอบเพิ่มเติม]** พบนิยามจริงที่ยังหลงเหลืออยู่ (restated ซ้ำเหมือนกันในสอง BA doc ของรอบหลัง ซึ่งเป็นรูปแบบมาตรฐานที่ทีมใช้อ้างอิงต่อเนื่องทุกรอบ ไม่ใช่นิยามเฉพาะรอบ 6-7):

> "ระดับความสำคัญ: P0 = ต้องมีก่อนปล่อย/ด้านความปลอดภัย, P1 = ควรมีในรอบนี้, P2 = ทำถ้ามีเวลา" (`docs/requirements-round6-ba.md:7`, ซ้ำคำต่อคำใน `docs/requirements-round7-ba.md:8`)

ถ้อยคำนี้น่าเชื่อถือกว่าการอนุมานในฉบับร่างแรกมาก เพราะเป็นข้อความที่ BA รอบหลัง ๆ คัดลอกมาใช้ซ้ำโดยตรง (แสดงว่าเป็นนิยามที่ยึดถือกันมาตั้งแต่ต้น ไม่ใช่นิยามใหม่ของรอบ 6-7 เท่านั้น) อย่างไรก็ตาม **ยังไม่ใช่ข้อความยืนยัน 100% ว่าเป็นคำต้นฉบับตัวอักษรต่อตัวอักษรของ `docs/requirements.md` รอบ 1** (อาจถูกสรุปใหม่เล็กน้อยตอนเขียน round6-ba) จึงยังคงจัดเป็น RECONSTRUCTED แต่ยกระดับความมั่นใจจาก "อนุมานล้วน" เป็น "อ้างอิงจากข้อความจริงที่หลงเหลือ":

- **P0**: ต้องมีก่อนปล่อยใช้งานจริง / เป็นเรื่องด้านความปลอดภัย
- **P1**: ควรมีในรอบนี้ (แต่ไม่ถึงกับบล็อกการปล่อยใช้งาน)
- **P2**: ทำถ้ามีเวลาเหลือ (ไม่ผูกมัดว่าจะทำในรอบนี้)

**ยังไม่พบ**: เกณฑ์ตัดสินที่ละเอียดกว่านี้สำหรับ item แบบ "P0 บางส่วน P1 บางส่วน" ที่ปรากฏหลายจุดในตารางสรุป (เช่น "US-4: P0 (รูปโปรไฟล์อัปโหลด P1...)") — ไม่มีกฎการแบ่งย่อยที่เป็นลายลักษณ์อักษรอยู่ที่ใดที่ค้นได้ สันนิษฐานว่าเป็นการแบ่งระดับ AC ย่อยภายใน story เดียวกันตามนิยามข้างต้น

## ข้อจำกัดจากโจทย์ (Constraints)
[RECONSTRUCTED FROM: หัวข้อ "บริบท" ที่ยังอยู่ (ด้านบน) + `docs/PROJECT_STATUS.md` (ทั้งไฟล์ ยังไม่เสียหาย) + `docs/design-db.md:3`, `docs/design-api.md:292/300` (อ้าง "free tier" ตรง ๆ) + รูปแบบข้อจำกัดที่ปรากฏซ้ำหลายจุดทั่วเอกสาร]

- Backend: Supabase project `gowithme` (`citzutjfivstryuquxnf`, org THAITRIP) — free tier (ยืนยันจาก `design-db.md:3` "Target: Supabase Postgres (free tier) + PostGIS" และ `design-api.md:292` "Supabase free tier")

  - ห้ามรันอะไรลง Supabase จริงโดยไม่ขออนุญาตทุกครั้ง แม้เป็นแค่การตรวจแบบ rollback
  - ต้องตรวจ SQL ก่อนรันจริงเสมอ (รันใน transaction ที่ rollback) และรันชุดทดสอบเก่าทั้งหมดควบคู่เสมอ
  - Concept แอป = "กลับบ้านใกล้กัน" ไม่ใช่บริการแบบ Grab/รับส่งทั่วไป — ทุกกฎจับคู่ใหม่ต้องตรวจสอบว่าไม่เบี่ยงกลับไปเป็นบริการรับส่งเชิงพาณิชย์
- ไม่มีการจัดการเงิน/ค่าโดยสารในแอปทุกรูปแบบในรอบนี้ (P2, ต้องผ่านฝ่ายกฎหมายก่อน)

**ยังไม่พบ**: ข้อความ "ข้อจำกัดจากโจทย์" ที่เป็นหัวข้อทางการในรูปแบบเดียวกับต้นฉบับ (เช่น ข้อจำกัดด้านกำหนดเวลาส่งมอบ/บุคลากร) — `PROJECT_STATUS.md` ยืนยัน "กฎการทำงาน" ซึ่งใกล้เคียงแต่ไม่ใช่สิ่งเดียวกับ "ข้อจำกัดจากโจทย์" อย่างแท้จริง (ข้อแรกคือกฎที่ทีมตกลงกันเองระหว่างทาง ข้อหลังคือข้อจำกัดที่มากับโจทย์ตั้งแต่ต้น) — ยังต้องให้ PM ยืนยัน

- R3-2: ระยะเบี่ยงจุดรับที่ยอมรับได้ตั้งค่าที่ config กลางจุดเดียว (`match.pickup_max_deviation_m`) เป็นการ "เตือน" เท่านั้น ไม่บล็อกการบันทึกจุดรับ — ค่าจริง = **500 เมตร** [แก้ไขหลังตรวจโค้ด: ยืนยันเป็นค่าคงที่จริงใน `lib/core/config/service_config.dart:47` (`PICKUP_MAX_DEVIATION_M`, default 500) และ `supabase/migrations/0006_driver_rider_roles.sql:29` ไม่ใช่ตัวเลขสมมติอีกต่อไป]
- R3-3: การไม่มาตามนัด (no-show) รายงานได้เฉพาะฝั่ง Driver รายงานว่า Rider ไม่มา ไม่มี timeout อัตโนมัติ ไม่มีบทลงโทษอัตโนมัติ เหตุผลเป็นข้อมูลภายใน (ไม่เปิดเผยให้ client อ่าน) [ยืนยันตรงกับโค้ด: `lib/features/matching/domain/match_repository.dart:54` "Driver only: ... (no timer, no penalty; reason is internal)"]
- R3-4: คำขอจับคู่ส่งได้ทั้งสองทิศทาง (Rider→Driver, Driver→Rider) แต่ตอบรับได้เฉพาะผู้รับที่มี role ตรงข้ามเท่านั้น

### คำตัดสินจากผู้ใช้ (รอบ 4 - ลงทะเบียนคนขับ / สลับบทบาท) (ไม่ใช่สมมติฐาน)
[RECONSTRUCTED FROM: design-roles.md §11 (หัวข้อย่อยบนสุด) + Changelog รอบ 4 ที่ยังอยู่] คำตัดสินหลักที่นำไป implement จริง:
- ทุกบัญชีที่สมัครใหม่เริ่มต้นเป็น Rider เท่านั้น ไม่มีทางเลือก role ตอนสมัคร
- การเป็น "คนขับ" ต้องผ่านขั้นตอนลงทะเบียน (กรอกข้อมูลรถ + รับรองตนเองว่ามีใบขับขี่ — ไม่เก็บเลข/รูปใบขับขี่จริงใน MVP) ดู US-19
- ลงทะเบียนแล้วมีผลทันที ไม่ต้องรอผู้ดูแลอนุมัติ และไม่มีหน้า admin สำหรับเพิกถอนสถานะคนขับ
- ยกเลิกการลงทะเบียนคนขับทำได้เมื่อไม่มีทริปคนขับที่ใช้งานอยู่/ไม่มีการจับคู่ตอบรับที่เป็นคนขับอยู่เท่านั้น ข้อมูลรถยังคงอยู่หลังยกเลิก (ไม่ลบทิ้ง)
- บัญชีที่ลงทะเบียนคนขับแล้วมี "บทบาทที่ใช้งานอยู่ (active role)" ที่สลับได้ระหว่าง Rider/Driver แบบแตะครั้งเดียว ซึ่งเป็นเพียงค่าเริ่มต้น/โทนของแอป ไม่ใช่ตัวตัดสิน role ของทริปที่สร้างไปแล้ว ดู US-20
- แอปมีโทนสี (ธีม) ต่างกันตามบทบาทที่ใช้งานอยู่ (Rider เดิม / Driver = โทนเข้มกว่า + amber)

### สมมติฐาน Driver/Rider (รอบ 3)
- สมมติฐาน: role เป็น "ต่อทริป" ไม่ใช่ต่อบัญชี (คนเดียวเป็น Driver ตอนเช้าและ Rider ตอนเย็นได้) และใช้เฉพาะทริป mode=car; โหมดเดิน/ขนส่งสาธารณะ/แท็กซี่ยังเป็น peer↔peer เหมือนเดิมและไม่มี role (รอบ 4: role ยังผูกกับทริป แต่ "สิทธิ์เลือก Driver" เป็นระดับบัญชี ต้องลงทะเบียนคนขับก่อน ดู US-19)
- [RECONSTRUCTED FROM: design-roles.md §1-2] ตามโครงสร้างตารางใน design-roles.md §1 อนุมานได้ว่าบรรทัดที่หายไปน่าจะระบุรายละเอียดเชิงเทคนิคเพิ่มเติม เช่น: ความเข้ากันได้ของ car คือ "Driver↔Rider เท่านั้น" (ไม่ใช่ Driver↔Driver หรือ Rider↔Rider), การจับคู่ตอบรับของ car จำกัด 1 คู่ต่อทริปเสมอ (ไม่ใช่สูงสุด 3 คนเหมือนโหมดอื่น), และ overlap ของ car คำนวณจาก "สัดส่วนเส้นทาง Rider ที่อยู่ในบัฟเฟอร์ของเส้นทาง Driver" ไม่ใช่สูตร overlap สมมาตรแบบโหมดอื่น — **ข้อความนี้เป็นการอนุมานจากกติกาที่ implement จริง ไม่ใช่ถ้อยคำต้นฉบับของบรรทัดที่หาย**

### สมมติฐาน ลงทะเบียนคนขับ / สลับบทบาท (รอบ 4)
[RECONSTRUCTED FROM: design-roles.md §11.1, §11.3] ส่วนที่หายไปบางส่วนก่อนบรรทัดที่รอดอยู่ น่าจะครอบคลุม:
- สมมติฐาน: "บทบาทที่ใช้งานอยู่" (active_role) เก็บระดับบัญชี ไม่ใช่ระดับอุปกรณ์ (ข้ามอุปกรณ์เห็นค่าเดียวกัน) ค่าเริ่มต้น = rider เสมอสำหรับบัญชีใหม่
- สมมติฐาน: การรับรองตนเอง (self-declaration) ผูกกับ "เวอร์ชันข้อความ" ที่ config ไว้กลางจุดเดียว (`driver.declaration_version`) เพื่อให้ฝ่ายกฎหมายแก้ถ้อยคำได้โดยไม่แก้โค้ด และบังคับให้ผู้ใช้ที่เคยรับรองเวอร์ชันเก่ารับรองใหม่หากเวอร์ชันเปลี่ยน (แอปเก่าที่ส่งเวอร์ชันเก่ากว่าปัจจุบันถูกปฏิเสธ) [ยืนยันตรงกับโค้ด: `lib/features/roles/domain/role_state.dart:9` ค่าคงที่ `driverDeclarationVersion = 'd1-draft'` ต้องตรงกับ config `driver.declaration_version` ฝั่ง server เป๊ะ]
- สมมติฐาน: ที่นั่งคนขับยังคงที่ = 1 คนเสมอ ไม่เปลี่ยนแปลงจากรอบ 3 แม้จะมีระบบลงทะเบียนคนขับเพิ่มเข้ามา
- สมมติฐาน: ข้อมูลรถหรือทริปคนขับที่เกิดก่อนรอบ 4 (เป็นข้อมูลทดสอบใน dev) ไม่ถือว่าลงทะเบียนคนขับ: บัญชีเหล่านั้นเป็น Rider จนกว่าจะลงทะเบียน (ข้อมูลรถเดิมเติมให้อัตโนมัติ) และทริปบทบาท Driver ของบัญชีที่ยังไม่ลงทะเบียนต้องไม่ปรากฏในค้นหาและไม่ถูกจับคู่ (ไม่ต้อง migrate เพราะยังไม่เปิดใช้จริง)

## User Stories

> หมายเหตุสำหรับ US-1 ถึง US-17: หัวข้อ/บรรทัด AC ที่มีคำว่า "รอบ" กำกับยังคงอยู่ในเอกสารเดิม และคัดลอกมาตรงนี้ **ไม่มีการแก้ไข**. บรรทัด "base AC" (ไม่มีคำว่า "รอบ" กำกับ) ที่สูญหายจะมีบันทึกสั้น ๆ ต่อท้ายหัวข้อว่า "พบร่องรอยอะไรบ้าง" แทนการแต่งข้อความเต็มขึ้นใหม่ เพื่อไม่ให้ดูเหมือนข้อความต้นฉบับ — ตามลำดับความสำคัญของงานนี้ที่ให้เน้น US-18/19/20 เป็นหลัก (รอบตรวจสอบที่ 2 นี้ไม่ได้แตะ US-1–US-17 เพิ่มเติม ตามขอบเขตที่ coordinator ระบุ)

### US-2: สมัครสมาชิกด้วยอีเมล + password [P0]
[RECONSTRUCTED FROM: Changelog รอบ 2/QA รอบ 1 ที่ยังอยู่ใน requirements.md] อ้างอิงจาก Changelog: มีการยืนยันอายุ 18+ (บังคับที่ server, self-declaration), สมัครสำเร็จนำไปหน้าตรวจอีเมล + ปุ่มส่งซ้ำ เข้าโปรไฟล์ได้หลังยืนยันอีเมลและ login, server ปฏิเสธการสร้างบัญชีที่ไม่ยืนยัน 18+/ไม่ยอมรับนโยบายเวอร์ชันปัจจุบันแม้เรียก API ตรง, เวลายืนยัน/ยอมรับเป็นค่าจาก server เท่านั้น
- [ ] (รอบ 4, P0) บัญชีที่สมัครใหม่ทุกบัญชีเป็น Rider เท่านั้น: ไม่มีขั้นตอน/ตัวเลือกเลือกบทบาทในการสมัคร และไม่มีการรับสถานะ "คนขับ" จากข้อมูลที่ส่งมาตอนสมัคร (server ตั้งเองเสมอ ดู US-19)

### US-3: เข้าสู่ระบบ / ออกจากระบบ / กู้รหัสผ่าน [P0]

### US-4: โปรไฟล์และการยืนยันตัวตน [P0/P1]
[RECONSTRUCTED FROM: Changelog "QA รอบ 1" ที่ยังอยู่] AC พื้นฐานตาม QA รอบ 1: (P0) ชื่อที่แสดง + ผู้ติดต่อฉุกเฉิน, (P0) avatar ตัวอักษรย่อทุกที่ที่แสดงผู้ใช้, (P1) อัปโหลด/เปลี่ยน/ลบรูปโปรไฟล์ (ไม่บังคับ; เห็นเฉพาะคู่ที่จับคู่แล้ว)
- [ ] (รอบ 3, P0) ข้อมูลรถของ Driver ไม่ถือเป็นส่วนของโปรไฟล์สาธารณะ: ไม่แสดงในโปรไฟล์ที่คู่ที่ยังไม่จับคู่เห็น (ดู US-17)
- [ ] (รอบ 4, P0) โปรไฟล์ของเจ้าของบัญชีแสดงบทบาทที่ตนมี ("คนนั่ง" เสมอ; "คนขับ" เมื่อลงทะเบียนแล้ว) และทางเข้าไป "ลงทะเบียนเป็นคนขับ" (เมื่อยังไม่ลงทะเบียน) หรือ "ยกเลิกการลงทะเบียนคนขับ" (เมื่อลงทะเบียนแล้ว) ตาม US-19
- [ ] (รอบ 4, P0) การที่บัญชีลงทะเบียนเป็นคนขับหรือไม่ ไม่ปรากฏในโปรไฟล์ที่คู่จับคู่/ผู้อื่นเห็นเป็นป้ายยืนยัน (ป้ายบอกบทบาทที่เห็นได้มีเฉพาะ role ของทริปนั้นตาม US-16); ห้ามใช้ป้ายที่สื่อว่าใบขับขี่ผ่านการตรวจแล้วจนกว่าจะมีการตรวจจริง (P1)

### US-5: สร้างทริป [P0]
[[เนื้อหาสูญหายบางส่วน — ไม่พบ base AC (ขั้นตอนสร้างทริปทั่วไปก่อนรอบ 3) ที่กู้คืนได้ชัดเจน]]
- [ ] (รอบ 3, P0; รอบ 4 ปรับ) เมื่อเลือกวิธีเดินทางเป็น car ต้องมี role ของทริปเป็น "คนขับ" หรือ "คนนั่ง" ก่อนบันทึก โดยแอปตั้งค่าเริ่มต้นตามบทบาทที่ใช้งานอยู่ (US-20) และผู้ใช้เปลี่ยนได้เฉพาะตัวเลือกที่ตนมีสิทธิ์ (ไม่มี role = บันทึกไม่ได้ และ server ปฏิเสธด้วย); โหมดอื่น (เดิน/รถสาธารณะ/แท็กซี่) ไม่มีการเลือก role และ server ปฏิเสธ role ที่แนบมากับโหมดที่ไม่ใช่ car
- [ ] (รอบ 3, P0) ไม่มีช่องกรอกจำนวนที่นั่ง: ทริปคนขับรับเพื่อนร่วมทางได้ 1 คนเสมอ และแสดงข้อความชัดเจนว่า "รับเพื่อนร่วมทางได้ 1 คน"
- [ ] (รอบ 3, P0; รอบ 4 ปรับ) ทริปบทบาท "คนขับ" สร้างได้เมื่อบัญชีลงทะเบียนเป็นคนขับแล้วเท่านั้น (ซึ่งหมายถึงมีข้อมูลรถครบตาม US-17/US-19) บังคับที่ backend: ถ้าบัญชียังไม่ลงทะเบียน server ปฏิเสธการสร้างทริป role คนขับแม้เรียก API ตรงหรือแก้ค่าฝั่งแอป พร้อมข้อความภาษาไทยชี้ทางไปลงทะเบียน; UI ไม่ให้เลือก "คนขับ" ได้ แต่เสนอทางไป "ลงทะเบียนเป็นคนขับ" โดยไม่เสียข้อมูลที่กรอกไว้ในฟอร์มสร้างทริป
- [ ] (รอบ 4, P0) ทริปบทบาท "คนนั่ง" สร้างได้ทุกบัญชี (ไม่ต้องลงทะเบียนอะไร) และเจ้าของบัญชีที่ลงทะเบียนคนขับแล้วสร้างทริปคนนั่งได้เสมอ
- [ ] (รอบ 3, P0) role ของทริปเปลี่ยนไม่ได้หลังสร้าง (แก้ไขทริปตาม US-9 AC6 แก้ role ไม่ได้; ต้องยกเลิกแล้วสร้างใหม่); ข้อจำกัด 1 ทริป "รอ/กำลังเดินทาง" ต่อผู้ใช้ยังใช้กับทริป car ทุก role (รอบ 4: นับรวมทั้งทริปคนขับและทริปคนนั่ง ผู้ใช้คนเดียวจึงไม่มีทั้งสองพร้อมกัน)

### US-6: ดูคนที่กำลังกลับในบริเวณใกล้เคียง / จับคู่ [P0]
[[เนื้อหาสูญหายบางส่วน — ไม่พบ base AC ทั่วไปของการค้นหา/จับคู่ก่อนรอบ 3]]
- [ ] (รอบ 3, P0) ทริป car ของ Driver เห็นเฉพาะทริป car ของ Rider ที่ผ่านเกณฑ์; ทริป car ของ Rider เห็นเฉพาะทริป car ของ Driver ที่ผ่านเกณฑ์; ทริป car ไม่เห็นทริปโหมดอื่น และทริปโหมดอื่นไม่เห็นทริป car (บังคับที่ backend ไม่ใช่แค่กรองใน UI)
- [ ] (รอบ 3, P0) ไม่แสดง Driver↔Driver และ Rider↔Rider ในผลค้นหาไม่ว่ากรณีใด
- [ ] (รอบ 3, P0) รายการที่เป็นทริปคนขับแสดง role "คนขับ" และ "รับได้ 1 คน"; รายการที่เป็นทริปคนนั่งแสดง role "คนนั่ง"; ก่อนตอบรับห้ามแสดงทะเบียน/รุ่น/สีรถ (ดู US-17) และตำแหน่งยังถูกทำให้คลาดเคลื่อนตามเดิม
- [ ] (รอบ 3, P0) ทริปคนขับที่มีการจับคู่ "ตอบรับแล้ว" อยู่ ไม่ปรากฏในผลค้นหาของใครทันที (ที่นั่งเต็ม); ทริปคนนั่งที่มีการจับคู่ตอบรับแล้วไม่ปรากฏในผลค้นหาของ Driver คนอื่นเช่นกัน; หากการจับคู่ถูกยกเลิกก่อนเริ่มทริป ทริปที่ยังรอออกเดินทางกลับมาปรากฏในผลค้นหาโดยอัตโนมัติ (ดู US-18)
- [ ] (รอบ 3, P0) เกณฑ์ระยะ/เวลา/overlap ใช้ค่าจาก config เดิมทั้งหมด (ไม่เพิ่มค่าใหม่สำหรับ car ยกเว้นระยะเบี่ยงจุดรับใน US-18)
- [ ] (รอบ 4, P0) ทริปบทบาทคนขับของบัญชีที่ไม่ได้ลงทะเบียนคนขับ (เช่น ข้อมูลเก่า/สถานะไม่สอดคล้อง) ไม่ปรากฏในผลค้นหาและถูกจับคู่ไม่ได้ (ป้องกันซ้อนที่ backend)
- [ ] (รอบ 4, P0) ผลค้นหาและการจับคู่ใช้ "role ของทริป" เท่านั้น ไม่ขึ้นกับบทบาทที่ใช้งานอยู่ของผู้ใช้ ณ ขณะนั้น (สลับบทบาทระหว่างที่มีทริปอยู่ไม่ทำให้ผลค้นหา/คำขอของทริปเดิมเปลี่ยน)

### US-7: ส่งคำขอและยอมรับการจับคู่ [P0]
[[เนื้อหาสูญหายบางส่วน — ไม่พบ base AC ทั่วไปก่อนรอบ 3]]
- [ ] หลังจับคู่ ฝ่ายใดฝ่ายหนึ่งเสนอจุดนัดพบได้ และอีกฝ่ายกดยืนยัน จึงถือว่าจุดนัดพบตกลงแล้ว (แก้ไข/เสนอใหม่ได้ก่อนเริ่มเดินทาง โดยต้องยืนยันใหม่) (รอบ 3: ใช้กับโหมดที่ไม่ใช่ car; สำหรับ car ผู้เสนอจุดรับคือ Driver ดู US-18)
- [ ] จับคู่ได้สูงสุด 3 คนต่อทริป (ค่าตั้งได้; สมมติฐาน) (รอบ 3: ใช้กับโหมดที่ไม่ใช่ car เท่านั้น; ทริป car จับคู่ตอบรับได้ 1 คนต่อทริปทุก role)
- [ ] (รอบ 3, P0) ทริป car: ผู้รับคำขอตอบรับได้เฉพาะเมื่อทริปของตนยังไม่มีการจับคู่ตอบรับ; ตอบรับคำขอที่สองต้องถูกปฏิเสธโดยระบบ (บังคับที่ backend) พร้อมข้อความภาษาไทยว่า "คุณมีคู่ร่วมทางแล้ว"
- [ ] (รอบ 3, P0) Rider ส่งคำขอถึง Driver หลายคนที่ยังรอตอบพร้อมกันได้ ภายในเพดาน max_pending เดิม; ส่งเกินเพดานถูกปฏิเสธด้วยข้อความชัดเจน
- [ ] (รอบ 3, P0) เมื่อการจับคู่ของ car ถูกตอบรับ คำขอที่ยังรอตอบอื่นทั้งหมดที่เกี่ยวกับทริปของ Driver หรือทริปของ Rider คู่นั้นถูกยกเลิกอัตโนมัติในธุรกรรมเดียวกัน; อีกฝ่ายของคำขอที่ถูกยกเลิกเห็นเพียงสถานะ "ปิดแล้ว" ไม่ระบุเหตุผลหรือตัวตนของคู่ที่ตอบรับ
- [ ] (รอบ 3, P0) กรณี race: Driver ตอบรับ Rider สองคนพร้อมกัน หรือ Rider ถูกตอบรับจาก Driver สองคนพร้อมกัน ต้องสำเร็จเพียง 1 การจับคู่ และอีกคำขอถูกปิดโดยไม่ทำให้เกิดการจับคู่ซ้อน (มีชุดทดสอบ)
- [ ] (รอบ 3, P0) ขณะตอบรับ Driver เห็นชัดว่าตอบรับแล้วจะรับเพื่อนร่วมทางได้ 1 คนและทริปจะหยุดปรากฏในการค้นหา (ข้อความยืนยันก่อนกดตอบรับ)
- [ ] (รอบ 3, P0) หน้าการจับคู่ของ Rider แสดงข้อมูลรถของ Driver (US-17) หลังตอบรับเท่านั้น

### US-8: แชทกับผู้ที่จับคู่ได้ [P0]
[[เนื้อหาสูญหายบางส่วน — ไม่พบ base AC ทั่วไปของแชท (เปิดแชทเมื่อไหร่, ฟีเจอร์พื้นฐาน) ก่อนรอบ 3]]
- [ ] (รอบ 3, P0) แชทของคู่ car ยังเป็น 1:1 ระหว่าง Driver กับ Rider เท่านั้น เปิดหลังตอบรับ; หัวแชทระบุ role ของคู่สนทนา ("คนขับ"/"คนนั่ง")
- [ ] (รอบ 3, P0) เมื่อการจับคู่ car ถูกยกเลิก (ไม่ว่าฝ่ายใด) หรือทริปฝ่ายใดยกเลิก/จบ แชทเป็นอ่านอย่างเดียวทันที (บังคับที่ backend) และคู่ที่ไม่ได้เป็นผู้ยกเลิกเห็นข้อความระบบที่เป็นกลาง เช่น "การจับคู่ถูกยกเลิก" โดยไม่ระบุเหตุผล
- [ ] (รอบ 3, P0) การเข้าถึงข้อมูลรถจากหน้าแชท/หน้าการจับคู่ของ Rider เป็นไปตามเงื่อนไขความเป็นส่วนตัวใน US-17 (หลังตอบรับและเฉพาะขณะการจับคู่ยังมีผล)

### US-9: จัดการทริป (เริ่ม / จบ / ยกเลิก) [P0]
[[เนื้อหาสูญหายบางส่วน — ไม่พบ base AC ของวงจรชีวิตทริปทั่วไป (สถานะ scheduled/in_progress/ended/cancelled) ก่อนรอบ 3]]
- [ ] (รอบ 3, P0) สถานะทริปของทั้ง Driver และ Rider ใช้ชุดสถานะเดิม (ไม่เพิ่มสถานะทริปใหม่); ขั้น "ขึ้นรถแล้ว" เป็นสถานะของการจับคู่ ไม่ใช่สถานะของทริป (ดู US-12)
- [ ] (รอบ 3, P0) การยกเลิกทริปที่มีการจับคู่ car ตอบรับแล้ว ทำให้การจับคู่สิ้นสุดและแจ้งอีกฝ่ายตาม US-18; ผลต่อทริปของอีกฝ่ายตาม US-18 (ทริปของอีกฝ่ายไม่ถูกยกเลิกไปด้วย)
- [ ] (รอบ 3, P0) การแก้ไขทริป (P1) ของทริป car ที่มีการจับคู่ตอบรับแล้ว ต้องถูกจำกัด: แก้เวลา/ปลายทางไม่ได้จนกว่าจะยกเลิกการจับคู่ (กันการเปลี่ยนเงื่อนไขหลังตกลงกัน) และแก้ role ไม่ได้เสมอ
- [ ] (รอบ 4, P0) รายการ "ทริปของฉัน" (ปัจจุบัน/ประวัติ) แสดง role ของแต่ละทริป car (ในฐานะคนขับ/คนนั่ง) เพื่อให้บัญชีที่ถือสองบทบาทแยกประวัติได้

### US-10: ปุ่ม SOS [P0]
[[เนื้อหาสูญหายบางส่วน — ไม่พบ base AC ของ SOS ทั่วไป (ผู้ติดต่อฉุกเฉิน, การโทร 191/1669, ข้อความเริ่มต้น) ก่อนรอบ 3]]
- [ ] (รอบ 3, P0, R3-1) SOS ของ Rider ในทริป car ที่มีการจับคู่ตอบรับแล้ว: ข้อความ/ลิงก์ที่ส่งให้ผู้ติดต่อฉุกเฉินต้องรวมชื่อที่แสดงของ Driver ที่จับคู่ และรวม "ทะเบียนรถของ Driver อย่างเดียว (ไม่มีรุ่น/สี)" เฉพาะเมื่อ Driver เปิดสวิตช์ยินยอมตาม US-17 เท่านั้น (บังคับที่ฝั่ง backend ที่สร้างข้อมูลสำหรับ SOS ไม่ใช่แค่ซ่อนใน UI); ถ้า Driver ไม่ยินยอม ข้อความไม่มีทะเบียนแต่ SOS ยังทำงานตามปกติและยังมีชื่อ Driver
- [ ] (รอบ 3, P0) SOS ของ Driver ในทริป car ที่มีการจับคู่ตอบรับแล้ว: ข้อความ/ลิงก์รวมทะเบียนรถของตนเองอย่างเดียว (ไม่มีรุ่น/สี) และชื่อที่แสดงของ Driver โดยไม่ผูกกับสวิตช์ยินยอม (เป็นข้อมูลของตนเอง); ไม่รวมชื่อ Rider ในข้อความของ Driver
- [ ] (รอบ 3, P0, R3-1) บันทึกเหตุการณ์ SOS ของ Rider เก็บ snapshot "ทะเบียนรถอย่างเดียว" ณ เวลากด เฉพาะกรณี Driver ยินยอม ณ เวลานั้น (ไม่เก็บรุ่น/สีของ Driver ในบันทึก SOS ของ Rider); เข้าถึงได้เฉพาะเจ้าของบัญชี/ผู้ดูแลตามกฎ SOS เดิม และใช้กฎเก็บ 90 วันเดิม; ไม่มีข้อมูลรถ (ยังไม่จับคู่/ไม่ใช่ car/ไม่ยินยอม) SOS ต้องทำงานตามเดิมโดยไม่ขวาง
- [ ] (รอบ 3, P0, R3-1) ผู้ใช้ (Rider) เห็นก่อนส่งว่าข้อความ SOS ที่จะส่งมี/ไม่มีทะเบียนรถของคนขับ โดยไม่ทำให้ขั้นตอน SOS ช้าหรือถูกขวาง
- [ ] (รอบ 3, P0) ปุ่ม SOS ใช้ได้ทั้งสองฝ่ายตลอดขณะทริป "กำลังเดินทาง" ไม่ขึ้นกับว่ากด "ขึ้นรถแล้ว" หรือยัง
- [ ] (รอบ 4, P0) ปุ่ม SOS ทำงานเหมือนกันทุกบทบาท/โทน และเนื้อหา SOS ตัดสินจาก role "ของทริป" ไม่ใช่บทบาทที่ใช้งานอยู่; การสลับบทบาทหรือการเป็นผู้ลงทะเบียนคนขับต้องไม่ขวางหรือหน่วง SOS

### US-11: แชร์ทริปให้คนไว้ใจ [P0]
[[เนื้อหาสูญหายบางส่วน — ไม่พบ base AC ของการแชร์ทริปทั่วไปก่อนรอบ 3]]
- [ ] (รอบ 3, P0, R3-1) การแชร์ทริปของ Rider ที่จับคู่กับ Driver แล้ว: ข้อความ/หน้าแชร์ต้องรวมชื่อที่แสดงของ Driver และรวม "ทะเบียนรถของ Driver อย่างเดียว (ไม่มีรุ่น/สี)" เฉพาะเมื่อ Driver เปิดสวิตช์ยินยอมตาม US-17 เท่านั้น (บังคับที่ backend ที่สร้างข้อความ/แถวแชร์ ไม่ใช่แค่ UI); ถ้า Driver ไม่ยินยอม การแชร์ทำงานตามปกติและยังมีชื่อ Driver แต่ไม่มีทะเบียน
- [ ] (รอบ 3, P0) การแชร์ทริปของ Driver รวมทะเบียนรถของตนเองอย่างเดียว (ไม่มีรุ่น/สี) และชื่อที่แสดงของ Driver โดยไม่ผูกกับสวิตช์ยินยอม (เป็นข้อมูลของตนเอง)
- [ ] (รอบ 3, P0, R3-1) ก่อนส่ง Rider เห็นชัดว่าข้อความ/ลิงก์จะมีหรือไม่มีทะเบียนรถของคนขับ (ตามสถานะสวิตช์ของ Driver) และเห็นคำเตือนเดิมว่าข้อความที่ส่งแล้วเรียกคืนไม่ได้; หน้าการจับคู่ของ Rider แสดงสถานะ "คนขับอนุญาต/ไม่อนุญาตให้ส่งทะเบียนไปกับการแชร์"
- [ ] (รอบ 3, P0, R3-1) ถ้า Driver ถอนความยินยอม ทะเบียนถูกตัดออกจากข้อมูลของลิงก์แชร์ backend ที่ยังใช้งานทันที และไม่ปรากฏในการแชร์/SOS ครั้งถัดไป; ข้อความ snapshot ที่ส่งไปแล้วเรียกคืนไม่ได้ (ตามกฎเดิม); ทะเบียนในลิงก์ backend หมดอายุ/ถูกเพิกถอนพร้อมลิงก์ และลิงก์ไม่เปิดเผยข้อมูลรถของทริปอื่น
- [ ] (รอบ 3, P0) ทริปที่ยังไม่มีการจับคู่ตอบรับ ไม่รวมข้อมูลรถของบุคคลอื่นใด (มีเฉพาะของ Driver เอง)
- [ ] (รอบ 4, P0) เนื้อหาแชร์ตัดสินจาก role "ของทริป" ไม่ใช่บทบาทที่ใช้งานอยู่; การยกเลิกลงทะเบียนคนขับ (ซึ่งทำได้เฉพาะเมื่อไม่มีทริปคนขับที่ใช้งาน) ไม่ทำให้ลิงก์แชร์ของทริปคนขับที่จบไปแล้วเปลี่ยนเนื้อหาย้อนหลังนอกจากตามกฎหมดอายุลิงก์เดิม

### US-12: ยืนยันการถึงจุดหมาย [P0]
[[เนื้อหาสูญหายบางส่วน — ไม่พบ base AC ของ "ถึงแล้ว" ทั่วไปก่อนรอบ 3]]
- [ ] (รอบ 3, P0) ทริป car ที่จับคู่แล้ว Rider มีปุ่ม "ขึ้นรถแล้ว" กดได้เมื่อทริปของทั้งสองฝ่ายอยู่ในสถานะ "กำลังเดินทาง" และมีการจับคู่ตอบรับ; ระบบบันทึกเวลากด, กดซ้ำไม่ได้, และแจ้ง Driver ว่า Rider ขึ้นรถแล้ว; ปุ่มนี้กดก่อนเงื่อนไขครบไม่ได้ (บังคับที่ backend)
- [ ] (รอบ 3, P0) ทั้ง Driver และ Rider กด "ถึงแล้ว" ของตนเองแยกกัน; การกดของฝ่ายหนึ่งทำให้ทริปฝั่งนั้นเสร็จสิ้น ปิดการแชร์ตำแหน่งสดของฝ่ายนั้น และแจ้งอีกฝ่ายว่า "อีกฝ่ายถึงแล้ว" แต่ไม่ทำให้ทริปของอีกฝ่ายเสร็จอัตโนมัติ [ยืนยันตรงกับโค้ด: `lib/features/trip/presentation/arrived_screen.dart:16-17` "Live sharing has already stopped (the trip is completed, so tracking and pushes are off)"]
- [ ] (รอบ 3, P0) การเตือน "ถึงแล้วหรือยัง" (P1) และการเสนอให้กดเมื่อใกล้ปลายทาง 300 ม. คำนวณจากปลายทางของแต่ละฝ่ายเอง (จุดลงของ Rider อาจต่างจากปลายทางของ Driver)
- [ ] (รอบ 3, P0) ถ้า Driver กด "ถึงแล้ว" ขณะ Rider ขึ้นรถแล้วแต่ยังไม่กดถึง Rider ยังคงเห็นทริปของตนกำลังเดินทาง มี SOS/แชร์ทริปใช้ได้ และได้รับการเตือนตามกฎเดิม
- [ ] (รอบ 3, P0) หลัง Rider กด "ขึ้นรถแล้ว" การแชร์ตำแหน่งสดของ Rider ให้ Driver หยุด แต่การแชร์ให้ผู้ติดต่อผ่านลิงก์ของ Rider ยังทำงานตามเดิม

### US-13: หน้าหลักและแผนที่ [P0]

### US-16: เลือกบทบาทคนขับ/คนนั่งและจับคู่แบบ Driver↔Rider [P0]
[[เนื้อหาสูญหายบางส่วน — ไม่พบ base AC เปิดหัวข้อ]]
- [ ] (P0; รอบ 4 ปรับ) role ของทริป car เป็น "คนขับ" หรือ "คนนั่ง" ตอนสร้างทริป (ดู US-5): "คนนั่ง" เลือกได้ทุกบัญชี ส่วน "คนขับ" เลือกได้เฉพาะบัญชีที่ลงทะเบียนเป็นคนขับแล้ว (US-19); บัญชีเดียวสร้างทริป car ต่างวัน/ต่างเวลาด้วย role ต่างกันได้ (role ผูกกับทริป ไม่ใช่ตัวตนถาวรของบัญชี)
- [ ] (รอบ 4, P0) ทริปบทบาทคนขับรับเพื่อนร่วมทางได้ "1 คนเท่านั้น" เสมอไม่ว่าบัญชีจะลงทะเบียนมากี่ครั้งหรือสลับบทบาทอย่างไร (ไม่มีการตั้งค่าที่นั่ง)
- [ ] (รอบ 4, P0) บัญชีที่ลงทะเบียนคนขับแล้วเป็นเจ้าของทริปคนขับในทริปหนึ่ง และเป็นคนนั่งในอีกทริปหนึ่ง "ต่างเวลากัน" ได้ (ทริปแรกต้องจบ/ยกเลิกก่อนสร้างทริปถัดไป ตาม US-5 AC6); ผู้ใช้คนเดียวไม่จับคู่กับตนเองไม่ว่าด้วย role ใด

### US-17: ข้อมูลรถของคนขับ (ทะเบียน รุ่น สี) [P0 / ตรวจสอบเอกสาร P1]
[[เนื้อหาสูญหายบางส่วน — ไม่พบ base AC เปิดหัวข้อ]]
- [ ] (P0; รอบ 4 ปรับ) ข้อมูลรถกรอกครั้งแรกในขั้นตอนลงทะเบียนคนขับ (US-19) และแก้ไขได้ภายหลังจากในแอป: ทะเบียน (บังคับ), รุ่น/ยี่ห้อ (บังคับ), สี (บังคับ); ต้องมีครบก่อนถือว่าลงทะเบียนคนขับและก่อนสร้างทริปคนขับ (US-5) และตรวจรูปแบบ/ความยาวเบื้องต้นฝั่ง server; การลบข้อมูลรถเป็นไปตาม AC "ลบข้อมูลรถไม่ได้ ..." ด้านล่าง **ความยาวที่อนุญาตจริง [แก้ไขหลังตรวจโค้ด — เดิมอ้างแค่ design-roles.md]: ทะเบียน ≤ 25 ตัวอักษร, รุ่น/ยี่ห้อ ≤ 60 ตัวอักษร, สี ≤ 30 ตัวอักษร, ห้าม control character, ห้ามว่างหลัง trim (ยืนยันตรงจาก `lib/features/vehicle/domain/vehicle.dart:6-8,73-88` — คอมเมนต์ในโค้ดระบุชัดว่า "Server limits (`vehicles` CHECKs...); the server re-validates")**
- [ ] (P0, R3-1) สวิตช์ยินยอมค่าเริ่มต้น "ปิด" และไม่บังคับเปิดเพื่อบันทึกข้อมูลรถ สร้างทริปคนขับ หรือถูกจับคู่ (รอบ 4: รวมถึงไม่บังคับเปิดเพื่อลงทะเบียนคนขับ); Driver เปิด/ปิดได้ทุกเมื่อจากหน้าข้อมูลรถ; เวลาที่ยินยอมถูกบันทึกโดย server (ไม่ใช่ค่าจากแอป) และการเปลี่ยนสถานะทำผ่านการเรียกฝั่ง server เท่านั้น [ยืนยัน: `lib/features/vehicle/domain/vehicle.dart:12-13` "Default false", คอมเมนต์ใน `vehicle.dart:19` "false = the plate is never forwarded with a Rider's share/SOS text"]
- [ ] (P0) เมื่อการจับคู่สิ้นสุดก่อนที่ Rider กด "ขึ้นรถแล้ว" (ยกเลิก/ปฏิเสธ/ปิดอัตโนมัติ/no-show) Rider เสียสิทธิ์เห็นข้อมูลรถทันที; เมื่อ Rider กด "ขึ้นรถแล้ว" แล้ว Rider ยังเห็นข้อมูลรถในแอปได้แม้การจับคู่สิ้นสุดเพราะ Driver จบทริป จนกว่าทริปของ Rider เองจะจบ/ยกเลิก หลังจากนั้นใช้กรอบ **24 ชั่วโมง** หลังทริปจบตามกฎเดิม แล้วอ่านไม่ได้ [แก้ไขหลังตรวจโค้ด: ยืนยันเป็นค่าคงที่จริงใน `supabase/migrations/0006_driver_rider_roles.sql:121-122` (`ta.ended_at > now() - interval '24 hours'` ของฟังก์ชัน `can_view_vehicle`) ไม่ใช่แค่ข้อความ design doc ที่ยัง "ไม่ได้ verify" อีกต่อไป — migration นี้ apply กับ Supabase จริงแล้วตาม `docs/PROJECT_STATUS.md:10`]; การเปลี่ยนนี้ไม่ขยายการส่งออกนอกแอป (สวิตช์ยินยอมยังคุมเฉพาะแชร์/SOS); ฝ่ายกฎหมายทบทวน
- [ ] (P0; รอบ 4 ปรับ) ลบข้อมูลรถไม่ได้ขณะ Driver มีทริปคนขับที่ยังรอออกเดินทางหรือกำลังเดินทาง หรือมีการจับคู่ตอบรับอยู่ (แสดงเหตุผลให้ยกเลิกทริปก่อน); และลบไม่ได้ขณะบัญชียังลงทะเบียนเป็นคนขับอยู่ (แสดงเหตุผลให้ยกเลิกการลงทะเบียนก่อน ตาม US-19); บัญชีที่ยกเลิกลงทะเบียนแล้วลบข้อมูลรถได้ [ยืนยัน: `lib/features/vehicle/domain/vehicle.dart:133` "`delete_my_vehicle`: GWM_VEHICLE_IN_USE while a Driver trip is active"]
- [ ] (P0; รอบ 4 เพิ่ม) ข้อมูลรถของบัญชีที่ยกเลิกลงทะเบียนคนขับแล้ว ยังคงไว้ 1 ชุดต่อบัญชี เห็นได้เฉพาะเจ้าของ (ไม่แสดงให้ใคร) และไม่ถูกใช้ในการแชร์/SOS/การจับคู่ใด ๆ จนกว่าจะลงทะเบียนใหม่
- [ ] (รอบ 3) เพิ่ม AC ลบข้อมูลรถไม่ได้ขณะมีทริปคนขับ scheduled/in_progress หรือ accepted match (Q-6) [[รายละเอียดเดิมสูญหาย รวมกับข้อข้างบน]]

### US-18: จุดรับ การขึ้นรถ และการยกเลิก/ไม่มาตามนัด (car) [P0 / บางส่วน P1]
[RECONSTRUCTED FROM: docs/design-roles.md §2-3/§5/§9-10; docs/dev-notes.md (T6.14, T6.16); **ตรวจยืนยันกับโค้ดจริงแล้ว**: `lib/features/matching/presentation/pickup_screen.dart`, `lib/features/matching/presentation/car_match_widgets.dart`, `lib/features/matching/domain/match_repository.dart`, `lib/features/trip/presentation/unified_ride_screen.dart`, `lib/core/config/service_config.dart`, `supabase/migrations/0006_driver_rider_roles.sql`]

**User story:** As a Driver หรือ Rider ของทริป car ที่จับคู่ตอบรับกันแล้ว, I want นัดจุดรับ ยืนยันการขึ้นรถ และยกเลิก/รายงานการไม่มาตามนัดได้อย่างชัดเจนและปลอดภัย, so that ทั้งสองฝ่ายมั่นใจว่าจะเจอกันถูกที่และมีทางออกเมื่อแผนเปลี่ยน

**Acceptance Criteria:**
- [ ] (P0) Driver เป็นผู้เสนอจุดรับคนแรกเสมอ; Rider เปิด proposal คนแรกไม่ได้ (ปฏิเสธด้วยรหัสข้อผิดพลาดเฉพาะ) แต่ counter-propose (เสนอจุดอื่นกลับ) ได้หลังจาก Driver เสนอแล้ว
- [ ] (P0) จุดรับที่เสนอต้องได้รับการ "ยืนยัน" จากอีกฝ่ายก่อนจึงถือว่าตกลงแล้ว (ผู้เสนอยืนยันเองไม่ได้) **[แก้ไขหลังตรวจโค้ด — เดิมเขียนกว้างเกินว่า "แก้ไขได้จนกว่าทริปใดทริปหนึ่งจะเริ่ม... ฝั่ง server อนุญาตจนถึง boarded" ซึ่งถูกแต่ยังไม่ชัดว่า UI เข้มกว่า server]**: ในแอป จุดรับแก้ไขได้ (ปุ่ม "แก้ไขจุดรับ" ใช้งานได้) ก็ต่อเมื่อ **ทั้งสองเงื่อนไขเป็นจริงพร้อมกัน**: (1) การจับคู่ยังเป็น `accepted` และ Rider ยังไม่กด "ขึ้นรถแล้ว" (2) ทริปของทั้งสองฝ่ายยัง**ไม่มีฝ่ายใดเข้าสถานะ "กำลังเดินทาง" (in_progress)** เลย (ยืนยันจาก `lib/features/matching/presentation/car_match_widgets.dart:15-19` ฟังก์ชัน `pickupEditable`: "Read-only once **either** trip started, after boarding, or when the match ended") — พูดง่าย ๆ คือ **เข้มกว่าที่ backend อนุญาต**: ฝั่ง server (design-roles.md §2) ยอมให้แก้ได้จนถึงก่อน Rider ขึ้นรถ แต่ฝั่งแอปล็อกเร็วกว่านั้นคือทันทีที่ฝ่ายใดฝ่ายหนึ่งเริ่มเดินทางแล้ว ไม่ว่าจะขึ้นรถหรือยัง
- [ ] (P0) เมื่อจุดรับที่เสนอห่างจากเส้นทางของ Driver เกินระยะที่ config กำหนด ระบบ**เตือนเท่านั้น ไม่บล็อกการบันทึก**จุดรับ; Rider เห็นผลเป็นการแจ้งเตือนแบบไป/ไม่ไป (ไม่เห็นระยะจริง เพื่อป้องกันการคำนวณย้อนหาเส้นทาง/บ้านของ Driver); Driver เห็นระยะเป็นเมตรจริงจากเส้นทางของตนเองก่อนส่ง (คำนวณในเครื่องจาก route ของตัวเอง) และยังส่งจุดนั้นต่อได้แม้เกินระยะ — **ค่าระยะเตือน = 500 เมตร ยืนยันเป็นค่าคงที่จริงในโค้ด [แก้ไขหลังตรวจโค้ด]**: `lib/core/config/service_config.dart:47` (`static const _pickupMaxDeviationM = int.fromEnvironment('PICKUP_MAX_DEVIATION_M', defaultValue: 500)`, ปรับได้ด้วย `--dart-define`) ตรงกับ `supabase/migrations/0006_driver_rider_roles.sql:29` (`match.pickup_max_deviation_m` = `'500'`) — ทั้งสองฝั่งตรงกัน ไม่ใช่ตัวเลขสมมติที่ "ยังไม่ verify" อีกต่อไป; ดู `lib/features/matching/presentation/pickup_screen.dart:74-91` สำหรับพฤติกรรม Driver คำนวณระยะเอง (`distanceToRouteM`) vs. Rider ได้แค่ boolean จาก server
- [ ] (P0) Rider กด "ขึ้นรถแล้ว" ได้เมื่อทริปทั้งสองฝ่ายอยู่ในสถานะ "กำลังเดินทาง" และมีการจับคู่ตอบรับอยู่เท่านั้น (บังคับที่ backend ไม่ใช่แค่ซ่อนปุ่มใน UI); ระบบบันทึกเวลาโดย server; กดซ้ำได้โดยไม่เกิดผลข้างเคียง (คืนเวลาที่บันทึกไว้เดิม); แจ้ง Driver ทันทีว่า Rider ขึ้นรถแล้ว — ยืนยันตรงกับ `lib/features/matching/domain/match_repository.dart:51-52` (`markBoarded`, ข้อผิดพลาด `GWM_TRIP_NOT_STARTED`/`GWM_NOT_RIDER`/`GWM_MATCH_NOT_FOUND`)
- [ ] (P0) **หลัง Rider กด "ขึ้นรถแล้ว": Driver ยกเลิกการจับคู่/ยกเลิกทริปไม่ได้อีก** (บังคับที่ backend รวมถึงกรณีเรียก API ตรง); ทางเดียวที่ทำต่อได้คือกด "ถึงแล้ว" เพื่อจบทริปของตน — ไม่มี "ลงรถกลางทาง" แยกต่างหากในแอป ยืนยันตรงกับ UI จริง: `lib/features/trip/presentation/unified_ride_screen.dart:1285` แสดงปุ่ม "ยกเลิกการจับคู่" (`ride-match-detail`) **เฉพาะเมื่อ** `m.status == MatchStatus.accepted && !m.boarded` เท่านั้น — หายไปทันทีหลัง boarded
- [ ] (P0) **ก่อน Rider ขึ้นรถ**: ทั้ง Driver และ Rider ยกเลิกการจับคู่ได้ฝ่ายใดฝ่ายหนึ่ง; เหตุผลการยกเลิก (ใครเป็นผู้ยกเลิก) เป็น**ข้อมูลภายใน** เก็บไว้สำหรับทีมงาน/ผู้ดูแลเท่านั้น (client อ่านไม่ได้ไม่ว่าฝ่ายใด); อีกฝ่ายเห็นเพียงข้อความระบบที่เป็นกลางในแชท เช่น "การจับคู่ถูกยกเลิก" โดยไม่ระบุเหตุผลหรือว่าใครเป็นผู้ยกเลิก (ข้อความจะต่างไปเล็กน้อยถ้าอีกฝ่ายกำลังเดินทางอยู่ขณะนั้น)
- [ ] (P0) เมื่อการจับคู่ถูกยกเลิกก่อนทริปเริ่ม/ยังไม่หมดอายุ **ทริปของทั้งสองฝ่ายกลับเข้าสู่ผลการค้นหาโดยอัตโนมัติทันที** (ไม่ต้องรอ job เบื้องหลัง เป็นผลจากการไม่มี accepted match อีกต่อไป)
- [ ] (P0) การไม่มาตามนัด (no-show): **มีเฉพาะฝั่ง Driver รายงานว่า Rider ไม่มา** ได้เมื่อทริปของ Driver อยู่ในสถานะ "กำลังเดินทาง" มีการจับคู่ตอบรับ และ Rider ยังไม่กด "ขึ้นรถแล้ว" เท่านั้น; ไม่มี timeout อัตโนมัติ ไม่มีบทลงโทษอัตโนมัติต่อ Rider ในระบบ; Rider ที่ถูกรายงานเห็นเพียงข้อความกลาง "การจับคู่สิ้นสุดแล้ว คุณเดินทางต่อได้ตามปกติ" ไม่ถูกแจ้งตรง ๆ ว่าตนถูกรายงาน no-show — ยืนยันคำต่อคำเกือบทั้งหมดจาก docstring จริงในโค้ด: `lib/features/matching/domain/match_repository.dart:54` "Driver only: 'คนนั่งไม่มาตามนัด' (no timer, no penalty; reason is internal)" และ `lib/features/matching/presentation/matching_providers.dart:199-200`
- [ ] (P0) ไม่มี RPC/ปุ่มแยกสำหรับ "Driver ไม่มาตามนัด" — ถ้า Driver ไม่มา Rider ใช้ปุ่มยกเลิกการจับคู่ปกติของตนเอง
- [ ] (P0) เมื่อทริปฝ่ายใดฝ่ายหนึ่งถูกยกเลิกหรือหมดอายุขณะมีการจับคู่ตอบรับอยู่ การจับคู่นั้นถูกปิดโดยอัตโนมัติในธุรกรรมเดียวกัน (มีข้อความระบบต่อท้ายข้อความ "ทริปถูกยกเลิก" เดิม) แต่**ทริปของอีกฝ่ายไม่ถูกยกเลิกไปด้วย** (กลับเข้าค้นหาเองถ้ายังไม่เริ่ม)
- [ ] (P0) การแจ้งเตือนยกเลิก/no-show ส่งถึงอีกฝ่ายทันทีผ่าน Realtime ของแอป + local notification (ไม่มี remote push ในรอบนี้ — ผู้ใช้ที่ปิดแอปอยู่อาจไม่เห็นจนกว่าจะเปิดแอปอีกครั้ง; ยืนยันจาก `docs/PROJECT_STATUS.md:48` "ยังไม่มีไฟล์ Edge Function สำหรับ push เลย" — สถานะนี้ยังจริงอยู่ ณ เวลาที่ project status อัปเดตล่าสุด แม้จะเริ่มมีโครง push ตั้งแต่รอบ 7 (US-42) แล้วก็ตาม)
- [ ] (P0) Rider ที่คำขอถูกปิดแบบอัตโนมัติ (เพราะ Driver ตอบรับคนอื่น) ส่งคำขอใหม่ไปยังทริปเดิมของ Driver ได้เอง; คำขอที่ถูกยกเลิก/ปฏิเสธด้วยมือ (ไม่ใช่ auto-close) ส่งซ้ำไปยังคู่เดิมไม่ได้
- [ ] (P1) การตรวจระยะจุดรับเทียบเส้นทาง Driver แบบละเอียด/แม่นยำกว่าการเตือนแบบ boolean ปัจจุบัน — ยังไม่ทำในรอบนี้เพราะความเสี่ยงด้านความเป็นส่วนตัว (ดู NFR)
- [ ] (P1) คนขับแจ้ง "ถึงจุดรับแล้ว" แบบข้อความสำเร็จรูปในแชท — เพิ่มเข้ามาในรอบ 6 (US-33) พึ่งพา US-18 โดยตรง ยืนยันมี implement จริง: `lib/features/trip/presentation/unified_ride_screen.dart:349-370` (`_sendArrivedAtPickup`, throttle 1 ครั้ง/นาที ตาม snackbar `R6.arrivedAtPickupThrottled`) **ไม่ได้อยู่ใน base AC ของ US-18 เดิม** แต่บันทึกไว้ที่นี่เพื่อความครบถ้วน

**หมายเหตุความเสี่ยง (จาก design-roles.md §5.3, ยืนยันด้วยโค้ด):** การตรวจระยะจุดรับเทียบเส้นทาง Driver ถ้าคืนค่าระยะจริงให้ Rider จะเป็นช่องทางให้ Rider คำนวณ/คลำเส้นทางและที่อยู่ของ Driver ได้ (oracle attack) จึงจำกัดไว้ที่การคืนค่า boolean เท่านั้นสำหรับ Rider (`pickup_screen.dart:86-90` เส้นทาง `route: m.iAmDriver ? (trip?.route ?? const []) : const []` — Rider ไม่เคยได้รับ route ของ Driver เลยแม้แต่ในแผนที่)

### US-19: ลงทะเบียนเป็นคนขับ / ยกเลิกการลงทะเบียน [P0 / ตรวจสอบเอกสาร P1] (รอบ 4)
[RECONSTRUCTED FROM: docs/design-roles.md §11.1-11.3, §11.7; **ตรวจยืนยันกับโค้ดจริงแล้ว**: `lib/features/roles/domain/role_state.dart`, `lib/features/roles/data/supabase_role_repository.dart`, `lib/features/roles/presentation/role_providers.dart`, `driver_register_screen.dart`, `role_cards.dart`, `supabase/migrations/0008_driver_registration.sql`]

**User story:** As a Rider ที่ต้องการขับรถพาเพื่อนร่วมทางกลับบ้านบ้าง, I want ลงทะเบียนเป็นคนขับด้วยข้อมูลรถและการรับรองตนเอง และยกเลิกการลงทะเบียนได้เมื่อไม่ต้องการแล้ว, so that ฉันสลับไปเป็นคนขับได้โดยไม่ต้องสมัครบัญชีใหม่ และยังควบคุมสถานะของตัวเองได้เสมอ

**Acceptance Criteria:**

- [ ] (P0) เวลาที่ลงทะเบียนครั้งแรกและเวลาที่รับรองตนเอง **เป็นค่าที่ server กำหนดเสมอ ไม่รับค่าจากฝั่งแอป** — ยืนยันจาก `supabase/migrations/0008_driver_registration.sql:119` (`set driver_registered_at = now(), licence_declared_at = now()`)

- [ ] (P0) ข้อมูลรถ (ทะเบียน/รุ่น/สี) **ยังคงถูกเก็บไว้ 1 ชุดต่อบัญชี** หลังยกเลิกลงทะเบียน (ไม่ลบทิ้ง) เห็นได้เฉพาะเจ้าของบัญชี ไม่ใช้ในการแชร์/SOS/จับคู่ใด ๆ จนกว่าจะลงทะเบียนใหม่ (ลงทะเบียนใหม่ = ฟอร์มเติมข้อมูลรถเดิมให้อัตโนมัติ แก้ไขได้ก่อนยืนยัน) — ยืนยันตรงกับ UI: `driver_register_screen.dart:74-83,206-216` (`_seed`, banner `D.prefillBanner`)

**หมายเหตุ edge case ที่ implement ไว้ (design-roles.md §11.7):** race ระหว่างสร้างทริปคนขับกับยกเลิกการลงทะเบียนพร้อมกันจากสองอุปกรณ์ ถูกจัดการด้วยลำดับ lock ที่ทำให้ผลลัพธ์สอดคล้องกันเสมอ (ธุรกรรมที่สำเร็จก่อนชนะ อีกธุรกรรมเห็นสถานะใหม่แล้วถูกปฏิเสธอย่างถูกต้อง ไม่เกิดทริปคนขับของบัญชีที่ไม่ได้ลงทะเบียน) — ฝั่งแอปมี fallback รองรับผลจาก race นี้ด้วย: `role_providers.dart:188-197` เมื่อ `set_active_role` คืน `GWM_NOT_A_DRIVER` (เช่นยกเลิกลงทะเบียนจากอุปกรณ์อื่นแล้ว) แอปจะปรับสถานะในเครื่องกลับเป็น Rider ทันทีโดยไม่ต้องรอ refresh

### US-20: สลับบทบาทที่ใช้งาน (Rider ↔ Driver) และโทนของแอป [P0] (รอบ 4)
[RECONSTRUCTED FROM: docs/design-roles.md §11.1-11.3; **ตรวจยืนยันกับโค้ดจริงแล้ว**: `lib/features/roles/presentation/role_providers.dart`, `role_strip.dart`, `role_cards.dart`, `lib/app.dart`, `lib/core/theme/tone.dart`]

**User story:** As a ผู้ใช้ที่ลงทะเบียนเป็นทั้งคนนั่งและคนขับ, I want สลับ "บทบาทที่ใช้งานอยู่" ได้ง่าย ๆ ด้วยการแตะครั้งเดียว และเห็นหน้าตา/โทนสีของแอปที่บอกชัดว่ากำลังอยู่โหมดไหน, so that ฉันไม่สับสนว่ากำลังใช้แอปในฐานะอะไร และสลับไปมาระหว่างสองบทบาทได้สะดวก

**Acceptance Criteria:**
- [ ] (P0) ทุกบัญชีมี "บทบาทที่ใช้งานอยู่" (active role) เริ่มต้นเป็น **คนนั่งเสมอ**; บัญชีที่ยังไม่ลงทะเบียนเป็นคนขับ (US-19) ตั้งบทบาทที่ใช้งานอยู่เป็นคนขับไม่ได้ ไม่ว่าจะพยายามผ่านช่องทางใด (บังคับที่ backend); ในแอปยังกันซ้ำที่ฝั่ง UI ด้วย: ปุ่มสลับ (`role-switch`) จะไม่แสดงเลยสำหรับบัญชีที่ยังไม่ลงทะเบียน (ยืนยัน `role_strip.dart:141` `canSwitch = s.registered == true || active == ActiveRole.driver`)
- [ ] (P0) บัญชีที่ลงทะเบียนเป็นคนขับแล้วสลับบทบาทที่ใช้งานอยู่ได้ด้วยการแตะครั้งเดียว จากแถบที่ปรากฏอยู่ใต้แอปบาร์ของหน้าหลักทั้ง 5 แท็บ (`role_strip.dart:108-175`, widget `RoleStrip`) และจากหน้าโปรไฟล์ (Me tab, `role_cards.dart:256-362` `MyRolesCard` แบบ segmented switch 2 ปุ่ม)
- [ ] (P0) **[แก้ไข/เพิ่มรายละเอียดหลังตรวจโค้ด]** กลไกการสลับ**ไม่สมมาตร**ระหว่างสองทิศทาง (ฉบับร่างแรกไม่ได้ระบุจุดนี้ชัดเจนพอ): สลับไป **"คนนั่ง"** ทำแบบ optimistic ทันทีในเครื่องก่อน (ไม่ต้องรอ server) แล้วค่อย sync — ถ้าออฟไลน์ระบบจะจัดคิวไว้ส่งภายหลังโดยอัตโนมัติ (`gwm.roleSync.<uid>` ใน SharedPreferences) แต่สลับไป **"คนขับ"** ต้องรอคำตอบจาก server ก่อนเสมอ (ปุ่มโชว์ loading spinner ระหว่างรอ) จะไม่เปลี่ยนโทน/สถานะจนกว่า server ยืนยัน — ถ้าออฟไลน์ขณะพยายามสลับเป็นคนขับ ระบบแจ้งว่าใช้ไม่ได้ทันที **ไม่**คิวไว้ (ยืนยันตรงจาก `role_providers.dart:153-201` ฟังก์ชัน `switchTo`, คอมเมนต์บรรทัด 153-154 "Driver needs the server first (tone does not change until it confirmed); Rider is applied at once and synced later if the network is down")
- [ ] (P0) "บทบาทที่ใช้งานอยู่" เป็นเพียง**ค่าเริ่มต้น**สำหรับตอนสร้างทริปใหม่และโทนสีของแอปเท่านั้น — **ไม่มีผลย้อนหลัง**ต่อทริปที่สร้างไปแล้ว (role ของทริปผูกกับทริป ไม่ใช่กับบทบาทที่ใช้งานอยู่ขณะนั้น ดู US-16); สลับบทบาทระหว่างที่มีทริปอยู่ไม่ทำให้ role/ผลค้นหา/คำขอของทริปเดิมเปลี่ยน และผู้ใช้เห็นข้อความยืนยันว่าทริปที่มีอยู่ยังเป็นทริปเดิมเหมือนเดิม (snackbar `D.switchedActiveTrip` — ยืนยัน `role_strip.dart:76-84`)
- [ ] (P0) แอปมี 2 โทนสี (ธีม) ตามบทบาทที่ใช้งานอยู่: โทนคนนั่ง (ค่าเริ่มต้นเดิมของแอป) และโทนคนขับ (เข้มกว่า + สี amber เป็นจุดเน้น); การสลับบทบาทสลับธีมทั้งแอปพร้อมแอนิเมชันเปลี่ยนผ่าน **= 200 มิลลิวินาที (cross-fade)** [แก้ไขหลังตรวจโค้ด — ยืนยันตัวเลขจริง]: `lib/app.dart:46` (`themeAnimationDuration: ... const Duration(milliseconds: 200)`) ยกเว้นเมื่อผู้ใช้เปิดการตั้งค่า "ลดการเคลื่อนไหว (reduce motion)" ของระบบซึ่งจะเปลี่ยนทันทีไม่มีแอนิเมชัน (`app.dart:27,46` `reduceMotion ? Duration.zero : ...`)
- [ ] (P0) หน้าจอที่ผูกกับทริป/การจับคู่ที่กำลังดำเนินอยู่ (รายละเอียดทริป, กำลังเดินทาง, ถึงแล้ว, แชร์ทริป, หน้าการจับคู่, จุดรับ, แชท, รายชื่อผู้สมัคร/คำขอ, SOS) ใช้โทนสีตาม **role ของทริปนั้น** เสมอ ไม่ใช่บทบาทที่ใช้งานอยู่ปัจจุบันของผู้ใช้ — ป้องกันความสับสนเมื่อผู้ใช้สลับบทบาทขณะมีทริปค้างอยู่
- [ ] (P0) การสลับบทบาทที่ใช้งานอยู่ **ไม่กระทบ**สิทธิ์การมองเห็น/การจับคู่/ผลการค้นหาของทริปที่มีอยู่แล้ว (ตัดสินจาก role ของทริปเสมอ ตาม US-6/US-16)
- [ ] (P0) ปุ่ม SOS ทำงานเหมือนกันทุกบทบาท/ทุกโทน และไม่ถูกขวางหรือหน่วงโดยการสลับบทบาท สถานะการลงทะเบียนคนขับ หรือการที่อุปกรณ์ออฟไลน์ (ดู US-10)
- [ ] (P1) การสลับบทบาทขณะอุปกรณ์ออฟไลน์ถูกจัดคิวไว้ส่งเมื่อกลับมาออนไลน์ — **เฉพาะทิศทางสลับไป "คนนั่ง" เท่านั้น** [แก้ไขหลังตรวจโค้ด — ดู bullet ด้านบนเรื่องความไม่สมมาตร]; สลับไปคนขับขณะออฟไลน์ไม่ถูกคิว ถูกปฏิเสธทันทีให้ผู้ใช้ลองใหม่เอง
- [ ] (P0) ทั้งสองโทนสีผ่านเกณฑ์ความคมชัดสี (contrast ratio) ระดับ WCAG AA สำหรับข้อความหลัก (มีฟังก์ชันตรวจสอบจริงในโค้ด: `lib/core/theme/tone.dart:337-338` `double contrastRatio(Color a, Color b)`), รองรับโปรแกรมอ่านหน้าจอ (screen reader) ด้วยป้ายบทบาทที่เป็นทั้งไอคอนและข้อความ (`role_strip.dart:32-33` ใช้ `Semantics` + ข้อความไม่ใช้สีอย่างเดียว), และรองรับการขยายขนาดตัวอักษรของระบบ: แถบสลับบทบาทจัดเรียงเป็นแนวตั้งเมื่อขนาดตัวอักษรขยาย **≥ 1.3 เท่า** [ยืนยันค่าตรงเป๊ะ]: `role_strip.dart:143-144` (`final scale = MediaQuery.textScalerOf(context).scale(14) / 14; final stacked = scale >= 1.3;`)
- [ ] (P1) ประสิทธิภาพการสลับบทบาท/เปลี่ยนโทนสีอยู่ที่ประมาณ ~1 วินาที (ตัวเลขนี้ยังไม่พบค่าคงที่ตรง ๆ ในโค้ด — แอนิเมชันธีมเองใช้ 200ms ตาม bullet ข้างบน แต่เวลารวมรวมการเรียก RPC ไป-กลับอาจมากกว่านั้น เป็นเป้าหมายด้าน UX ไม่ใช่ timeout ที่ enforce จริง)
- [ ] (P0) การสลับบทบาทไม่ทำให้ระบบเปลี่ยนโทนหรือ role ของทริปโหมดอื่นที่ไม่ใช่ car (เดิน/รถสาธารณะ/แท็กซี่ ยังไม่มี role อยู่แล้ว)

**Out of scope ของรายละเอียด UI:** ไอคอนรอบข้าง ตำแหน่งสวิตช์ เฉดสีจริง และรายละเอียดแอนิเมชันเป็นหน้าที่ของฝ่ายออกแบบ ไม่ใช่ขอบเขตของ requirement นี้

### ความเป็นส่วนตัวของข้อมูลรถและ role (รอบ 3) [P0]
[RECONSTRUCTED FROM: docs/design-roles.md §5 (Privacy/blur review) ทั้งหมด + ยืนยันบางส่วนกับโค้ดในรอบตรวจสอบที่ 2]
- [ ] ทะเบียน/รุ่น/สีรถ**ไม่ปรากฏ**ในผลการค้นหา, คำขอที่ยังรอตอบ/ถูกปฏิเสธ/ถูกปิด — แสดงได้เฉพาะ Rider ที่การจับคู่ถูกตอบรับแล้วเท่านั้น (ในแอป) และเจ้าของรถเอง
- [ ] ข้อมูลที่ส่งออกนอกแอป (ลิงก์แชร์แบบ public/anon-callable, ข้อความ SOS) มีเฉพาะ**ทะเบียนรถ**และชื่อที่แสดงของ Driver เท่านั้น ไม่มีรุ่น/สีในผลลัพธ์ของทั้งสองช่องทางนี้ และเฉพาะเมื่อ Driver เปิดสวิตช์ยินยอม ณ เวลาที่สร้างข้อมูลนั้น ๆ — บังคับที่ backend ไม่ใช่การซ่อนใน UI
- [ ] การตรวจสอบระยะจุดรับเทียบเส้นทางของ Driver (US-18) คืนค่าเป็น boolean เท่านั้น ไม่คืนระยะจริง และจำกัดจำนวนครั้งที่เรียกได้ต่อชั่วโมงต่อคู่จับคู่ เพื่อป้องกันไม่ให้ Rider ใช้เป็นช่องทางคำนวณย้อนหาเส้นทาง/ที่อยู่ของ Driver (oracle attack) — ยืนยันซ้ำในรอบตรวจสอบนี้ว่า route ของ Driver ไม่เคยถูกส่งให้ Rider ในแอปเลย (`pickup_screen.dart:132`)
- [ ] หลัง Rider กด "ขึ้นรถแล้ว" ตำแหน่งสดของ Rider **ไม่ถูกส่งให้ Driver อีกต่อไป**
- [ ] เหตุผลของการยกเลิกการจับคู่/รายงาน no-show เป็นข้อมูลภายในที่ client อ่านไม่ได้ทุกกรณี; ข้อความในแชทที่อีกฝ่ายเห็นเป็นกลางเสมอ
- [ ] ข้อมูลทะเบียนรถที่ส่งเข้า RPC (upsert_my_vehicle/register_driver) ห้ามถูกบันทึกใน log/ระบบติดตาม error แบบดิบ
- [ ] ความเสี่ยงคงเหลือที่ยอมรับ: ทะเบียนที่ถูกแชร์ออกไปแล้วอาจรั่วต่อได้อีกทอดหนึ่งนอกการควบคุมของระบบ; ทะเบียนที่ผู้ใช้กรอกเป็นการแจ้งเองไม่มีการตรวจสอบกับหน่วยงานจริงใน MVP

## Edge Cases ที่ต้องพิจารณา
[[เนื้อหาสูญหายส่วนใหญ่ — ไม่พบ base edge case ทั่วไป (ก่อนรอบ 3) ที่กู้คืนได้]]

### Edge Cases เพิ่มเติม: Driver/Rider (รอบ 3)
[[เนื้อหาสูญหายบางส่วน]]
- คนเดียวมีทริป car เป็น Driver และ Rider ในเวลาทับซ้อน: ไม่ได้ เพราะจำกัด 1 ทริป "รอ/กำลังเดินทาง" ต่อผู้ใช้ (US-5 AC6) (รอบ 4: ยืนยันโดยผู้ใช้ ยังเป็นจริงหลังมีการถือสองบทบาท; ทำได้เฉพาะ "ต่างเวลากัน")
- Driver ยังไม่มีข้อมูลรถ / ข้อมูลรถกรอกไม่ครบ: สร้างทริปคนขับไม่ได้จนกว่าจะกรอกครบ (รอบ 4: ลงทะเบียนคนขับไม่สำเร็จจนกว่าจะกรอกครบ)
[[เนื้อหาสูญหายบางส่วน]]
- ทริป car เดิม (ก่อนรอบ 3) ไม่มี role: ไม่ปรากฏในค้นหา

### Edge Cases เพิ่มเติม: ลงทะเบียนคนขับ / สลับบทบาท (รอบ 4)
[RECONSTRUCTED FROM: docs/design-roles.md §11.3, §11.5, §11.7; ยืนยัน/เพิ่มรายละเอียดจากโค้ดในรอบตรวจสอบที่ 2]
- บัญชีที่ยังไม่ลงทะเบียนพยายามสร้างทริปคนขับผ่านการเรียก API ตรงหรือแก้ค่าในแอป: server ปฏิเสธเสมอ
- บัญชีที่ลงทะเบียนคนขับพยายามยกเลิกการลงทะเบียนขณะมีทริปคนขับ scheduled/in_progress หรือมีการจับคู่ตอบรับที่ตนเป็นคนขับ: ถูกปฏิเสธ ต้องยกเลิก/จบทริปหรือการจับคู่ก่อน — แอป pre-check ในเครื่องก่อนแสดง dialog ยืนยัน (`role_cards.dart:266-289`) แต่ server ยังเป็นด่านตัดสินจริงเสมอ
- Race: สร้างทริปคนขับพร้อมกับยกเลิกการลงทะเบียนจากสองอุปกรณ์พร้อมกัน: ลำดับการล็อกข้อมูลถูกออกแบบให้ผลลัพธ์สอดคล้องกันเสมอ; ฝั่งแอปมี fallback เมื่อพบว่า server ปฏิเสธ `set_active_role` ด้วย `GWM_NOT_A_DRIVER` หลังเหตุการณ์นี้ (ปรับสถานะในเครื่องกลับเป็น Rider ทันที — `role_providers.dart:188-197`)
- ยกเลิกการลงทะเบียนสำเร็จ: ข้อมูลรถยังอยู่แต่ไม่แสดงให้ใครนอกจากเจ้าของ ไม่ใช้ในการแชร์/SOS/จับคู่ จนกว่าจะลงทะเบียนใหม่
- ลงทะเบียนใหม่หลังเคยยกเลิก: ฟอร์มเติมข้อมูลรถเดิมให้อัตโนมัติ (พร้อม banner แจ้งผู้ใช้) แก้ไขได้ก่อนยืนยัน
- แอปเวอร์ชันเก่าส่งเวอร์ชันข้อความรับรองที่ล้าสมัย: ถูกปฏิเสธ (`GWM_DECLARATION_VERSION_STALE`)
- ผู้ใช้สลับบทบาทที่ใช้งานอยู่ขณะมีทริปที่สร้างด้วย role ตรงข้ามอยู่แล้ว: ทริปเดิมไม่เปลี่ยน role ทำงานตามปกติ ผู้ใช้เห็นข้อความอธิบายว่าทริปเดิมยังเป็นทริปเดิม (`D.switchedActiveTrip`)
- ขอลบบัญชี (soft delete) ขณะลงทะเบียนเป็นคนขับและมี Rider ที่กด "ขึ้นรถแล้ว" ค้างอยู่: คำขอลบบัญชีถูกปฏิเสธด้วยเหตุผลเดียวกับการยกเลิกทริประหว่างมี Rider boarded — เป็นพฤติกรรมที่ตั้งใจ (design-roles.md §10 Q-1)
- ข้อมูลทดสอบ/ทริปคนขับที่มีอยู่ก่อนเปิดใช้ระบบลงทะเบียนคนขับของบัญชีที่ยังไม่ลงทะเบียน: ถูกปรับสถานะเป็นยกเลิกเฉพาะช่วง migrate ข้อมูล dev ก่อนเปิดใช้งานจริง
- **[เพิ่มจากการตรวจโค้ด]** พยายามสลับเป็น "คนขับ" ขณะอุปกรณ์ออฟไลน์: ปฏิเสธทันที ไม่คิวไว้ (ต่างจากสลับเป็น "คนนั่ง" ที่คิวได้) — `role_providers.dart:176-201`
- **[เพิ่มจากการตรวจโค้ด]** กดสลับบทบาทซ้ำระหว่างที่คำขอก่อนหน้ายังไม่เสร็จ: คำขอที่สองถูกเพิกเฉย (ไม่ยิงซ้ำ) — `role_providers.dart:155,157` (`if (uid == null || state.switching.isSwitching) return RoleSwitchOutcome.unchanged`)

## Out of Scope (MVP 0.1)
[[เนื้อหาสูญหาย — รายการพื้นฐานของ MVP 0.1 ก่อนรอบ 3 หายไป ด้านล่างคือเฉพาะรายการที่เพิ่มจากรอบ 3-4 ซึ่งกู้คืนได้ครบ — คัดลอกจาก requirements.md เดิมตรง ๆ ไม่มีการแก้ไข]]
- (รอบ 3) การรับเพื่อนร่วมทางมากกว่า 1 คนต่อคนขับ และช่องกรอกจำนวนที่นั่ง
- (รอบ 3) Driver↔Driver และ Rider↔Rider สำหรับทริป car; role กับโหมดเดิน/ขนส่งสาธารณะ/แท็กซี่
- (รอบ 3) การจัดการเงินในแอปทุกรูปแบบ (ค่าโดยสาร แบ่งค่าน้ำมัน ค่าประมาณ) เลื่อนเป็น P2 และต้องผ่านการตรวจโดยฝ่ายกฎหมายก่อน
- (รอบ 3) การตรวจสอบใบขับขี่/ทะเบียนรถ/ประกันภัย (license verification เป็น P1 หลัง MVP 0.1); ใน MVP ข้อมูลรถเป็นการแจ้งเอง
- (รอบ 3) การให้คะแนน/ระบบชื่อเสียงคนขับ-คนนั่ง และบทลงโทษอัตโนมัติจาก no-show
- (รอบ 3) การจับคู่แบบมีจุดแวะ/รับหลายจุด และการปรับเส้นทางคนขับตามจุดรับอัตโนมัติ
- (รอบ 3) การส่งรุ่น/สีรถของ Driver ออกนอกแอปผ่านแชร์/SOS ของ Rider และการบังคับให้ Driver เปิดสวิตช์ยินยอมเพื่อสร้างทริปหรือถูกจับคู่
- (รอบ 4) การตรวจสอบเอกสารใบขับขี่จริง การเก็บเลขใบขับขี่/รูปเอกสาร/ตรวจวันหมดอายุ และการตรวจว่าผู้ขับเป็นเจ้าของรถ (P1 หลัง MVP 0.1; MVP ใช้การรับรองตนเองเท่านั้น)
- (รอบ 4) การมีหลายคันต่อบัญชี (ยังคงข้อมูลรถ 1 ชุดต่อบัญชี) และการลงทะเบียนคนขับหลายครั้งพร้อมกันหลายรถ
- (รอบ 4) การถือ role อื่นนอกจาก Rider/Driver, การขออนุมัติ/รอผู้ดูแลอนุมัติการลงทะเบียนคนขับ (ลงทะเบียนแล้วมีผลทันที) และการเพิกถอนสถานะคนขับโดยผู้ดูแล (ไม่มีหน้า admin)
- (รอบ 4) การมีมากกว่า 1 ทริปที่ใช้งานพร้อมกันต่อผู้ใช้ — ยังจำกัด 1 ทริปที่ใช้งาน
- (รอบ 4) การกำหนดรายละเอียดหน้าตา (ไอคอนรอบข้าง ตำแหน่งสวิตช์ เฉดสีจริง แอนิเมชัน) ของการสลับบทบาทและโทนสองแบบ เป็นหน้าที่ของฝ่ายออกแบบ; ธีมแบบผู้ใช้ปรับเองหรือธีมมืด/สว่างเพิ่มเติม
- (รอบ 4) การบังคับให้ผู้ใช้เลือกบทบาทตอนสมัคร และการเปลี่ยน role ของทริปที่สร้างแล้ว (ยังคงห้ามตามรอบ 3)
